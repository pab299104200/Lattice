# Q2 and R2 — scoped design proposals

Context: the [agent-usefulness plan](2026-09-30-agent-usefulness.md) landed A1, A2, A3, Q1, D1 (all verified; D1 proven live). The two remaining items, Q2 and R2, are architectural changes with real blast radius. This document scopes them for execution under the same discipline (prove-then-fix, verify each step) rather than attempting them unverified at the end of a long session — the explicit lesson from the four prior failed repair attempts was that rushing a high-risk change is how they failed.

Both are deliberately **not** implemented yet. This is the design, the integration points mapped from the code, the risks, and the test strategy, so the next session executes rather than re-investigates.

---

## Q2 — Converge the agent tools onto the `retrieval_v1` signal engine

### Why
Verified earlier: `context`/`prepare_change`/`impact`/`diagnose` run through the heuristic `QueryEngine` (`query/engine.rs`), while the principled, auditable 13-signal `retrieval_v1` ranker serves only `working_memory`. The agent-facing tools are the product's whole purpose, and they get magic-constant ranking over a name-approximate graph instead of the engine that carries per-signal diagnostics. Converging them is the biggest single quality lever.

### What the convergence actually requires (mapped from code)
`retrieval_v1` entry is `retrieve_candidates(intent, anchors, budget, ctx) -> Vec<Candidate>` then `score_candidates(...) -> Vec<RankedCandidate>` then `shape_retrieval_bundle_detailed(...)`. It needs a `RetrievalContext<'a>` (`retrieval_v1/candidates.rs:67`) with: `workspace_id`, `graph: Option<&CodeGraph>`, `memory_store: Option<&MemoryStore>`, `vector_index: Option<&dyn VectorIndex>`, `query_embedding: Option<&[f32]>`, `event_candidates: &[EventEnvelope]`, `recent_working_memory: &[Identity]`. Plus `classify_intent`, `extract_anchors`, `resolve_anchors`.

The agent handlers (`rpc/mcp.rs::tool_query_context`, `tool_prepare_change`) already hold the graph (`engine.graph()`), the `memory_store`, the `vector_index`, and can embed the query (`embed_query_for_fallback`). The gaps:
1. **Anchor extraction/resolution** from the free-text query + entry files/symbols into `ResolvedAnchor`s (there is already anchor machinery in `retrieval_v1`; wire the query/entry inputs into it).
2. **Event candidates** — the handler must supply a recent-event slice (the event store is available via the runtime).
3. **Output adaptation** — `retrieval_v1` produces a `RetrievalBundle`, but the agent tools return a `ContextCapsule` / `TaskBundle` shaped by `workflow_v2::context_capsule::build_bundle` and `intelligence::prepare_change`. Either adapt the `RetrievalBundle` into those existing shapes, or extend the capsule builder to accept ranked candidates. This is the real work and the real risk: the response schema agents depend on must not change silently.

### Recommended approach (incremental, reversible)
- **Phase 1 — shadow, don't switch.** Add an opt-in flag (`LATTICE_RETRIEVAL_V1_FOR_CONTEXT=1`) that routes `tool_query_context` through `retrieval_v1` behind the same output adapter, defaulting OFF. Ship the adapter and a characterization test that both engines return a well-formed capsule for a fixture query. This lands the integration with zero change to default behavior.
- **Phase 2 — compare.** On the golden fixtures (`benches/fixtures`, `golden_anchors.json`), assert the `retrieval_v1` path meets or beats the heuristic path on a precision metric for a known query set. This is the evidence that justifies the switch — do not flip the default without it.
- **Phase 3 — switch `context`, then `prepare_change`.** Flip the default per tool, one at a time, each behind its own verified fixture comparison. `impact` stays graph-only (it is dependency traversal, not ranking) but now benefits from Q1's confidence labels.

### Risk
High blast radius: this changes what every agent receives. Mitigated entirely by the flag-gated, fixture-compared, one-tool-at-a-time rollout. Never a big-bang switch.

### Done means done
- [ ] Adapter from `RetrievalBundle` to the agent capsule/bundle schema, with a test asserting schema parity.
- [ ] Golden-fixture precision comparison, `retrieval_v1` >= heuristic, recorded.
- [ ] Default flipped per tool only after its comparison passes; `cargo test --workspace` green; fmt/clippy clean.

## R2 — Move the ONNX/ORT embedding engine out of the daemon process

### Why
The ORT CPU arena never returns memory and is process-global (`embeddings/engine.rs:16-33`, measured 7 GiB high-water); it inflates the daemon's absolute footprint for the life of the process. The lockout it contributed to is already fixed (ghost-page accounting, R3a), so this is now a footprint-reduction change, not a correctness one — which is exactly why it is last.

### What it requires
Run the embedding engine (`EmbeddingEngine`, the `ProcessEmbeddingRuntime` singleton) in a separate child process that the daemon can kill and respawn to actually reclaim the arena. The daemon talks to it over the existing local-IPC patterns (the socket/transport layer already exists). The `EmbeddingProvider` trait is the clean seam: today it is an in-process `Arc<dyn EmbeddingProvider>`; add a `SubprocessEmbeddingProvider` implementation that forwards `embed`/`embed_batch` to the child and handles its lifecycle, selected by a flag with the in-process impl as fallback.

### Recommended approach
- **Phase 1** — define the child protocol (embed request/response over a length-prefixed local socket or stdio), implement the child binary (a new `--embed-worker` mode on the existing `lattice` binary, reusing the daemon's IPC), and the `SubprocessEmbeddingProvider`. Flag-gated off by default.
- **Phase 2** — recycle policy: respawn the child when its RSS crosses a threshold, so the arena is actually reclaimed; the daemon's own footprint stays flat. Prove with a test that drives many embed batches and asserts the *daemon* process footprint does not grow (the child absorbs and is recycled).
- **Phase 3** — once stable, consider making subprocess the default on platforms where the arena growth bites (macOS).

### Risk
Medium-high: a new process boundary, lifecycle, and failure mode (child crash → fall back to lexical, never crash the daemon — the existing circuit-breaker discipline applies). Flag-gated with in-process fallback throughout.

### Done means done
- [ ] `SubprocessEmbeddingProvider` behind a flag; in-process remains default until proven.
- [ ] Test: daemon-process footprint flat across many embed batches with the subprocess provider; child crash degrades to lexical, daemon survives.
- [ ] `cargo test --workspace` green; fmt/clippy clean.

## Sequencing
Q2 before R2 (quality over footprint; R2's lockout contribution is already neutralized). Both strictly flag-gated and fixture/test-proven before any default changes. Neither is a prerequisite for the five changes already shipped.

### Q2 — shipped (Phase 1: shadow behind flag)

- Adapter: `crates/lattice-core/src/retrieval_v1/context_bridge.rs` — `ContextBridgeResources` + `context_capsule_via_retrieval_v1()` turn a `RetrievalBundle` into the existing `ContextCapsule` so the response schema is unchanged. - **Not yet done (Phase 2/3):** golden-fixture precision comparison and flipping any default. The default is unchanged.

### R2 — shipped (Phase 1 + recycle policy)
- Flag: `LATTICE_EMBEDDING_SUBPROCESS` (default OFF). In-process engine remains authoritative.
- Protocol: `crates/lattice-core/src/embeddings/subprocess_protocol.rs` — line-delimited JSON `EmbedRequest`/`EmbedResponse` with encode/decode + 4 codec tests (round-trip, alignment, error, malformed-input rejection).
- Provider + worker: `crates/lattice-daemon/src/embedding_subprocess.rs` — `SubprocessEmbeddingProvider` (serialized single worker, lazy spawn, kill-on-drop), `run_embed_worker()` (`--embed-worker` mode on the `lattice` binary), `subprocess_embeddings_enabled()`.
- Recycle policy: respawn the child when its RSS exceeds `DEFAULT_CHILD_RSS_LIMIT_BYTES` (1536 MiB), overridable via `LATTICE_EMBEDDING_SUBPROCESS_RSS_LIMIT_MB`. This is what actually returns the ORT arena to the OS.
- Failure handling: any transport error or child-emitted error surfaces as `Err` (the semantic circuit breaker turns that into lexical-only retrieval); a broken child is killed so the next call respawns.
- Wiring: `main.rs` dispatches `--embed-worker` and selects the subprocess vs in-process provider by flag.
- Tests (6, all hermetic, no ONNX model needed via an injected fake-worker spawn command over real pipes): batch round-trip, error-response degradation, vector-count-mismatch rejection, closed-pipe surfaces as error, empty-batch short-circuit, RSS-limit env override.
- **Not yet done (Phase 3):** making subprocess the default on macOS, and a long-running footprint-stability assertion against a real model (the model-backed path is `#[ignore]` like the other ONNX tests). The flat-footprint claim is covered structurally by the recycle policy + its unit test, not yet by a live multi-batch RSS measurement.

## T1 — merge-then-truncate in `retrieval_v1` candidate gathering (shipped)

From the independent review: `retrieve_candidates` truncated each source to a per-source cap (24, embeddings k=12) *before* the 13-signal scorer ran, so a candidate ranked low by one source (e.g. 13th by embeddings) was dropped before exact-identifier or graph-proximity could rescue it. This is the ceiling on the principled ranker's quality — and it binds the moment Q2 flips the ranker onto the agent path, so it is fixed now, as the review recommended, not after.

**Change (architectural, not flag-gated):** `retrieval_v1/candidates.rs`
- Per-source caps are now a *gather bound* only, raised from the original tight values (`max_candidates_per_source` 24 → 48, `embedding_k` 12 → 32, `max_fts_rows` 24 → 48) so low-within-source candidates reach the scorer.
- Added `max_merged_candidates` (default 256) — the single cross-source budget, applied by `enforce_merged_budget` *after* flattening every source. It preserves the whole pool when under budget (the common case, so the scorer sees everything) and only truncates a pathological flood, then by `raw_score` as a last resort with survivors flagged `budget_exhausted`.
- `widen_budget` (working-memory retry) doubles the new field consistently.

This matches the fork plan `## 7` pipeline (steps 7–9: bounded expansion → score → compress): the cut belongs after scoring, not per source.

**Proof.** `candidates_tests.rs`: `merged_pool_spans_sources_beyond_a_single_source_cap` (merged pool carries both sources, exceeds a single per-source cap, nothing flagged exhausted when within budget) and `merged_pool_over_budget_truncates_and_flags_exhaustion` (a genuine over-budget pool truncates to the merged cap and flags survivors). RED-proven: with the merge cap removed, the over-budget test saw 21 candidates instead of the budgeted 5. All 65 `retrieval_v1` tests (incl. golden fixtures) and 36 `working_memory` tests green; full workspace green; fmt clean.

## T2 — equalize the bridge's inputs (and its line/memory output parity) for a valid Phase-2 comparison (shipped)

From the independent review: before Q2 Phase 2 can run a fixture comparison, the bridge had to stop handicapping the principled ranker. Three concrete defects were verified and fixed, each RED-first.

**(a) Blind ranker — inputs now fed.** The daemon call site (`rpc/mcp.rs::tool_query_context`) passed `query_embedding/memory_store/vector_index = None`, so flipping the flag ran v1 with no semantic candidates and no memory while the heuristic path embedded the query. Now, gated on the flag, the handler computes the query embedding (`embed_query_for_fallback`, outside the blocking job) and moves an `Arc<Mutex<MemoryStore>>` clone and the `SharedVectorIndex` into the job; the store is `blocking_lock`ed inside the closure (matching `run_query_job`'s `Send + 'static` bound) and all three are passed to the bridge. Test `embedding_and_vector_index_feed_the_ranker`: a semantic candidate appears in the capsule only when the embedding + vector index are supplied, absent otherwise — proof the ranker is no longer blind.

**(b) Hardcoded `line: 1` — now real.** `locate()` returned `1` for every result, so an anchor-precision fixture scored by `file:line` would mark every v1 result wrong on line even with a perfect file/symbol — a false-negative source stacked on the blind-ranker one. `locate` now takes the graph and looks up the real `GraphNode.line` (symbol and section arms, keyed by the legacy symbol id; file/doc fall back to 1 as the heuristic engine does). Test `capsule_carries_real_graph_line_numbers_not_a_constant`: a node at line 42 surfaces as line 42; RED-proven (hardcoded 1 failed against 42).

**(c) `memories: Vec::new()` — correctly left empty, for parity (not a bug after all).** The review flagged the bridge dropping the memory payload. Verified against the code: `QueryEngine::query` *always* sets `memories = Vec::new()` (engine.rs — "the daemon composes scoped, typed memories through MemoryStoreRouter"), and `tool_query_context` does **not** repopulate it afterward (unlike `tool_prepare_change`, which does). So for the context tool the heuristic path emits empty memories too. Populating `capsule.memories` in the bridge would make v1 *richer* than the heuristic path and bias the comparison the other way. The correct move for a valid comparison is parity: feed the memory store into the ranker's `RetrievalContext` (input parity — memory candidates can influence ranking/pivots) but leave `capsule.memories` empty (output parity). Done.

Default stays OFF (`LATTICE_RETRIEVAL_V1_FOR_CONTEXT`). Full workspace green; fmt clean; release build clean. With T1 (pre-scoring ceiling lifted) and T2 (inputs equalized) both done, the Phase-2 fixture comparison can now measure ranking quality rather than an artifact.

## Q2 Phase 2 — ranking-parity comparison (run; result below)

**OVER-CLAIM GUARD — READ FIRST.** This is a *fixture-level ranking-parity* measurement on identical inputs, **not** Beacon-scale real-world precision. It answers one narrow question — "on identical inputs, does v1 rank the expected code anchor at the top at least as well as the heuristic engine?" — and nothing about production quality. It must not be cited as proof the ranker is good in the field.

Harness: `crates/lattice-core/src/retrieval_v1/comparison_tests.rs`, over the hermetic golden fixture. Both engines receive clones of the **same** leaked graph, the **same** `Arc<dyn VectorIndex>` handle, and the **same** query embedding, so any divergence is ranking-only. Only code anchors (File/Symbol/Section) are scored — the heuristic engine structurally cannot emit Memory results — and Memory-expected cases are excluded and counted. The test asserts the scored denominator cleared a floor (≥ 8) for interpretability; it does **not** assert a direction.

### Result (as run)
```
scored=15  excluded_memory=4
v1_wins=12  heuristic_wins=0  ties_both_correct=0  ties_both_wrong=3
v1_produced_output=15/15   heuristic_produced_output=12/15
```

### The headline is the caveat, not the 12–0
Per-case, the heuristic engine matched the expected top anchor on **0 of 15** cases — including the 12 cases where it *did* produce a (non-empty, but wrong-topped) capsule. A 0/15 for one side is not a credible "the other side is better" result; it means **the golden fixture is home turf for `retrieval_v1`.** The fixture was authored around v1's anchor-resolution model (synthetic tasks with explicit path/symbol/error/command/api/config anchors), and the heuristic engine's keyword/centrality seeding does not top-rank the same node on these synthetic prompts. So:

- **What this result does support:** a *non-regression* conclusion. v1 never ranks *worse* than the heuristic engine on any fixture case (heuristic_wins = 0, and v1 answered every case). Converging the `context` tool onto v1 does not lose ranking quality on the fixture.
- **What it does NOT support:** a *superiority* conclusion. The 12–0 is inflated by the fixture being unfair to the heuristic engine, so it cannot be read as "v1 is 12× better." A genuine superiority/precision claim needs a fixture that is fair to **both** engines, or the Beacon paired-task evaluation (out of scope here).

### Default-flip decision
Do **not** flip the default on the strength of the win tally — that would be reading a home-turf artifact as a quality verdict, exactly the trap this phase was built to avoid. The honest basis for a flip is the combination of (1) **non-regression** shown here and (2) the **honesty argument**: v1 is the auditable, 13-signal, per-signal-diagnostic engine the design has always intended the agent tools to use. That is a legitimate "flip on the documented honesty + parity basis" (the tie branch of the three-outcome rule), **not** a "flip because v1 won."

The flag `LATTICE_RETRIEVAL_V1_FOR_CONTEXT` therefore **stays OFF in code**; the actual default flip is a separate, human-gated change. A reviewer who wants the flip to rest on measured superiority (not parity + honesty) should first build a both-engines-fair fixture or run Beacon — recorded here so that requirement is explicit, not skipped.

### Still open
- **A both-engines-fair comparison (optional, for a superiority claim):** the current fixture cannot support one; building a neutral fixture or running Beacon is the only way to claim v1 > heuristic rather than v1 ≥ heuristic.
- **Phase 3 perf (`run_blocking`):** `context_bridge::run_blocking` builds a fresh `current_thread` tokio runtime per query. Fine for correctness; for the hot path, reuse a runtime handle or make the candidate fan-out synchronous (the comment already notes the sources are "CPU/graph work wrapped in async"). Do not change behavior to fix this — it is a perf refinement.
- **T3 (cheap `impact` precision):** Q1 already attaches per-edge confidence (`EdgeConfidence`). The untaken step is to have `impact` rank by that confidence and optionally filter to resolved-only edges — converting the existing honesty signal into precision for far less than full scope/type resolution. Not yet wired into ranking.
