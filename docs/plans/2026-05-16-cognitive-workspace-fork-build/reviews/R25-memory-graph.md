## CounterMemory coverage

`CounterMemory` is implemented as a first-class memory class, not as an edge:

- **Class membership.** `memory_graph/classes.rs:44` enumerates `MemoryClass::CounterMemory`; `schema.sql:32` adds `'counter_memory'` to the CHECK list, so a CounterMemory row uses the same `memories` table, the same required-field surface, the same scope columns, and the same verification-status state machine as every other class.
- **Independent evidence and scope.** The `counter_memory_is_first_class_record_and_can_be_superseded_independently` test (`contradiction_tests.rs:55-136`) creates a `CounterMemory` with its own `MemoryClass::CounterMemory`, its own `AssertionType::Counter`, its own seed evidence (`memory_evidence("counter-seed")`), its own `branch` scope, and its own `Unverified` initial verification status. After creation, `harness.store.get(&counter.memory_id, &harness.branch_scope())` confirms `loaded_counter.class == MemoryClass::CounterMemory`, `loaded_counter.scope == counter.scope`, and `loaded_counter.verification_status == VerificationStatus::Unverified` — proving the counter is a row, not an edge, and that retrieval re-resolves it on its own merits (`memory-graph-schema.md ## CounterMemory Semantics`).
- **Independent lifecycle: supersession.** The same test then creates a `replacement` memory, inserts a `Supersedes` link from replacement → counter, writes the supersession transition, and asserts `transitioned.verification_status == VerificationStatus::Superseded` and `transitioned.superseded_by == Some(replacement.memory_id)`. The counter is itself superseded — separate from the supersession state of the prior claim it contradicts — which is exactly the lifecycle independence the spec calls for.
- **Independent lifecycle: invalidation without re-opening the target.** The `counter_memory_can_be_invalidated_without_reopening_its_target` test (`contradiction_tests.rs:139-191`) invalidates the counter via `store.delete(&counter.memory_id, …)`, then reloads both rows and asserts the counter is `Invalidated` while the original target stays `Contradicted`. The counter has its own tombstone row and event provenance; the target's lifecycle is unaffected.
- **Distinct from the `Contradicts` link.** The `contradiction_link_contradicts_target_and_emits_memory_updated_event` test (`contradiction_tests.rs:12-52`) demonstrates the link-only path: a non-CounterMemory contradicts a verified memory via a `MemoryLinkType::Contradicts` row, and the target transitions to `Contradicted`. The link is observably different — a `memory_links` row owned by the source memory — and shares the same target lifecycle but never carries its own scope, evidence, or verification status.
- **Stream classification.** `streams.rs:107-114` routes `CounterMemory` to its target's stream when known and to `SemanticRepoClaims` with a `warn!` log when the target stream is not available at classification time. The `test_classify_stream_mapping_is_exhaustive_over_memory_class` test (`scope_tests.rs:285-309`) covers every `MemoryClass` variant including `CounterMemory`, proving the classifier is total.
- **Replay survival.** The `event_log_replay_matches_original_memory_tables_byte_for_byte` test (`replay_tests.rs:15-26`) seeds the scenario via `seed_replay_scenario`, which creates a `CounterMemory` row, inserts the contradiction link, runs the contradiction transition, and finally invalidates the counter. The full event log replays into an empty database to a byte-for-byte fingerprint match — so the CounterMemory class travels through the snapshot payload, transition events, evidence rows, link rows, and tombstone path without loss.

The Phase 3 DoD line "memory can represent atomic notes, claims, workflow outcomes, procedures, preferences, and counter-memory" is satisfied for CounterMemory specifically, both structurally (it's a row) and behaviourally (it has independent verification status, evidence, scope, and a separate supersession/invalidation lifecycle).

## Verdict

**APPROVED WITH FOLLOW-UPS.**

Phase 3 satisfies every declared deliverable and definition-of-done line. All 41 `memory_graph::*` tests pass on the current tree. CounterMemory is a first-class class with independent evidence, scope, verification status, and supersession/invalidation lifecycle — proven by two dedicated tests and by full event-log replay. Deny-by-default scope enforcement is implemented at both the SQL CHECK level and the `ScopeFilter` API boundary, with negative tests for branch leakage, user leakage, org opt-in, scope-widening, and identity drift. The legacy migration importer is idempotent, dry-runnable, restartable, and emits a typed conflict error rather than overwriting. The verification-status state machine matches the schema doc table exactly and rejects disallowed transitions with a typed error.

The follow-ups (F-1 through F-7, all minor) are quality items that should be cleaned up before Phase 4 retrieval depends on this substrate at scale, particularly the missing `memories`-table indexes (F-3) — but none of them block the Phase 3 contract that R26 will gate.

R26 may proceed.
