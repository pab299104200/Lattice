# Cadres Coding Standard

Aspirational: do it right the first time. No shortcuts, no MVP, no stubs, no deferrals, no half-finished work. Enterprise grade on day one.

## Prime directive

Code is read 10× more than written. Optimize for the reader.

If you're tempted to leave a mess and "clean it up later," stop. Later doesn't come. The cost compounds with every reader who has to decode it.

---

## Hard limits

Ceilings, not targets. Cross them deliberately, with a one-line justification in the commit message.

| Unit | Max | When exceeded |
|---|---|---|
| File | 800 lines | Split along a coherent boundary (tabs, service modules, sub-routers, hooks). |
| Function | 50 lines | Extract helpers. If you can't name the helpers clearly, the function is doing too many things. |
| Nesting | 3 levels | Flatten with early returns, guard clauses, or extraction. No pyramid of doom. |
| Positional args | 5 | Group into a dataclass / TypedDict / Pydantic model. |
| Cyclomatic complexity | 10 per function | Same answer as above. |
| `useState` per component | 10 | Group into `useReducer` or custom hooks. |
| Test length | 30 lines | If setup is larger than the assertion, the abstraction is wrong — factor into fixtures or builder helpers. |

Numbers are heuristics: an 850-line file with 9 coherent sections is fine; a 400-line file doing 6 unrelated things is not. But cross a limit without a clear reason and you're making the codebase worse.

---

## Single source of truth

Every piece of knowledge lives in exactly one place.

- **Duplicate detection before writing.** Grep for the name, the signature, or a characteristic line of the logic. If it already exists, import it. If it almost exists, extend the existing helper — don't fork.
- **Copy-paste is a design smell.** When you catch yourself duplicating, stop and extract. If you extract mid-way through a task, migrate every caller in the same commit — partial migration is worse than none.
- **When three places duplicate, extract.** Two can be coincidence; three is a pattern.

## Error handling

Every failure path either recovers meaningfully or surfaces loudly.

**Banned**
- Silent `.catch(() => {})` or `.catch(e => console.error(e))` on user-initiated mutations
- Bare `except:` or catch-all `except Exception:` without a specific reason documented
- Ignoring a `Result` / `Optional` return without a one-line reason
- Generic error messages that hide the real cause ("Something went wrong")
- Swallowing validation errors and returning `200 OK` with an empty payload

**Required**
- Frontend mutations (POST/PUT/PATCH/DELETE): `catch (e) { toast.error(parseApiError(e)); }`. Reads may show an empty state, but never silently.
- Backend: structured `HTTPException` with accurate status codes and detail bodies. Pydantic validators for input shape. SCIM endpoints use the RFC 7644 error envelope.
- Validate at system boundaries (request/response, external APIs, DB rows parsed from JSON). Don't re-validate inside trusted code.
- Log with enough context to diagnose without reproducing (request id, user id, tenant id, and safe-to-log inputs).

## Naming

Clear names remove 80% of the need for comments.

- **Intent over mechanism.** `isAdmin` not `hasPermissionX`. `cancelRotation()` not `resetState()`.
- **Full words.** Abbreviations allowed only for a small set: `id`, `url`, `db`, `ctx`, `err`, `req`, `res`, `pk`.
- **Symmetry.** `create_user` pairs with `delete_user`, not `remove_user`. `load_*` pairs with `save_*`, not `persist_*`.
- **No generic containers.** `data`, `info`, `result`, `obj`, `stuff` — if you can't name it better, you haven't understood it yet.
- **Booleans read as questions.** `is_active`, `has_membership`, `can_manage`, `should_retry`.
- **Verbs lead handlers.** `handleRotateSecret`, `handleSubmit`, `handleChange`. Not noun-only (`rotation`, `submit`).
- **Types are nouns.** `UserProfile`, not `UserProfileManager` (there is no Manager; it's just the profile).

## Consistency over cleverness

- **Match the nearest neighbor.** Read an adjacent file before writing. If it has a pattern, follow it. If you think the pattern is wrong, change it globally — don't diverge locally.
- **One way to do X per codebase.** Two modal patterns is one too many. Two date renderers is one too many. Two pagination controls is one too many.
- **Boring is a feature.** A clever one-liner that takes 30 seconds to parse is worse than a boring 8-line loop.

## No broken windows

These are the accumulations that turn "works" into "messy" over time. Ban them at PR time, not "later."

- **No unjustified suppressions.** `# noqa`, `# type: ignore`, `eslint-disable`, `@ts-ignore`, `@ts-expect-error` — each requires an inline one-line comment explaining *why the rule is wrong here* (not *what the code does*) on the same line or immediately above. A bare suppression is an admission the rule is wrong or the code is; fix the actual problem instead. If the rule is genuinely wrong for the project, change the rule globally in the config — don't diverge per line.
- **For file-local structural exceptions, use per-file-ignores.** Some patterns are legitimate in one file only — `load_dotenv()` before env-reading imports, alembic path manipulation, `__init__.py` re-exports that must follow a base-class registration. Use `[lint.per-file-ignores]` in `ruff.toml` or ESLint config `files:` overrides with a comment saying *why this file is special*. This is neither a global rule change nor a per-line suppression; it's the right tool for structural ordering constraints. **Not** for individual violations — those still get fixed in code.
- **No `TODO` / `FIXME` / `XXX` in committed code.** Either fix it in this change or file an issue with a link.
- **No commented-out code.** Delete it; git remembers.
- **No dead imports, dead symbols, dead routes, dead feature flags.** Remove as part of the change that made them dead.
- **No `window.confirm / prompt / alert`.** Use `<dialog>`.
- **No duplicate logic surviving a refactor.** If you extract a helper, migrate every caller in the same commit.
- **No leftover scaffolding.** Test fixtures for features that didn't ship, commented placeholder imports, half-written classes — delete them.

## Schema / model parity

Public API schemas mirror persistence models unless intentional.

- Every non-private column on the model has a field in the relevant response schema, or an explicit reason to omit (e.g. `password_hash`).
- Field types in the schema mirror column nullability: `nullable=False` column → required schema field; `nullable=True` → `Optional`.
- If a schema field is derived (not backed by a column), document it in the field's docstring with a pointer to the serializer that computes it. Example: `SupportAccessResponse.tenant_access_grant_id` is derived — noted in its docstring.
- Update schema + migration + test together. Schema drift is a latent bug.

## Tests as documentation

- **One test per behavior**, named for the behavior: `test_delete_last_admin_returns_409`, not `test_delete_user_1`.
- Tests read like a spec. A new reader should learn what the code does from the test list alone.
- Integration tests prefer real collaborators (real DB, real Jinja renderer, real SAML XML). Mock only at the process boundary (outbound HTTP, SMTP). Don't mock within the domain.
- Test the public boundary, not the implementation. Refactors shouldn't break tests; behavior changes should.
- Every bug gets a regression test in the same commit.

## Observability

If it can't be debugged from logs and the audit trail without reproduction, it isn't finished.

- Every user-visible action emits a log line and, where appropriate, an audit record.
- Every error log includes request/user/tenant context.
- Every mutation crosses through the audit helper before `db.commit()` so the audit shares the business transaction.
- Webhook / email / external-service failures log at `warning` or `error` — never silently retry into the void.

## 1. Foundational Principles

These are the principles every UI decision should be measurable against. Each one is grounded in established UX research; the citation tells you *why* the rule exists so you can apply it correctly to cases this document doesn't enumerate.

1. **Design for scale.** Every list will eventually have thousands of items. Every form will eventually be filled by someone in a hurry. Every page will eventually be opened by someone who wasn't trained on it. Build for that reality from the first commit.

2. **Recognition over recall** *(Nielsen heuristic #6).* Operators never type numeric IDs, never recall slugs from memory, never reconstruct context they saw three screens ago. Every FK reference is a searchable dropdown that shows the human-readable name. Every selected filter stays visible. Every multi-step flow shows where you are.

3. **Match the user's mental model** *(Nielsen #2, Jakob's Law).* Use the words the operator uses, not the words the database uses. Follow the patterns established by the rest of the platform — and by the platforms our users come from (ServiceNow, Datadog, Okta) — instead of inventing local idioms. Familiar > clever.

4. **Limit choices at any moment** *(Hick's Law, Miller's Law).* Decision time grows with the number of options. Working memory holds 7±2 items. Group, chunk, and paginate so the operator never sees more than ~7 peers in a single visual region. Sidebar sections, form sections, dashboard cards, dropdown options — all bounded.

5. **Sub-400ms or show progress** *(Doherty Threshold).* Below ~400ms the interface feels instant and the user stays in flow. Past 400ms, show acknowledgement; past 1s, show progress; past 10s, allow cancel. See section 2.

6. **Consistent inputs and patterns** *(Nielsen #4, Jakob's Law).* All form controls behave identically. The same destructive-action confirm pattern appears everywhere a destructive action exists. The same empty state. The same error toast. Surprises waste cognitive load.

7. **Fail loudly, recover gracefully** *(Nielsen #1, #9).* Every API call handles loading, empty, and error states independently. Errors are stated in plain language, point at the offending input, and suggest the fix. Silent failures are never acceptable. See section 8.

8. **Permission-aware UI** *(Nielsen #5 — Error Prevention).* Actions the user can't perform are hidden or disabled with explanation, never shown-and-then-403'd. The UI is always in agreement with the backend's RBAC. See section 9.

9. **Accessible by default** *(WCAG 2.2 Level AA).* Keyboard navigable, screen-reader compatible, sufficient contrast, visible focus, respects `prefers-reduced-motion`. Accessibility is not an audit item we do at the end — it's built in. See section 3.

10. **Accept some irreducible complexity** *(Tesler's Law).* Every system has a minimum complexity it cannot drop below. The question is who carries it. Carry it on the system's side wherever possible (sensible defaults, server-computed fields, autofilled context) so the user doesn't have to.

11. **Be liberal in what you accept, strict in what you produce** *(Postel's Law).* Trim whitespace, normalize emails to lowercase, accept dates in any reasonable format. But emit ISO-8601 to APIs, store integer cents, and never round-trip user-typed garbage back into shared state.

12. **Plumbing over per-site refactor.** When a rule touches >5 sites and can be enforced by a single CSS rule, a wrapper component, or a shared hook, fix it that way rather than editing every call site. Global CSS (prefers-reduced-motion, touch-target minimums, modal-action sticky-on-phone), a canonical component (see §7.1 `ResponsiveModal`), or a shared hook (see §3.3 `useModalFocus`) are the preferred enforcement surfaces. Per-site refactors are a last resort — they're slow to review, easy to miss sites, and drift the moment someone copy-pastes the old pattern. If you're about to touch 50 files with the same change, stop and find the plumbing fix.

## 2. Response Time & Perceived Performance

Per the Doherty Threshold, the interface should answer fast enough that the user stays in flow. The thresholds below are budgets, not aspirations — anything beyond a budget needs explicit feedback so the user knows the system hasn't hung.

| Latency budget | What the UI must do | Examples |
|---|---|---|
| **0–100 ms** | Feels instant — no feedback needed | Hover, button press visual change, dropdown open, in-page tab switch |
| **100–400 ms** | Still feels responsive — no spinner needed; data should just appear | Cached list re-render, filter change, pagination of in-memory data |
| **400 ms – 1 s** | User starts noticing — show acknowledgement (button enters loading state, toast appears, optimistic UI applied) | Most form submits, most API mutations |
| **1–4 s** | User starts wondering — show a spinner or skeleton in the affected region; keep the rest of the page interactive | Loading a large table, fetching a detail view, generating a small report |
| **4–10 s** | User considers giving up — show **explicit progress** (percent, step counter, "Loading X of Y…"); disable competing actions | Bulk operations on dozens of items, complex aggregation queries |
| **> 10 s** | User WILL leave or refresh — show progress AND a Cancel button; offer to email/notify when done | Long-running reports, exports, mass imports |

### 2.1 Skeletons vs spinners

| Choice | When to use |
|---|---|
| **Skeleton loader** (gray placeholder boxes matching the eventual layout) | First-load of a predictable layout — table rows, card grids, detail-view fields. The skeleton tells the user *what is about to appear*, which keeps them oriented. |
| **Spinner / progress bar** | Indeterminate work where the layout cannot be predicted — modal opening with dynamic content, action confirmation, file upload, server-side computation. |
| **Inline button spinner** | Form submit / single-action button — the spinner replaces the button label so the affordance stays in place. |
| **Nothing / instant** | Anything under 400 ms. Never blink a spinner for 80 ms — it's worse than no feedback. |

### 2.2 Optimistic UI

For low-risk mutations where the success rate is >99% and rollback is clean, apply the change to the UI immediately and reconcile when the API responds. Examples: toggling a switch, marking notifications read, reordering items.

For destructive or rare-success operations, do NOT use optimistic UI. Show the action in flight, wait for the server, then reflect the result.

When optimistic UI is wrong, roll back the visible change and surface the error via toast with the same `parseApiError()` text the explicit path would use.

## 3. Accessibility Baseline (WCAG 2.2 Level AA)

Every Cadres surface conforms to **WCAG 2.2 Level AA**. The requirements below are the ones we ship against — not the entire WCAG catalog, but the slice that gets violated most often in admin tooling.

### 3.1 Color & Contrast

- **Normal text contrast: ≥ 4.5:1** (WCAG 1.4.3). Test every text/background pair with a contrast checker. DaisyUI's default themes pass; custom overrides do not get a free ride.
- **Large text (≥ 18pt or ≥ 14pt bold) contrast: ≥ 3:1**.
- **Non-text contrast: ≥ 3:1** (WCAG 1.4.11) for icons, focus rings, form-field borders, status indicators against their adjacent surface.
- **Never carry meaning on color alone** (WCAG 1.4.1). Status badges pair color with a text label or icon. Form errors pair red with an icon and an error message. Required fields pair the asterisk with the word "Required" or `aria-required="true"`.

### 3.2 Keyboard

- **Every interactive element is reachable and operable via keyboard** (WCAG 2.1.1). No mouse-only widgets. No drag-only interactions — provide a non-drag alternative (WCAG 2.5.7).
- **Tab order matches visual order.** Don't use positive `tabindex` values; rely on DOM order.
- **`Esc` closes any open modal, drawer, dropdown, or popover** without saving.
- **`Enter` submits the focused form** if a single primary action exists.
- **A "Skip to main content" link** is the first focusable element on every page; visible on focus.
- **No keyboard traps.** A user can always Tab out of any region.

### 3.3 Focus Management

- **Visible focus indicator on every interactive element** (WCAG 2.4.7) — minimum 2px outline at ≥ 3:1 contrast against both the element and the adjacent surface. Never `outline: none` without a replacement. The one acceptable exception is a non-interactive `tabIndex={-1}` skip-link target (e.g., a `<main>` region focused only by a skip-to-main anchor) — there's no control there to indicate focus on.
- **Focus moves predictably on dynamic events:**
  - Modal opens → focus moves to the first focusable descendant of the modal (input, select, textarea, button, link — in DOM order). If there are none, the modal container itself gets focus so Tab still lands inside the trap.
  - Modal closes → focus returns to whatever was focused right before the modal opened (almost always the trigger button).
  - Route changes → focus moves to the page's main `<h1>` (or to a `<main role="main">`).
  - Drawer opens → same pattern as modal.
- **Canonical implementation: `hooks/useModalFocus.ts`** (per §1 Principle 12 — plumbing over per-site). The hook takes a `React.RefObject<HTMLElement>`, reads `document.activeElement` on mount as the trigger, moves focus to the first focusable descendant, traps Tab/Shift+Tab so focus wraps first↔last, and restores focus to the trigger on unmount. Callers do not thread a `triggerRef` through props — `document.activeElement` at mount time is the source of truth. The `ResponsiveModal` component wires this hook, so any modal built on ResponsiveModal inherits focus management for free.
- **Focus is never obscured** (WCAG 2.4.11) by sticky headers, footers, or chat widgets. If a sticky header could overlap focus, scroll it out of the way.
- **Confirm-style modals.** For destructive confirm dialogs with only Cancel and a dangerous primary, "first focusable" lands on Cancel (the safer option). That is the intended behavior, not a bug.

### 3.4 Target Size

- **Desktop minimum: ≥ 24×24 CSS pixels** (WCAG 2.5.8 AA) OR have ≥ 24px center-to-center spacing from any other target. DaisyUI `btn-sm` is borderline — pair small icon buttons with adequate spacing or use `btn-sm` with explicit padding.
- **Touch minimum (phone / tablet): ≥ 44×44 CSS pixels** (Apple HIG, WCAG 2.5.5 AAA). See section 13.4 for how this interacts with our breakpoints — compact density and `btn-sm` icon buttons are desktop-only.
- Inline icon-only actions in tables get ≥ 8px gap between them, regardless of device.

### 3.5 Forms

- **Every input has a programmatic label** (WCAG 1.3.1, 3.3.2). Use `<label for="…">` or wrap `<input>` inside `<label>`. Never use `placeholder` as the label.
- **Required fields are programmatically marked** with `aria-required="true"`. Visual marking depends on form shape:
  - **Mixed forms** (some required, some optional): each required field gets a visible marker (asterisk in the label, plus "Required" in the `label-alt` slot for SR parity). Never mark optional fields — marking everything marks nothing.
  - **All-required forms** (auth: sign-in, password reset, MFA; any form where every field is required): do NOT mark fields individually. State it once at the form level — either "All fields required" near the form header or the implicit convention for auth surfaces — and keep individual labels clean. Per-field asterisks in an all-required form are visual noise that degrades scannability without informing anyone. `aria-required="true"` is still set on the inputs for SR.
- **Errors are identified programmatically** (WCAG 3.3.1) via `aria-invalid="true"` and `aria-describedby` pointing at the error text. The error text is in plain language and suggests a fix (see section 8.6).
- **Don't make the user re-enter data they already gave you in the same flow** (WCAG 3.3.7). If a tenant_id is already in the URL or session, prefill it.
- **Don't require typing/transcribing/cognitive tests in auth** (WCAG 3.3.8). Provide a paste-friendly TOTP field; allow password managers; use copy buttons next to one-time secrets.

### 3.6 Live Regions & Status Messages

- **Toast notifications use an ARIA live region** (WCAG 4.1.3). Two equivalent implementations — pick one per component and stay consistent:
  - **ARIA roles (preferred on per-toast elements).** `role="alert"` on error toasts (implies `aria-live="assertive"` + `aria-atomic="true"`). `role="status"` on info / success / warning (implies `aria-live="polite"`). Screen readers announce role-bearing nodes when they mutate into the DOM, which is the behavior we want for toasts that appear one at a time.
  - **Explicit `aria-live` on the container.** When a container holds a stream of status messages and you want SR to batch them, put `aria-live="polite"` (or `assertive`) on the container and let children be plain `<div>`s. Use this shape for a transcript or activity log.
  - In doubt, use both on the toast component (container `aria-live="polite"` + per-toast `role="alert"`/`role="status"`) — browsers that honor one or the other will still announce correctly.
- **Loading states announce themselves** to assistive tech: `aria-busy="true"` on the region while loading, removed when the data arrives.
- **Dynamic counts and result totals** — when a filter changes the result count, announce the new count (e.g., `aria-live="polite"` on the "Showing X of Y" element).

### 3.7 Motion & Animation

- **Respect `prefers-reduced-motion`** (WCAG 2.3.3 AAA, but we treat it as table stakes). Use the **opt-out** plumbing pattern — one global rule in `index.css` that neutralizes animation and transition on every element when the user opts out:

  ```css
  @media (prefers-reduced-motion: reduce) {
    *,
    *::before,
    *::after {
      animation-duration: 0.01ms !important;
      animation-iteration-count: 1 !important;
      transition-duration: 0.01ms !important;
      scroll-behavior: auto !important;
    }
  }
  ```

  This covers animation we own **and** animation injected by DaisyUI, Tailwind, and third-party components we don't control. The opt-in alternative (`@media (prefers-reduced-motion: no-preference) { ... }` around each transition) is a per-site refactor that violates §1 Principle 12 and misses library animations entirely.

- No flashing content faster than 3 Hz (WCAG 2.3.1).

### 3.8 Screen Reader Patterns

- Decorative icons have `aria-hidden="true"` and are paired with text. Functional icon buttons have `aria-label="…"`.
- Tables use `<th scope="col">` / `<th scope="row">` so screen readers read column/row context with each cell.
- Modal dialogs use `<dialog>` (which gives us focus trap + Esc + backdrop for free) OR `role="dialog" aria-modal="true" aria-labelledby="…"` if a `<dialog>` won't work.

## 5. Form Inputs

### 5.1 Numeric Inputs — No Spinners

All numeric inputs MUST hide browser-default up/down spinner buttons. Apply globally via CSS:

```css
/* Hide number input spinners globally */
input[type="number"]::-webkit-inner-spin-button,
input[type="number"]::-webkit-outer-spin-button {
  -webkit-appearance: none;
  margin: 0;
}
input[type="number"] {
  -moz-appearance: textfield;
}
```

Add this to the global stylesheet (`index.css` or equivalent). Do NOT rely on per-component overrides.

**When to use `type="number"`:** Only for values where keyboard numeric entry is natural (port numbers, thresholds, counts, timeouts). For IDs, use a select/dropdown instead.

### 5.2 ID Reference Fields — Searchable Dropdowns (MANDATORY, NO EXCEPTIONS)

**ANY form field that accepts an ID, foreign key, or reference to another entity MUST be converted to a searchable dropdown that shows human-readable names.** This is a hard requirement — not a suggestion. If a field name ends in `_id` or references another record, it MUST be a dropdown. No text inputs, no number inputs, no "enter the ID" fields. Ever.

**Detection rule:** If you see `<input type="number">` or `<input type="text">` where the value will be stored as a foreign key or used to look up another record, it is a violation. Convert it to a dropdown immediately.

**Every ID reference dropdown must:**

- Fetch options from the relevant API endpoint on mount or on modal open
- Display the human-readable name as the primary label
- Show secondary context (type, count, status, IP address, etc.) to help the user choose
- Store/submit the numeric ID internally — the user never sees or types the ID
- Support type-ahead search/filtering for lists > 10 items
- Show a loading spinner while fetching options
- Show "No results found" when search/filter returns empty
- Show a clear/reset button for optional fields
- Handle the case where the referenced record was deleted (show "Unknown (ID: N)" fallback)

**Common ID fields and what to show:**

| `script_id` | Number input | Script name + language |

### 5.3 Slug And Machine-Readable Reference Fields (MANDATORY DEFAULT)

**Any field that stores a slug, handle, path segment, key, or other machine-readable reference derived from the record's friendly name MUST auto-generate from that friendly name by default.** Operators should not have to invent slugs manually when the system can derive them deterministically.

**Source field:** Use the primary human-readable naming field for the record. Depending on the product, this may be labeled `Display name`, `Name`, `Title`, or `Label`.

**Default transformation rules:**

- Trim leading and trailing whitespace
- Convert to lowercase
- Replace spaces and other visible separators with a single dash (`-`)
- Collapse repeated dashes into one
- Remove leading and trailing dashes

**Canonical example:** If the operator enters `Workday Production` as the friendly name, the slug auto-generates as `workday-production`.

**Required UX behavior:**

- Populate the slug automatically as soon as the friendly name has a value
- Keep the slug synchronized with the friendly name until the operator manually edits the slug field
- If manual override is allowed, stop auto-sync after the first manual slug edit and provide a clear `Regenerate` action
- If manual override is not part of the product contract, render the slug as read-only or hide the editable slug control entirely
- Show helper text when useful so the operator understands that the slug is the machine-readable form of the friendly name
- Validate uniqueness, reserved words, and server-side normalization conflicts in the backend; surface failures inline in the form

**Do not:**

- Ask the operator to type both a friendly name and a matching slug when the slug can be derived automatically
- Leave slug formatting to operator guesswork
- Allow UI-only normalization that the backend does not also enforce

### 5.6 Currency Input Fields (MANDATORY, NO EXCEPTIONS)

**ANY field that represents money MUST use a dedicated `CurrencyInput` component.** Never use `<input type="number">` or `<input type="text">` for currency. This applies to ALL monetary values: prices, totals, tax amounts, payments, budgets, billing amounts, refunds, credits, fees.

#### Behavior — Auto-Formatting Cents Input

The currency input works like a calculator/POS register: the user types digits and the last two digits are always cents. No decimal point entry needed. The display auto-formats as the user types.

**How it works:**

| User types | Raw digits | Display shows | Stored value (cents) |
|-----------|-----------|---------------|---------------------|
| `1` | 1 | $0.01 | 1 |
| `10` | 10 | $0.10 | 10 |
| `100` | 100 | $1.00 | 100 |
| `1500` | 1500 | $15.00 | 1500 |
| `10000` | 10000 | $100.00 | 10000 |
| `999999` | 999999 | $9,999.99 | 999999 |

**Input rules:**
- Only numeric digits (0-9) are accepted — reject all other characters on keypress
- No decimal point entry — the decimal is always auto-placed before the last 2 digits
- Backspace removes the last digit
- Leading zeros are stripped from the display (but "0" alone shows as $0.00)
- Thousands separator (comma) displayed but not stored
- Always shows exactly 2 decimal places
- Dollar sign ($) prefix displayed in the input (or as an input-group addon)
- Negative values: prefix with minus sign if the field allows negatives (e.g., credits, adjustments)

**Storage and API contract:**
- **Frontend stores and submits: integer cents** (e.g., 1500 for $15.00)
- **Backend stores: integer cents** in the database column
- **Display to user: formatted dollars** with $ prefix, comma thousands, 2 decimal places
- Conversion: `displayValue = (cents / 100).toLocaleString('en-US', { style: 'currency', currency: 'USD' })`

**IRS rounding rules:**
- All currency calculations MUST round to the nearest cent using **banker's rounding** (round half to even): `Math.round(value * 100) / 100`
- Tax calculations: compute in cents, round once at the final step — do NOT round intermediate calculations
- Totals: sum the cent values, then format for display — do NOT sum formatted dollar strings

**Implementation pattern:**
```tsx
// CurrencyInput component
interface CurrencyInputProps {
  label: string;
  value: number;           // cents (integer)
  onChange: (cents: number) => void;
  required?: boolean;
  disabled?: boolean;
  allowNegative?: boolean;
  max?: number;            // max cents
}

function CurrencyInput({ label, value, onChange, required, disabled, allowNegative, max }: CurrencyInputProps) {
  const displayValue = (value / 100).toLocaleString('en-US', {
    minimumFractionDigits: 2,
    maximumFractionDigits: 2,
  });

  const handleKeyDown = (e: React.KeyboardEvent<HTMLInputElement>) => {
    // Allow: backspace, delete, tab, escape, enter
    if ([8, 9, 13, 27, 46].includes(e.keyCode)) {
      if (e.key === 'Backspace') {
        e.preventDefault();
        onChange(Math.floor(value / 10));
      }
      return;
    }
    // Allow minus for negative fields
    if (allowNegative && e.key === '-') {
      e.preventDefault();
      onChange(-value);
      return;
    }
    // Block non-numeric
    if (e.key < '0' || e.key > '9') {
      e.preventDefault();
      return;
    }
    // Append digit
    e.preventDefault();
    const newValue = value * 10 + parseInt(e.key);
    if (max && newValue > max) return;
    onChange(newValue);
  };

  return (
    <div className="form-control w-full">
      <label className="label">
        <span className="label-text">{label}</span>
        {required && <span className="label-text-alt text-error">Required</span>}
      </label>
      <label className="input input-bordered flex items-center gap-2">
        <span className="text-base-content/60">$</span>
        <input
          type="text"
          inputMode="numeric"
          className="grow text-right font-mono"
          value={displayValue}
          onKeyDown={handleKeyDown}
          readOnly={disabled}
        />
      </label>
    </div>
  );
}

// Usage:
<CurrencyInput
  label="Unit Price"
  value={form.unit_price_cents}
  onChange={(cents) => setForm({ ...form, unit_price_cents: cents })}
  required
/>
```

**Where to apply:** Every field in the system that stores money. This includes but is not limited to:
- Bills & AP: line item amounts, tax, totals, payments
- Invoices & AR: line items, totals, payments received
- Budgets: monthly allocation amounts
- Subscription plans: monthly/annual pricing
- Tax estimates: estimated amounts, payments
- Journal entries: debit/credit amounts
- Service catalog: any pricing fields
- Obligations: payment amounts

**Display (read-only contexts):**
```tsx
// For displaying currency in tables, cards, detail views:
const formatCurrency = (cents: number) =>
  new Intl.NumberFormat('en-US', { style: 'currency', currency: 'USD' }).format(cents / 100);
```



- Client-side validation for obvious issues (required, min/max length, format)
- Server-side validation errors displayed inline below the field
- Submit button disabled while form is submitting (prevent double-submit)
- Toast notification on success/failure after submission

## 7. Modals & Dialogs

### 7.1 Standard Modal — use `ResponsiveModal`

**Every modal in every Cadres product is built with the `ResponsiveModal` wrapper** (`components/common/ResponsiveModal.tsx`). Raw DaisyUI `<dialog className="modal modal-open">` usage is forbidden — the wrapper owns responsive sizing (§13.6), focus management (§3.3), Esc handling, backdrop click-to-close, and ARIA role wiring, and centralizing those concerns is the only way they stay correct as the codebase grows.

```tsx
import ResponsiveModal from 'components/common/ResponsiveModal';

{showEditor && (
  <ResponsiveModal onClose={() => setShowEditor(false)} maxWidth="lg">
    <h3 className="font-bold text-lg">Edit user</h3>
    <div className="py-4">{/* body */}</div>
    <div className="modal-action">
      <button className="btn" onClick={() => setShowEditor(false)}>Cancel</button>
      <button className="btn btn-primary" onClick={onSubmit} disabled={saving}>
        {saving ? <span className="loading loading-spinner loading-sm" /> : 'Save'}
      </button>
    </div>
  </ResponsiveModal>
)}
```

**API:**

| Prop | Required | Notes |
|---|---|---|
| `onClose` | yes | Called on backdrop click, Esc, and the wrapper's internal close paths. |
| `maxWidth` | no | `sm` / `md` (default) / `lg` / `xl` / `2xl` / `3xl` / `4xl` — applied at `md:` and above only; below `md:` the modal occupies the full viewport per §13.6. |
| `labelledBy` | no | `aria-labelledby` hook for when the heading id needs to be explicit. |
| `className` | no | Extra classes on the `.modal-box` for rare one-off cases. |

**Mount pattern:** wrap with `{state && <ResponsiveModal ...>}`. Don't render ResponsiveModal always-on and toggle classes — conditional mounting is what gives focus-return and body-reset-on-reopen for free.

**Banned modal patterns:**

- `<dialog ref={dialogRef} className="modal">` + `ref.current.showModal()` / `.close()` (imperative native `<dialog>` API). It bypasses ResponsiveModal's focus trap, sizing, and Esc wiring, and it makes the "is this modal open" state invisible to React. If the `ResponsiveModal` API doesn't cover your use case, extend it — don't bypass it.
- `<div className="modal modal-open">` — a `<div>` doesn't provide the native `<dialog>` affordances ResponsiveModal depends on.
- `<dialog className={\`modal ${cond ? 'modal-open' : ''}\`}>` — always-mounted dialog with class-toggled visibility. Use `{cond && <ResponsiveModal>}` instead.
- `window.confirm` / `window.prompt` / `window.alert` — native browser dialogs (§7.2). The standards gate enforces this.

**Legacy patterns in existing code**, if any, are hot spots — when you're already touching a file with a raw `<dialog>` pattern, convert it to ResponsiveModal in the same change rather than adding to it.

### 7.2 Confirmation Dialogs

Destructive actions (delete, cancel, revoke) MUST show a confirmation dialog:
- Red/warning styling
- Clear description of what will be deleted/cancelled
- Type-to-confirm for high-impact actions (e.g., type resource name)
- Cancel + Confirm buttons (Confirm in red/warning color)

## 8. State Management

### 8.1 API Error Handling

**NEVER use `Promise.all()` for independent API calls.** One failure kills all results.

```tsx
// WRONG — one fails, all fail
const [groups, policies] = await Promise.all([
  api.getAssignmentGroups(),
  api.getEscalationPolicies()
]);

// CORRECT — independent error handling
let groups = [], policies = [];
try { groups = await api.getAssignmentGroups(); } catch (e) { console.error(e); }
try { policies = await api.getEscalationPolicies(); } catch (e) { console.error(e); }
```

### 8.2 Loading States

- Initial page load: skeleton loader or centered spinner
- Table reload (filter/page change): subtle overlay spinner, keep existing data visible
- Form submit: disable submit button, show inline spinner
- Never show a blank page during loading

### 8.3 Empty States

- Centered icon + message + optional CTA button
- Different messages for "no data yet" vs "no results matching filter"
- Example: "No assignment groups configured. Create one to start routing incidents."

### 8.4 Toast Notifications

All user-triggered mutations show feedback:
```tsx
const { toast } = useToast();

try {
  await api.createAssignmentGroup(data);
  toast.success('Assignment group created');
  onClose();
  refresh();
} catch (err) {
  toast.error(parseApiError(err));
}
```

### 8.4.1 Plan Limit Errors (HTTP 429)

HTTP 429 responses from plan-based resource limits should be displayed as a clear toast message:

```
"You've reached the maximum [resource] for your plan. Upgrade to add more."
```

Where `[resource]` is "hosts", "scripts", "workflows", or "storage". If the response body includes `limit` and `current` fields, include them: `"You've reached the maximum scripts for your plan (50/50). Upgrade to add more."`

Optionally include an upgrade link/button that navigates to the subscription management page.

### 8.5 Error Display on API Failure (MANDATORY)

Every API call that mutates data (POST/PUT/PATCH/DELETE) MUST display an error to the user on failure. Silent failures are never acceptable.

**Rules:**
1. Every mutation API call must have a `catch` block that shows a `toast.error()` with a meaningful message
2. Pydantic validation errors (`422` with `detail` array) must be parsed into human-readable field-level messages
3. Never show a blank screen, spinner-forever, or swallowed error on API failure
4. For form submissions: display field-level errors inline below the relevant fields when possible
5. For non-form mutations: show a toast with the error detail

**Standard error parsing helper** (`src/utils/errors.ts`):
```typescript
import { parseApiError } from '../../utils/errors';

// In catch blocks:
catch (error: any) {
  toast.error(parseApiError(error));
}
```

`parseApiError()` handles all three error shapes:
- Pydantic 422 arrays: `[{loc: ["body", "field"], msg: "..."}]` -> `"field: msg, field2: msg2"`
- FastAPI string detail: `{detail: "message"}` -> `"message"`
- Generic errors: `error.message` -> fallback string

**Anti-patterns (NEVER do these):**
```tsx
// WRONG — swallows error, user sees nothing
catch (e) { console.error(e); }

// WRONG — shows "[object Object]" for Pydantic 422 errors
toast.error(error.response?.data?.detail || 'Failed');

// WRONG — no catch at all, unhandled promise rejection
await api.createThing(data);
```

### 8.6 Error Message Style (Nielsen #9)

Errors are written to be acted on, not just acknowledged. Every user-facing error obeys the rules below.

| Rule | Bad | Good |
|---|---|---|
| Plain language, no codes | `ERR_4021: validation_failed` | `Email is already in use. Try signing in or use a different address.` |
| State the problem AND suggest the fix | `Invalid input.` | `Password must be at least 12 characters. Add 4 more.` |
| Be specific | `Something went wrong.` | `Could not reach the directory service. Retry in a few seconds.` |
| Place at the source | Single banner at the top of a long form | Inline error directly under the offending field |
| Tone matches who's at fault | "You broke this." | "We can't load this right now — retry?" for system errors; clear-but-not-shaming for user errors |
| Never blame the user | `Wrong format.` | `Use YYYY-MM-DD (e.g., 2026-04-14).` |
| Don't dead-end the user | `Failed.` | `Failed. <a>Reset to defaults</a> or <a>contact support</a>.` |

### 8.7 Success & Confirmation Messages

Successful mutations get a brief toast that confirms what happened, in the past tense:

- "User created." (not "Creating user…" — that was the in-flight state)
- "Webhook deleted."
- "3 users deactivated."

For high-stakes actions where the user might want to undo: include an Undo action in the toast (see 8.8) for ~5 seconds.

For low-stakes mutations where the screen visibly updates (table reload, badge change, switch flip), the screen update IS the confirmation — a toast becomes noise. Skip it.

### 8.8 Undo & Optimistic UI

Undo is the antidote to confirm dialogs. Confirm interrupts every action; undo only catches the rare mistake.

**Use undo (no confirm) for:**
- Reversible actions (archive, mark-complete, mark-read, reorder, snooze).
- Low-stakes single-row deletes where the row can be restored.
- Toggle switches.

**Use confirm (no undo) for:**
- Truly destructive, irreversible actions (delete tenant, delete user with audit history, revoke a service credential) — section 7.2 enforces the confirm-dialog pattern for these.
- Actions with side effects beyond the current screen (sending email, triggering a deploy, charging a card).
- Bulk destructive actions where the impact count is large.

**Pattern:**

```tsx
// Optimistic + undo
const original = items;
setItems(items.filter(i => i.id !== item.id));            // optimistic remove
const result = await toast.actionable(
  `${item.name} archived.`,
  { action: 'Undo', timeoutMs: 5000 }
);
if (result === 'undo') {
  setItems(original);                                      // local rollback
} else {
  await api.archive(item.id).catch((e) => {
    setItems(original);
    toast.error(parseApiError(e));
  });
}
```

### 8.9 Bulk Action Patterns

Tables with selection always follow this pattern:

- **Selection column** is the first column, leftmost. Header checkbox toggles "select all on this page" (NOT all rows in the database — clarify with copy if total > page size).
- **Selected count** appears in a sticky toolbar above the table when ≥ 1 row is selected: `3 selected · [Bulk action ▾] · [Clear selection]`.
- **Action menu** lists only actions the user has permission for (per section 9). Unavailable actions are absent, not greyed.
- **Confirmation dialog for destructive bulk** includes the count: "Delete 47 users? This cannot be undone. Type DELETE to confirm." Type-to-confirm is required when count > 10.
- **Progress for bulk operations** that take > 1 s shows X of Y processed (per section 2). Failures within a batch are reported in a per-row results list at the end.

### 8.10 Auto-save vs Explicit Save

| Use auto-save when… | Use explicit save when… |
|---|---|
| Each change is independently meaningful (settings toggles, profile fields) | Multiple changes form a single transaction (multi-step form, complex object edit) |
| The user is unlikely to want to discard | Discard is a real possibility (user is exploring options) |
| Latency budget allows debouncing (1–2 s after last keystroke) | The change has visible side effects the user wants to time |

Auto-save UIs show a subtle "Saved" indicator + last-saved timestamp. A failure to auto-save MUST surface as a toast — never silently retain unsaved local state.

## 10. Navigation & Page Architecture

### 10.1 Sidebar — Task-Oriented Sections

The sidebar groups items by what the operator is trying to DO, not by which subsystem
the code lives in. Sections have a short uppercase label and contain 2-5 items each.

```
━━━ OPERATE ━━━━━━━━━    (triage, respond)
━━━ MANAGE ━━━━━━━━━━    (hosts, patching, backup)
━━━ DISCOVER ━━━━━━━━    (network, AD, infra, M365)
━━━ SECURE ━━━━━━━━━━    (vulns, compliance, PAM, certs)
━━━ AUTOMATE ━━━━━━━━    (scripts, workflows, marketplace)
━━━ CONFIGURE ━━━━━━━    (alert rules, on-call, settings)
━━━ COMMUNITY ━━━━━━━    (feature requests)
```

**Rules:**
- Max 20 sidebar items total (across all sections). If you're adding item 21, something else must merge or move.
- Each feature gets ONE sidebar entry. If the same data is viewable from two pages, one is a redirect, not a second nav item.
- Don't create a sidebar item for a feature that's a tab inside another page.

### 10.2 Feature Page Pattern — Tabs + Configure Drawer

Complex features use a standard three-layer architecture:

```
┌─────────────────────────────────────────────────┐
│  Feature Page                    [Configure ⚙]  │  ← Page header with Configure button
│                                                   │
│  ┌─────────┬──────────┬────────┬─────────┐      │
│  │ Tab A   │  Tab B   │ Tab C  │  Tab D  │      │  ← Top-level tabs (views of the data)
│  └─────────┴──────────┴────────┴─────────┘      │
│                                                   │
│  ┌───────────────────────────────────────────┐   │
│  │  Tab content area                          │   │  ← Each tab is a self-contained component
│  │  (list, detail, dashboard, etc.)           │   │
│  │                                             │   │
│  └───────────────────────────────────────────┘   │
│                                                   │
│  ┌─ Configure Drawer (slides in from right) ──┐  │
│  │  ┌────────┬──────────┬───────────┐         │  │
│  │  │ Cfg A  │  Cfg B   │  Cfg C    │         │  │  ← Config tabs (settings for THIS feature)
│  │  └────────┴──────────┴───────────┘         │  │
│  │  [config form / CRUD table]                 │  │
│  └─────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

**Layer 1 — Top tabs** show different VIEWS of the feature's data. These are URL-driven
(`/incidents?view=service`, `/incidents?view=events`, `/incidents?view=sla`). Each tab
renders a self-contained component. The operator switches between views without leaving
the feature.

**Layer 2 — Sub-tabs** (optional) subdivide a top tab into related domains.
Example: Incidents → Service Mgmt has sub-tabs for Incidents, Problems, Changes, Catalog, KB.
These are also URL-driven (`/incidents?tab=problems`).

**Layer 3 — Configure drawer** provides settings that are SPECIFIC to this feature.
It slides in from the right, overlaying the content. The operator makes a config change,
closes the drawer, and sees the effect immediately.

**The critical rule: the configure drawer ONLY contains config specific to its feature.**
Shared infrastructure (alert rules, notification channels, escalation policies) belongs in
its own dedicated page (`/alerting`), not duplicated into every feature's config drawer.

| Config item | Where it belongs | Why |
|-------------|-----------------|-----|
| SLA Policies | Incidents configure drawer | Only used by ITSM |
| Assignment Groups | Incidents configure drawer | Only used by ITSM |
| Change Governance | Incidents configure drawer | Only used by ITSM |
| Change Freeze | Incidents configure drawer | Only used by ITSM |
| Alert Rules | Alert Rules page (`/alerting`) | Used by alerting, monitoring, incidents — shared |
| Notification Channels | Alert Rules page (`/alerting`) | Used by alerts, SLA, escalation — shared |
| Escalation Policies | Alert Rules page (`/alerting`) | Used by alerts, incidents — shared |

**Anti-pattern: "one-stop-shop" drawers.** Don't put shared config into a feature drawer
just because it feels convenient. This creates duplication (same UI in two places),
confuses operators ("which one is authoritative?"), and increases maintenance burden.
If an operator needs alert rules while working on incidents, they navigate to `/alerting` —
that's one click, not a burden.

### 10.3 Dedicated Config Pages

Some features are entirely configuration — they don't have operational data to view,
they just set up rules/policies. These get their own sidebar entry and use tabs:

```
Alert Rules (/alerting)
  ├── Routing Rules       (notification routing)
  ├── Channels            (email, slack, webhook targets)
  ├── Event Sources       (event source registry)
  ├── Escalation Policies (multi-stage escalation)
  ├── Alert Rules         (metric threshold rules)
  └── Snoozes             (active alert snoozes)

Settings (/settings)
  ├── Organizations       (tenant org management)
  ├── Locations           (physical locations)
  ├── Roles               (RBAC role definitions)
  ├── Role Assignments    (user-to-role mappings)
  ├── Feature Flags       (feature kill switches)
  ├── Webhooks            (outbound webhook config)
  └── Audit Log           (read-only audit trail)
```

### 10.4 No Duplicate Views

**If the same data can be viewed from two pages, one must be a redirect, not a second route.**

- `/alerts` → redirects to `/incidents?view=events` (same `<Alerts />` component)
- `/tickets` → removed (same `AlertIncident` model as Incidents)
- `/noc-dashboard` → redirects to `/` (same Dashboard)

**Detection rule:** If two routes render the same component or query the same API endpoint,
one is redundant. The canonical route stays, the duplicate becomes a `<Navigate>` redirect.

### 10.5 Breadcrumbs

Detail pages show breadcrumbs:
```
Alerting > Escalation Policies > Standard IT Escalation
```

### 10.6 Deep Links

Every resource detail must be accessible via a stable URL that can be linked from alerts,
incidents, and notifications.

## 11. Visual Standards

### 11.1 Status Badges

| Status | DaisyUI Badge | Required text/icon companion |
|--------|--------------|------|
| Active / Success / Healthy | `badge badge-success` | "Active" / ✓ icon |
| Warning / Pending / In Progress | `badge badge-warning` | "Pending" / ⏱ icon |
| Error / Failed / Critical | `badge badge-error` | "Failed" / ✕ icon |
| Info / New / Draft | `badge badge-info` | "Draft" / ◆ icon |
| Inactive / Disabled / Archived | `badge badge-ghost` | "Inactive" / ⏸ icon |

**Color is never the sole carrier of meaning** (WCAG 1.4.1 — see section 3.1). Every badge pairs the color with the status word and/or a glyph, so colorblind users and high-contrast-mode users see the same information.

### 11.2 Priority Indicators

| Priority | Visual |
|----------|--------|
| Critical / P1 | Red dot or `badge-error` |
| High / P2 | Orange/amber `badge-warning` |
| Medium / P3 | Blue `badge-info` |
| Low / P4 | Gray `badge-ghost` |

### 11.3 Typography

- Page titles: `text-2xl font-bold`
- Section headers: `text-lg font-semibold`
- Table headers: `text-sm font-medium uppercase text-base-content/60`
- Body text: default size
- Help text: `text-sm text-base-content/60`

### 11.4 Spacing

- Page padding: `p-6`
- Card padding: `p-4`
- Between sections: `space-y-6`
- Between form fields: `space-y-4`
- Between buttons: `gap-2`

### 11.5 Density (Comfort vs Compact)

Two density modes are supported across every list-heavy surface:

| Mode | Row height | When | Toggle |
|---|---|---|---|
| **Comfort** (default) | ~48px | Default for new users; ample whitespace | Stored per-user in localStorage |
| **Compact** | ~32px | Power users on desktop scanning long lists | Same toggle, sticky |

Both modes must keep targets ≥ 24×24 CSS px on desktop (section 3.4). Compact does NOT mean shrink-icons-below-target-size; it means tighten vertical padding only.

**Compact density is auto-disabled on touch devices** (≥ 44px tap targets are mandatory there — section 13.4). The toggle is hidden below the `lg:` breakpoint.

The toggle lives in the user's preferences menu (top-right). Tables remember their per-user choice across sessions.

### 11.6 Visual Hierarchy

Per the Aesthetic-Usability Effect, polish raises perceived usability — so apply hierarchy deliberately rather than letting it emerge:

- **One primary action per surface.** A page with three "primary" buttons has zero. Primary = `btn-primary`; everything else is `btn` or `btn-ghost`.
- **Heading levels match nesting.** `<h1>` once per page (the page title). `<h2>` for major sections. `<h3>` for sub-sections inside cards. Don't skip levels.
- **Use the Law of Proximity.** Related fields are ≤ 8px apart; section breaks are ≥ 24px apart. The eye uses spacing as the structure cue before it reads any label.
- **Use the Serial Position Effect.** First and last items in a list are remembered best — put the most important option first or last, never in the middle.

## 12. Data Display

### 12.1 Dates & Times

- Always parse with `parseUTCDate()` from `src/utils/dates.ts`
- Display relative time for recent events ("5 minutes ago")
- Display absolute time for older events with timezone indicator
- Never show raw ISO strings to the user

### 12.2 Numbers

- Use `toLocaleString()` for large numbers (1,234 not 1234)
- **Currency: See section 5.6 — all currency fields MUST use the `CurrencyInput` component**
- Percentages: 1 decimal place with % suffix
- Durations: human-readable ("2h 15m" not "135 minutes")

### 12.3 Truncation

- Long text in table cells: truncate with `truncate` class + title attribute for full text
- Names: never truncate (wrap instead)
- Descriptions: truncate at ~100 chars in lists, show full in detail view

### 12.4 Selects

- HUMAN READABLE - use sensible data from the available table for the drop down never just present or expect the user to enter the ID of a record

## 13. Responsive Design

Cadres is desktop-first but **must work decently on phones and tablets**. Admins approve access requests, triage incidents, ack pages, check status, and run common mutations from their phones — those flows are first-class. Building those well from the start is much cheaper than retrofitting.

The desktop-first framing means: design every page at desktop width, then degrade gracefully to tablet and phone. It does NOT mean: ignore mobile and call it done.

### 13.1 Breakpoints

DaisyUI's Tailwind defaults — match the rest of the codebase:

| Breakpoint | Min width | Typical device | What changes |
|---|---|---|---|
| (default) | 0 | Phones (320–428px) | Sidebar → drawer; tables → card list (or horizontal scroll); modals → full-screen sheet; multi-column forms → single column |
| `sm:` | 640 px | Large phones / small tablets portrait | Same as phone with slightly more breathing room |
| `md:` | 768 px | Tablets portrait | Sidebar still drawer; tables can stay tabular with horizontal scroll; modals revert to centered card |
| `lg:` | 1024 px | Tablets landscape / small laptops | Sidebar pinned; full table layout; multi-column forms |
| `xl:` | 1280 px | Standard laptop | Comfortable reading widths; secondary panels can appear |
| `2xl:` | 1536 px | Large monitors | Wider content area; multi-pane layouts with side detail panels |

**Minimum supported viewport: 360 × 640 px.** That's the lower bound of "modern Android phones." Below that, content can be acknowledged-broken.

### 13.2 Mobile Tier (must work)

Every Cadres surface MUST be usable on phone for these flows:

- **Authentication** — sign in, sign up, password reset, MFA verify.
- **Read the dashboard** — see status, alerts, KPIs.
- **Approve / deny** — support access requests, change approvals, invite acceptances.
- **Triage and ack** — view an incident/alert, assign it, ack it, comment on it.
- **List + detail** — every list page; tap a row to see detail; basic filtering.
- **Common single-record mutations** — toggle a setting, change a status, edit one field.
- **Notification surfaces** — read and act on whatever Portal sent you a webhook/email/push about.

If a destination URL appears in an outbound notification (email, webhook, push), it MUST work on phone — the recipient is going to click it from their phone first.

### 13.3 Mobile Tier (allowed to be desktop-only, but degrade gracefully)

These flows can show "Open on a larger screen for the full experience" with a working summary view on phone:

- **Bulk operations** — selecting > 5 rows and applying a bulk action.
- **Multi-pane layouts** — split-pane editors (rule builder, workflow designer, JSON config).
- **Wide tables with > 8 columns** of dense numeric data.
- **Drag-and-drop reordering** — must have a non-drag alternative (per section 3.2 — WCAG 2.5.7).
- **Complex creation forms** with > 15 fields across multiple sections.

Even for these, do NOT block the user. Render a read-only or simplified version + a "Continue on desktop" hint with a deep link emailed/saved for later.

### 13.4 Touch Targets & Hover

- **All interactive elements ≥ 44 × 44 CSS pixels on touch** (Apple HIG; matches WCAG 2.5.5 AAA). Section 3.4's 24×24 minimum is the WCAG AA floor — we use 24px on dense desktop tables only, never on phones.
- **Enforce the 44×44 minimum in CSS, not per site.** Per §1 Principle 12, the right plumbing for this is a single global rule in `index.css` that promotes compact densities to 44×44 below the `lg:` breakpoint. This neutralizes `btn-xs`, `btn-sm.btn-circle`, and `btn-xs.btn-circle` on touch viewports without editing any call sites and without regressing desktop density:

  ```css
  @media (max-width: 1023px) {
    .btn-xs,
    .btn-xs.btn-circle,
    .btn-sm.btn-circle {
      min-height: 2.75rem;
      min-width: 2.75rem;
      height: auto;
      padding-inline: 0.75rem;
      padding-block: 0.375rem;
      font-size: 0.875rem;
    }
  }
  ```

  With this rule in place, `btn-xs` is a legal per-site choice — on desktop it renders dense as intended, on touch it auto-promotes. Do not refactor 60 `btn-xs` call sites one by one.
- **No hover-only interactions.** Anything reachable via hover (tooltip, dropdown, action menu) MUST also be reachable via tap. Use `@media (hover: none)` to detect touch and convert hover-trigger to tap-trigger. Base CSS state: visible. `focus-within:` may reveal a control for keyboard users. `group-hover:` on a hidden-by-default control is banned — that pattern fails keyboard and touch users simultaneously.
- **Minimum 8px gap between adjacent tap targets.**
- **Avoid the 300ms tap delay** — already handled by `<meta name="viewport" content="width=device-width, initial-scale=1">`, which is mandatory on every page.

### 13.5 Tables on Phone

**Bright-line rule: any table that appears in a §13.2 mobile-tier flow uses Pattern B (card-list).** That set — authentication, dashboard read, approve/deny, triage and ack, list + detail, common single-record mutations, notification surfaces — is the set of flows we've committed to making work on phone. Tables inside those flows must not require horizontal scroll to reach action columns.

**Pattern A (horizontal scroll) is allowed for tables outside the §13.2 set** — dense numeric tables, admin-only surfaces operators would never open on a phone, deep configuration screens. If you're writing a new table and it might ever appear in a §13.2 flow, build Pattern B from the start; retrofitting is much more expensive than doing it once.

```tsx
{/* Pattern A — horizontal scroll (outside §13.2 flows only) */}
<div className="overflow-x-auto">
  <table className="table">…</table>
</div>

{/* Pattern B — card list on phone, table on lg+ (required for §13.2 flows) */}
<div className="lg:hidden divide-y divide-base-300">
  {rows.map(row => (
    <div key={row.id} className="p-4 space-y-2">
      <div className="font-medium">{row.name}</div>
      <div className="text-sm text-base-content/60">{row.subtitle}</div>
      <div className="flex flex-wrap gap-2 pt-1">{/* actions */}</div>
    </div>
  ))}
</div>
<div className="hidden lg:block overflow-x-auto">
  <table className="table">…</table>
</div>
```

The Pattern B card must expose every action the desktop row exposes, gated by the same permission checks. A card that drops actions on phone is a regression, not a responsive variant.

Avoid: a six-column table that requires horizontal scroll AND has an action column on the far right. The user can't see what they're clicking.

**Shared extraction trigger.** The moment a third table needs Pattern B, extract a shared `components/common/MobileCardList.tsx` (or equivalent per-product) — per §1 Principle 12, three duplicates is extraction threshold.

### 13.6 Modals on Phone

- Modals occupy the full viewport on phone — `max-w-none w-full h-full rounded-none` below `md:`. The `ResponsiveModal` wrapper (§7.1) handles this; don't replicate the sizing logic per modal.
- **Close paths on touch** (at least two of three must work):
  - Backdrop tap (ResponsiveModal provides this via `<form method="dialog" className="modal-backdrop">`).
  - Esc / hardware back gesture (ResponsiveModal's document-level keydown listener covers this).
  - Explicit X close button in the top-right — required when the modal has no Cancel button in the action area, recommended otherwise. Not currently added automatically by ResponsiveModal; callers that need it pass it in the modal header. Swipe-down-to-close is a nice-to-have, not a requirement.
- **Sticky action area.** `.modal-action` sticks to the bottom of the viewport below `md:` so primary/secondary actions are reachable without scrolling the form. This is handled by a global rule in `index.css` — do not replicate with inline classes.
- Form modals stack their fields one per row. No two-column field layouts on phone.

### 13.7 Navigation on Phone

- The sidebar collapses to a hamburger-triggered drawer below `lg:`.
- The drawer overlays the content (does not push it).
- Tapping a nav item closes the drawer.
- The page title appears in a sticky top app bar with the hamburger on the left and primary action on the right.
- Bottom navigation bars are NOT used (we have too many sections; bottom nav caps at 5).

### 13.8 Forms on Phone

- One field per row.
- Inputs are full-width (`w-full`) and at least 44px tall.
- Inputs use the right `inputmode` and `autocomplete` attributes so phones show the right keyboard:
  - Email → `inputmode="email" autocomplete="email"`
  - Phone → `inputmode="tel" autocomplete="tel"`
  - Numeric → `inputmode="numeric"`
  - URL → `inputmode="url"`
  - One-time codes → `inputmode="numeric" autocomplete="one-time-code"` (lets iOS suggest the SMS code)
- Date/time pickers use the native picker (`type="date"` / `type="time"` / `type="datetime-local"`) on phone — DO NOT replace with a custom JS picker that doesn't work with the soft keyboard.
- The submit button is full-width and sticky to the bottom of the viewport on phone.

### 13.9 Performance Budget for Phone

Phones are slower CPUs and flakier networks. Hold initial bundle to ≤ 250 KB gzipped per route (lazy-load everything else). Lighthouse Mobile Performance ≥ 80 on the auth, dashboard, and list-view routes.

Long-running operations on phone surface a notification offer ("We'll email you when this finishes") at the 4s mark — phone users back-out far faster than desktop users.

## 14. Internationalization & Localization

Even though the platform ships in English today, every surface is built so that translation never requires a refactor. The cost of doing this from day one is small; the cost of retrofitting is enormous.

- **Never concatenate strings to form user-facing text.** "Hello, " + name does not localize. Use template strings like `t('greeting', { name })` so translators can re-order tokens.
- **All user-facing strings live in a single i18n catalog** (no inline literals in JSX — wrap with `t('…')` or your i18n hook). Even before we add a second locale, this gives us one place to edit copy.
- **Numbers, dates, currency: format via `Intl`** (`Intl.NumberFormat`, `Intl.DateTimeFormat`). Never hand-format with `toFixed(2)` for currency or `padStart(2, '0')` for dates. Don't hardcode a `'en-US'` locale on `toLocale*` calls — pass `undefined` so the user's browser locale wins.
- **Plurals use ICU MessageFormat** (`{count, plural, one {# user} other {# users}}`), not `count === 1 ? 'user' : 'users'`. The latter breaks for languages with non-binary plural rules.
- **Mid-string interpolation uses ICU placeholders, not concatenation.** Prefer `"priority_value": "Priority {value}"` + `t('common.priority_value', { value })` over `<>Priority {value}</>`. The latter forces translators into English word order.
- **Don't bake text into images.** SVGs that need text render the text as `<text>` so translation works.
- **Bidi-friendly layout.** Use logical CSS properties (`margin-inline-start`, `padding-inline-end`) over `margin-left` / `padding-right` so RTL locales flip correctly.
- **Allow text growth.** German is ~30% longer than English; allow 50% growth in button labels and table headers without truncation or layout collapse.

### 14.1 Canonical setup (Cadres Portal)

- `src/i18n/index.ts` initializes `i18next` with `LanguageDetector`, `i18next-icu`, and `initReactI18next`. The detector stores the chosen locale in `localStorage` under `cadres_locale`.
- The catalog is a single JSON file per locale under `src/i18n/locales/<lang>.json`, keyed by feature namespace (matching the sidebar: `users`, `groups`, `tenants`, `applications`, `federation`, `auth`, `common`, …). New strings go into the namespace of the file that owns them; reusable copy goes into `common`.
- Components import the bound `t` from `src/i18n` for module-level use (`import { t } from '../i18n'`). Components that must re-render on language change use `useTranslation()` from `react-i18next` instead — mostly irrelevant today since we ship only English.
- Tests import `../i18n` in `src/test/setup.ts` so `t(…)` resolves against the real catalog instead of returning raw keys. Queries in Testing Library stay on the English strings.
- When the tooling catches an untranslated literal (the `check-standards.sh` gate or review feedback), fix it in the same PR as the change that introduced it. Don't defer.

## 15. Theming & Dark Mode

DaisyUI's theme system is the single source of truth for colors. Custom CSS that hard-codes `#fff` or `text-gray-700` defeats theming and breaks dark mode.

- **Use semantic color tokens, not literal colors.** `bg-base-100`, `text-base-content`, `text-primary`, `border-base-300` — these adapt to the active theme. `bg-white` does not.
- **Test every page in both light and dark themes** before merging. The CI gate doesn't catch this; design review must.
- **Custom illustrations / SVGs** use `currentColor` for strokes and fills wherever possible so they pick up the theme automatically.
- **Status colors** (success/warning/error/info) come from DaisyUI's semantic palette, which is contrast-tuned for each theme. Don't override them per-component.
- **Theme selection** is per-user, persisted in localStorage. Honor `prefers-color-scheme` for the default on first visit.

## 16. Telemetry-Friendly Markup

The frontend is the cheapest place to add the breadcrumbs that incident response needs later. Bake them in now.

- **Every interactive element gets a stable `data-testid`** for both Playwright tests and product analytics. Format: `data-testid="<feature>-<action>"` (e.g., `data-testid="users-create-button"`). IDs never change shape between releases; renaming one is a breaking change.
- **Every page logs a `route_view` event on mount** with the route path and the current tenant_id. This drives the page-level analytics dashboard and the per-route latency telemetry.
- **Every form submit logs `form_submit` with form name + outcome (success/error)** before the toast fires. Failed submits include the parsed error text — the same string the user saw — so support can correlate user reports to telemetry without asking the user to screenshot.
- **No PII in event payloads.** Email addresses, passwords, tokens, secret values, even raw resource names go through a redaction layer before they leave the browser. When in doubt, send the resource ID and let the backend join.
