## Goal

This task delivers the MCP tool that lets a client inspect the current `WorkingMemoryState` and the event-capture hooks that automatically log included and excluded context per spec §Phase 5 deliverable ("automatic event capture for included and excluded context"). The MCP tool exposes the same compact-by-default shape the rest of the MCP surface uses; the event hooks emit `MemoryRetrieved` and `MemoryExpanded` events (Phase 2 event kinds) every time the working memory's `selected_memories` or `excluded_memories` change. Together these make working memory observable — meeting the Phase 5 Definition of Done ("workflow tools can show what context is active, why it is active, and what was intentionally excluded").

## Steps

1. Re-read spec §Phase 5 deliverables, §3. Event Log event-kind list, and §9. MCP Surface response contract to fix the tool shape and event-emission contract.
2. Implement `daemon/crates/lattice-daemon/src/rpc/working_memory_tool.rs`: register a new MCP tool `inspect_working_memory` with schema `{ task_id: string, mode: "compact" | "diagnostic", include_excluded: boolean }`. The handler loads the active `WorkingMemoryState` for the task (from the session-scoped in-memory store maintained by T35's `OpContext`, falling back to the latest checkpoint if the session has rolled), then returns either a compact summary (via T35 `summarize`) or the full state including `excluded_memories` when `include_excluded=true`. Response carries an `expansion_handle` per spec §9 so the caller can expand the full state without re-fetching.
3. Wire the tool into `mcp.rs` dispatch alongside the existing 43 tools. Tool registration includes the schema in the MCP `tools/list` response; failure to expose a parameter is a contract violation caught by the cross-layer MCP schema test gate.
4. Implement `daemon/crates/lattice-core/src/working_memory/event_hooks.rs`: a small module exposing `emit_memory_retrieved(state_before, state_after, op_summary, writer)` and `emit_memory_expanded(state_before, state_after, op_summary, writer)`. Each function computes the diff (which identities were added to `selected_memories`, which were added to `excluded_memories` with reasons), packages the diff into an event payload per Phase 2's event-payload contract (workspace, branch, session, task, actor, timestamp, payload hash, compact summary, optional full payload location), and writes through the Phase 2 event writer.
5. Attach the hooks to T35's `record_state_mutation` so every state-mutating operation emits the appropriate event automatically: `retrieve` and `compress` emit `MemoryRetrieved` (since they decide what is included/excluded); `expand` emits `MemoryExpanded`; `pin`, `evict`, `filter`, `checkpoint` emit `MemoryRetrieved` when they change inclusion/exclusion. `summarize` emits no event.
6. Honor the spec invariant "the full event stream should not be injected into prompts" — the event hooks never put event data back into `WorkingMemoryState`. Events flow one way: state mutation → event log.
7. Hot-path discipline: event writes share the existing Phase 2 write budget (`≤5ms P99`). If the writer returns a backpressure error, the operation does not fail — the event is dropped with a `warn!` log naming the task and operation, per `coding.md` "no silent .catch" but tolerant of event-log overload.
8. Add `daemon/crates/lattice-daemon/src/rpc/working_memory_tool_tests.rs` covering: tool registration appears in `tools/list`; compact mode returns a summary; diagnostic mode returns the full state and embedded `RetrievalBundle`-shaped `selected_memories`; `include_excluded=true` returns excluded entries with reasons; expansion handle round-trips back to the same state; a synthetic event writer captures one `MemoryRetrieved` event per `retrieve` call and one `MemoryExpanded` event per `expand` call; event payload carries the included and excluded identity diffs and reasons.
9. Run `cd daemon && cargo build --release` (release build verifies the whole daemon still compiles with the new tool registered), then `cd daemon && cargo test -p lattice-daemon --lib rpc::working_memory_tool_tests`. Deploy the new daemon binary per the project rule (`pkill -f lattice && cp daemon/target/release/lattice extension/bin/ && cp daemon/target/release/lattice ~/.vscode/extensions/lattice.lattice-0.1.0/bin/`) only when explicitly told to ship; the test commands themselves do not require a redeploy.
