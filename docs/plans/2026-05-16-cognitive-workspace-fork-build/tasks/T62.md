## Goal

This task wires automatic workflow-outcome recording into every redesigned tool from T56–T60 and ships the composition test suite that proves the new tools compose correctly over the underlying substrates. Spec §Phase 8 Deliverables names "workflow outcome recording integrated by default" as a binding deliverable. Spec §MCP Tool Contract Principles requires "every workflow tool should record inputs, resolved anchors, selected candidates, excluded high-scoring candidates where useful, response summary, downstream use events." Without this task, individual tools work in isolation but the event log + memory consolidation cannot observe whether a workflow succeeded, which breaks Phase 6 procedure extraction and Phase 9 success metrics.

## Steps

1. Read spec §Phase 8, §MCP Tool Contract Principles, and §Event Log in full. Quote the "Every workflow tool should record…" paragraph verbatim into a doc comment on `workflow_v2/outcome_capture.rs` so the contract is enforced at the call site.
2. Implement `workflow_v2/outcome_capture.rs` as a reusable interceptor: a `WorkflowOutcomeRecorder` type that wraps any tool handler, captures inputs, resolved anchors, selected candidates, excluded candidates (the top-N high-scoring candidates that were rejected and why), response summary, and emits a `WorkflowSucceeded` or `WorkflowFailed` event on completion. The recorder must run on the hot path within the spec §Phase 2 budget (≤5ms P99 overhead).
3. Wire `WorkflowOutcomeRecorder` into every redesigned tool from T56 and T57 by default. Wire it into every memory tool from T58/T59/T60 that participates in a user-facing workflow (excluding `get_event_trace`, which would create a feedback loop). Default-on means the tool registration in `mcp.rs` constructs the recorder around the handler; the legacy explicit `record_workflow_outcome` tool remains available as a manual override per the T02 compatibility policy.
4. The recorder must also feed `session_metrics` so success rate, irrelevant-files-opened, and `workflow_success_after_first_plan` (from spec §Phase 9) are accumulated automatically.
5. Define how "downstream use events" are tracked: when a returned context handle or memory ID is subsequently referenced in another tool call, the recorder back-links the later event to the originating workflow via the Phase 2 `EventEnvelope::references` field.
6. In `workflow_v2/composition_tests.rs`, write composition tests that exercise the new tools end-to-end against a fixture workspace: (a) `prepare_change → plan_edit → apply_patch_simulated → record outcome` chain emits the correct sequence of events; (b) `get_context_capsule → expand_context` chain returns stable handle deltas without redundant payload; (c) `diagnose_failure → prepare_change` chain reuses anchors from the failure diagnosis; (d) `save_memory → verify_explain_memory` chain transitions an unverified memory to a verified state and emits the matching events; (e) `consolidate_session → propose_memory_evolution(action="apply")` chain applies a proposal that the session produced; (f) every workflow chain emits exactly one `WorkflowSucceeded` or `WorkflowFailed` event per outer call; (g) excluded high-scoring candidates appear in the recorded outcome with rejection reasons.
7. Assert that the hot-path budget is honored: composition tests measure the per-tool overhead added by `WorkflowOutcomeRecorder` and fail if it exceeds the spec §Phase 2 ≤5ms P99 budget.
8. Assert that scope-leak and workspace-boundary protections from T58–T60 are preserved when the recorder is in the path.

## Coding-standard checks

- File length ≤800 lines per file.
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10.
- Schema parity: the recorded outcome payload uses the same `WorkflowSucceeded` / `WorkflowFailed` envelopes defined in Phase 2; no parallel outcome struct is introduced.
- No silent error handling — recorder failures emit `tracing::warn!` AND surface as `RiskNote`s in the bundle, never swallowed.
- No `TODO`, `FIXME`, `XXX`, commented-out code; no unjustified `#[allow(...)]`.
- Public API names follow intent-over-mechanism naming (`WorkflowOutcomeRecorder::record_excluded`, not `WorkflowOutcomeRecorder::also_excl`).
- For SQLite: outcome persistence goes through the Phase 2 event writer; no raw SQL in the RPC layer.
- Observability: the recorder emits one `tracing::info!` span per recorded outcome with `tool`, `task_id`, `session_id`, `outcome`, `excluded_count`, `latency_ms` fields.
- Doc citation: cite spec headings `## Phase 8: Workflow Engine V2`, `## MCP Tool Contract Principles`, `## Event Log`, and `## Phase 2 — Event Log Substrate` Definition of Done (hot-path budget) in module doc comments.
