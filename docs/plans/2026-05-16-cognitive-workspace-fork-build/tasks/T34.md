## Goal

This task delivers the per-task, short-lived working-memory state model the spec mandates in §5 — making context management explicit instead of implicit prompt accumulation — and pins it to a versioned `working_memory_checkpoints` SQLite table so checkpoints can be restored. The state model contains exactly the eleven fields the spec enumerates; the checkpoint schema preserves the full state along with timestamps and a checkpoint name so T35's `checkpoint` operation has a target to write into and T37's restore tests have a target to restore from.

## Spec excerpts that drive this task

> "Working memory is per-task and short-lived. It should be explicit rather than implicit prompt accumulation. Working memory contains: task statement; interpreted intent; active files and symbols; active hypotheses; active failures; current plan; selected memories; excluded memories and reasons; budget decisions; unresolved questions; verification status." (spec §5. Working Memory)

> "Phase 5: Working Memory — Deliverables: explicit per-task working memory state; operations for retrieve, summarize, filter, pin, evict, expand, compress, and checkpoint; MCP surface for inspecting current working memory; automatic event capture for included and excluded context; tests for token budgets, pinned context, eviction, and checkpoint restore." (spec §Phase 5: Working Memory)

> "Definition of done: workflow tools can show what context is active, why it is active, and what was intentionally excluded; context management is no longer just prompt accumulation." (spec §Phase 5: Working Memory)

## Steps

1. Re-read spec §5. Working Memory and §Phase 5: Working Memory in full; copy the eleven-field state list verbatim into a doc comment at the top of `state.rs`.
2. Create the module skeleton: `daemon/crates/lattice-core/src/working_memory/mod.rs` re-exports `state`, `operations` (T35), `event_hooks` (T36) and registers the module with `lib.rs`.
3. Implement `daemon/crates/lattice-core/src/working_memory/state.rs` with `WorkingMemoryState { task_statement: String, interpreted_intent: IntentClassification, active_files: BTreeSet<FileIdentity>, active_symbols: BTreeSet<SymbolIdentity>, active_hypotheses: Vec<Hypothesis>, active_failures: Vec<FailureRecord>, current_plan: Option<PlanRef>, selected_memories: Vec<BundleResult>, excluded_memories: Vec<ExcludedMemory>, budget_decisions: BudgetDecisions, unresolved_questions: Vec<String>, verification_status: WorkingMemoryVerification }`. Field names mirror the spec exactly. `ExcludedMemory { result: BundleResult, exclusion_reason: String }` makes the "and reasons" half of the spec phrase a type-system requirement, not a convention.
4. Define supporting types in the same module: `Hypothesis { text, evidence_refs, confidence }`, `FailureRecord { kind, message, observed_at, evidence_refs }`, `PlanRef { plan_id, version }`, `BudgetDecisions { token_cap, dropped_count, truncated_results, pinned_identities }`, `WorkingMemoryVerification { last_verified_at, status: enum, notes }`.
5. Author the schema SQL in `daemon/crates/lattice-core/src/working_memory/schema.sql` for the `working_memory_checkpoints` table: `(checkpoint_id INTEGER PK, workspace_id TEXT NOT NULL, session_id TEXT NOT NULL, task_id TEXT NOT NULL, checkpoint_name TEXT NOT NULL, created_at INTEGER NOT NULL, state_version INTEGER NOT NULL, state_json TEXT NOT NULL, state_hash TEXT NOT NULL)` plus indexes on `(workspace_id, session_id, task_id, created_at DESC)` and `(state_hash)`. `state_version` is bumped whenever `WorkingMemoryState` shape changes; migrations are rejected at load time if `state_version` is unknown.
6. Wire the migration into the existing storage bootstrap: `working_memory_checkpoints` lives in the existing memory DB (`.lattice/memories.db`) so it shares the session/task identity referenced elsewhere. Document this placement decision inline with `## Storage Design` citation.
7. Implement `save_checkpoint(state: &WorkingMemoryState, name: &str, conn: &Connection) -> Result<CheckpointId>` and `load_checkpoint(id: CheckpointId, conn: &Connection) -> Result<WorkingMemoryState>` in `state.rs`. Serialization uses serde JSON; `state_hash` is a deterministic SHA-256 over the canonical-JSON form so restore can be verified bit-for-bit.
8. Add `daemon/crates/lattice-core/src/working_memory/state_tests.rs` covering: default-constructed state has the eleven required fields; serde round-trips the state without data loss; `save_checkpoint` followed by `load_checkpoint` returns a byte-identical `WorkingMemoryState`; `state_hash` matches between save and load; loading a checkpoint with an unknown `state_version` is rejected with a clear error; `excluded_memories` cannot be constructed without an `exclusion_reason` (type-system enforced).
9. Run `cd daemon && cargo build --release` and the verification test command; fix any clippy warnings before stopping.
