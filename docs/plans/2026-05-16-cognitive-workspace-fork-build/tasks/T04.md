# T04 — Phase 0 — Baseline benchmark capture (current Lattice workflows)

**Phase:** 0
**Type:** tests
**Model class:** balanced
**Depends on:** T01
**Spec anchor:** [§Phase 0: Fork Foundation](../../2026-05-16-cognitive-workspace-fork-plan.md#phase-0-fork-foundation)
**Standards:** Cadres coding standard; Lattice project rules (`/home/pete/cadres/lattice/CLAUDE.md`, `AGENTS.md`).

## Goal

This task captures benchmark numbers for the existing Lattice workflow tools so Phase 4 (retrieval), Phase 9 (metrics), and the hot-path budget assertions in Phase 1 and Phase 2 have a real baseline to regress against. Spec §Phase 0 Deliverables explicitly requires "baseline benchmark suite from current Lattice workflows." Without these numbers, later claims of "no regression" or "30 percent fewer discovery tool calls" cannot be evaluated objectively. The benchmark must follow Rust criterion conventions, run from `cargo bench`, and emit a JSON metrics file the build harness can verify.

## Spec excerpts that drive this task

> "Phase 0 Deliverables: ... baseline benchmark suite from current Lattice workflows."

> "Verification: current Lattice daemon tests pass in the fork before major changes; current MCP workflow fixtures run unchanged or with documented compatibility shims."

> Spec §Measurable Success Criteria targets ("30 percent fewer discovery tool calls on benchmark tasks; 40 percent fewer irrelevant file reads") only make sense against a measured baseline.

## Steps

1. Read T01 to confirm the branch and `daemon/crates/lattice-core/Cargo.toml` to confirm criterion availability; add `criterion = { version = "...", features = ["html_reports"] }` under `[dev-dependencies]` and a `[[bench]]` entry pointing at the new file if needed.
2. Create `daemon/crates/lattice-core/benches/baseline_workflows.rs` using `criterion::{criterion_group, criterion_main, Criterion}`.
3. Add one benchmark function per critical workflow: `bench_prepare_change`, `bench_get_context_capsule`, `bench_expand_context`, `bench_impact_from_diff`, `bench_diagnose_failure`, `bench_search_symbols`, `bench_find_relevant_tests`. Each must operate on a fixture workspace identical to the one used in `benchmark_tests.rs` so future regressions are comparable.
4. Each benchmark records latency distribution (p50, p95, p99) and result-size statistics (bytes returned, candidate count). The fixture must be deterministic and self-contained — no I/O outside a tempdir.
5. After running, persist a structured metrics snapshot to `docs/plans/2026-05-16-cognitive-workspace-fork-build/baselines/baseline_metrics.json` containing one object per benchmark with `name`, `p50_us`, `p95_us`, `p99_us`, `bytes_returned`, `commit_sha`, and `recorded_at`. A small helper in the bench file or a follow-up `bench_report` binary should write this file at the end of the bench run.
6. Add `docs/plans/2026-05-16-cognitive-workspace-fork-build/baselines/README.md` explaining how to re-run the benchmarks, how to interpret the metrics file, and the rule that regression checks in Phase 4 and Phase 9 use this file as the reference.
7. Document the absolute target budgets (≤2ms P99 identity resolution, ≤5ms P99 event write on hot paths) and confirm the bench file measures the pre-Phase-1 baseline so the budget asserts can be evaluated as deltas.
8. Run `cd daemon && cargo build --release --benches` and `cd daemon && cargo bench --bench baseline_workflows -- --warm-up-time 1 --measurement-time 3` to validate the bench compiles, runs, and produces the metrics file.
