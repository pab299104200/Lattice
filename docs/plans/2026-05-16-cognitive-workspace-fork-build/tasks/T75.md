## Goal

This task delivers two diagnostic surfaces: the event trace view (operator-facing renderer for the append-only event log filtered by session/task/workspace) and the retrieval explanation view (renders the ranking scores + reasons emitted by the Phase 4 retrieval diagnostic mode). They are the surfaces operators use to answer two binding questions: "what actually happened in this session?" (event trace) and "why did this context get included and that other thing get excluded?" (retrieval explanation). Spec §10 lists both as required; spec §7 requires the ranker to expose scores and reasons in diagnostic mode, which is the data shape this UI consumes.

## Spec excerpts that drive this task

> "Required operator views: ... event trace view; retrieval explanation view; ..." (spec §10)

> "The ranker should expose scores and reasons in diagnostic mode. Compact mode should include only enough explanation for an assistant to trust the result." (spec §7)

> "Events should carry: workspace id; branch; session id; task id; actor; timestamp; stable references to files, symbols, docs, events, and memories; payload hash; compact payload summary; optional full payload location." (spec §3 — every column the event trace view renders)

> "New or redesigned memory tools: ... `get_event_trace`." (spec §9)

## Steps

1. Read spec §3 Event Log (event types and envelope fields) and §7 Retrieval Engine (pipeline steps, candidate sources, ranking signals, diagnostic mode requirement) so the column sets are grounded in the spec, not invented.
2. Create `extension/src/review/eventTraceView.ts` exporting `mountEventTraceView(host, bridge, i18n, { sessionId?, taskId?, memoryId? })`. The optional initial filter lets the inbox (T72) and evidence inspector (T74) deep-link directly to the relevant trace slice. Render a sortable, paginated table with columns: `Timestamp`, `Kind` badge, `Actor`, `Task`, `Session`, `Workspace`, `References` (compact summary of `StableRef`s), `Summary` (compact payload summary), `Payload` (expand to inline view via `<dialog>`).
3. Filter bar: `Kind` (multi-select over the 20 event kinds from spec §3), `Actor` (multi-select over `Assistant`, `User`, `Tool`, `Daemon`), `Session`, `Task`, `Workspace`, `Branch`. Filters route through `vscode.window.showQuickPick`. Time window is two text inputs validated against ISO 8601.
4. Payload expansion uses a native `<dialog>` that renders the structured payload as a syntax-highlighted JSON tree (collapsible) with `Copy to clipboard` and `Open in editor` actions. Never `window.confirm`/`prompt`/`alert`.
5. Create `extension/src/review/retrievalExplanationView.ts` exporting `mountRetrievalExplanationView(host, bridge, i18n, requestId)`. The subview is a single-request deep dive that renders:
   - Request header: tool name, task statement, intent classification (from Phase 4 T27), timestamp.
   - Anchors panel: every resolved anchor (file/symbol/error/command/API/config-key per spec §7) with its resolution provenance.
   - Candidate table: every candidate retrieved across the seven candidate sources from spec §7, with columns `Source`, `Identity`, `Inclusion Decision` badge (`included`/`excluded`/`expanded`), `Score`, `Top Signals` (truncated list of the top three ranking signals from spec §7), `Reason` (compact explanation).
   - Excluded-candidate panel: high-scoring candidates that were intentionally excluded, with the exclusion reason — spec §MCP Tool Contract Principles requires "excluded high-scoring candidates where useful" to be recorded.
   - Full-signal panel: per-candidate expandable view listing every ranking signal from spec §7 (task-type compatibility, graph proximity, exact identifier match, semantic similarity, verification status, freshness, scope, evidence strength, contradiction/supersession state, past usefulness, recent successful reuse, user-preference compatibility, token cost) with the candidate's score on each.
6. Wire cross-navigation: from the event trace, clicking a `MemoryRetrieved` event opens the retrieval explanation view for that request id; clicking a memory reference opens the evidence inspector (T74); clicking a file/symbol reference opens the file in VS Code via `vscode.commands.executeCommand('vscode.open', uri)`.
7. Add i18n keys under `eventTraceView` and `retrievalExplanationView` namespaces: column headers, filter labels, all 20 event-kind labels, all 13 ranking-signal labels, decision badge labels, dialog title, copy/open action labels, success/error strings, loading hint, empty state.
8. Wrap every bridge call in `try/catch` and surface failure both inline and via `vscode.window.showErrorMessage`.
9. Run `cd extension && npm run compile && npm run lint` and fix every error/warning before stopping.

## Coding-standard checks

- File length ≤800 lines per file. If the retrieval explanation grows beyond, split per panel (`anchors.ts`, `candidates.ts`, `signals.ts`).

### UI specification

- All user-facing strings via `i18n.t(...)` from the `eventTraceView` and `retrievalExplanationView` namespaces; no inline literals in either file.
- All modals via native `<dialog>` — payload expansion in the event trace uses `<dialog>`. Never `window.confirm/prompt/alert`.
- All mutation handlers — these views are predominantly read-only; the `Copy to clipboard` and `Open in editor` actions on the payload dialog use `try/catch` with `vscode.window.showErrorMessage(err.message)` on failure (`parseApiError` does not apply in the VS Code extension context).
- All ID inputs use `SearchableSelect` (webview) or `vscode.window.showQuickPick` (tree-view) — session/task/workspace/branch filter pickers all use `showQuickPick`. Never raw `<select>` or `prompt`-based ID entry.
- Sortable tables use `SortableHeader` + `useTableSort` equivalents on the event trace (sortable on `Timestamp`, `Kind`, `Actor`) and on the candidate table (sortable on `Score`, `Source`, `Decision`). Pagination is required on every list per `ui-specification.md` §6.1.
- Status badges + loading + empty + error states for every interactive surface: event-kind badges + decision badges via the shared component; loading skeleton on first load; distinct empty states ("No events for the selected filters." vs "No retrieval request found for this id."); error banner inline + VS Code toast on failure.
