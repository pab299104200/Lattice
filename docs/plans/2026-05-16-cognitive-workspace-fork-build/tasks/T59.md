## Goal

This task introduces the unified `verify_explain_memory` MCP tool (collapsing the spec's `verify_memory` + `explain_memory` per §MCP Surface "Tool surface discipline") and the new `list_memory_conflicts` tool. The unified tool runs verification checks against a memory and returns both the resulting status (`verified` | `unverified` | `in_review` | `stale` | `contradicted` | `superseded` | `expired` | `invalidated`) and a structured explanation of why each linked file/symbol/doc/test contributed to that status. `list_memory_conflicts` surfaces all contradiction and supersession edges anchored on a target memory or graph node so an operator can review them. Both tools are required by spec §MCP Surface and are the trust surface for the verification engine — without them, the Phase 7 verifier produces statuses that no assistant or operator can interrogate.

## Steps

1. Read spec §MCP Surface and §Verification Engine in full. Quote the "Tool surface discipline" paragraph verbatim into a doc comment on `memory_v2/verify_explain_memory.rs` so the rationale for unifying `verify_memory` + `explain_memory` is preserved at the call site.
2. Implement `verify_explain_memory` in `memory_v2/verify_explain_memory.rs` as the unified tool. Accept `memory_id: MemoryId` plus optional `mode: "verify" | "explain" | "verify_and_explain"` (default `verify_and_explain`). Internally run the Phase 7 verifier on the memory, then construct an `ExplainReport` that itemizes each verification check (linked file exists, linked symbol exists, cited doc exists, linked test exists, evidence span still matches, contradiction state coherent, scope leak absent, time-bound expiry honored) and the outcome per check. Return a `VerifyExplainResponse` with `status: VerificationStatus`, `checks: Vec<CheckResult>` (each carrying `kind`, `target`, `outcome`, `evidence_ref`), `confidence_delta`, and an `expansion_handle` so the caller can pull richer context.
3. Mode semantics: `verify` returns only the status + a minimal summary; `explain` skips re-running checks and returns the last persisted `ExplainReport`; `verify_and_explain` runs verification and returns the freshly-derived `ExplainReport`. Default is `verify_and_explain` because spec §Verification Engine and §MCP Tool Contract Principles together require fresh, explainable status on every memory surface.
4. Implement `list_memory_conflicts` in `memory_v2/list_memory_conflicts.rs`. Accept `anchor: MemoryId | FileId | SymbolId | DocSectionId`, traverse `contradicts` and `supersedes` link types from Phase 3 memory_links, and return a paginated list of `ConflictRecord`s each carrying `source`, `target`, `link_type` (`contradicts` | `supersedes`), `link_strength`, `created_by`, `created_at`, `link_verification_status`, and `reason`. Honor scope filters per spec §Risks "Scope Leakage."
5. Both tools must emit appropriate Phase 2 events: `verify_explain_memory` emits `MemoryRetrieved` plus `MemoryInvalidated` when status transitions away from `verified`; `list_memory_conflicts` emits `MemoryRetrieved` for each surfaced conflict.
6. Both tools must support compact + full + diagnostic render modes per spec §MCP Tool Contract Principles. Compact mode for `verify_explain_memory` returns status + one-line per failed check; diagnostic mode returns the full check trace.
7. Register the two tools in `daemon/crates/lattice-daemon/src/rpc/mcp.rs`. Per the T02 compatibility policy, the spec's nominal `verify_memory` and `explain_memory` names continue to respond as deprecation shims that forward to `verify_explain_memory` with the appropriate `mode`. The shims emit a deprecation warning in the response.
8. In `memory_v2/verify_explain_tests.rs`, write tests that: (a) round-trip each tool's request/response through serde; (b) assert `verify_explain_memory` returns the exact Phase 7 status taxonomy and never invents a new status string; (c) assert every check result carries an evidence reference; (d) assert a memory whose linked symbol was deleted transitions to `stale` with a `linked_symbol_missing` check failure; (e) assert `list_memory_conflicts` returns both `contradicts` and `supersedes` edges with correct directionality; (f) assert scope-leak negative tests; (g) assert the `verify_memory` and `explain_memory` deprecation shims continue to respond and forward correctly.
