# T15 — Phase 2 — MCP/tool-call event capture wiring (all workflow tools)

**Phase:** 2
**Type:** backend
**Model class:** advanced
**Depends on:** T13, T14
**Spec anchor:** [§Phase 2: Event Log Substrate](../../2026-05-16-cognitive-workspace-fork-plan.md#phase-2-event-log-substrate)
**Standards:** Cadres coding standard; Lattice project rules.

## Goal

This task instruments the JSON-RPC / MCP handler and every existing workflow tool so each invocation emits the right event sequence: `AssistantTaskStarted` (when a session/task begins), `ToolCalled` (on dispatch), `ToolResult` (on return), plus the workflow-specific outcome events (`ContextBundleReturned`, `MemoryRetrieved`, `MemoryExpanded`, `PlanCreated`, `WorkflowSucceeded`, `WorkflowFailed`, etc.). All events use the stable identities from Phase 1 — never transient names. Capture must be non-blocking on the hot path, must not hide tool errors, and must respect the workspace scope of the calling session. This task is the bridge that lets every later capability (consolidation, retrieval explanations, metrics) reference real history.

## Spec excerpts that drive this task

> "MCP/tool-call event capture using stable identities from Phase 1 … workflow task/session correlation …"

> "every high-level MCP workflow records task, retrieval, response, and outcome events … failure paths emit useful events without hiding errors."

> "event write adds no more than 5ms P99 to hot-path tool calls (`prepare_change`, `get_context_capsule`); large payloads spill to a side table rather than blocking the writer."

## Steps

1. In `extension/`-adjacent docs, confirm the existing list of workflow tools to instrument. The capture wiring must cover at minimum: `prepare_change`, `plan_edit`, `get_context_capsule`, `expand_context`, `get_working_set_context`, `trace_scenario`, `summarize_subsystem`, `impact_from_diff`, `diagnose_failure`, `record_workflow_outcome`, `save_observation`, plus any others currently dispatched through `McpHandler::handle_tools_call()`.
2. In `rpc/event_capture.rs`, define `pub struct EventCapture { writer: Arc<EventWriter>, session_id: SessionId, current_task: Mutex<Option<TaskId>> }`. The capture is created per-session by `server.rs` at connection start.
3. Define lifecycle methods:
   - `EventCapture::begin_task(&self, task_id: TaskId, statement: &str) -> Result<EventId, EventWriteError>` — emits `AssistantTaskStarted`.
   - `EventCapture::record_tool_called(&self, tool: &str, inputs: &serde_json::Value) -> Result<EventId, EventWriteError>` — emits `ToolCalled` with inputs as the payload.
   - `EventCapture::record_tool_result(&self, tool: &str, result: &ToolOutcome, parent: EventId) -> Result<EventId, EventWriteError>` — emits `ToolResult` referencing the parent `ToolCalled` event.
4. Define workflow-outcome helpers used by each tool:
   - `record_context_bundle(handle: ContextHandleId, anchors: &[StableRef], inclusion_reasons: &[String])` — emits `ContextBundleReturned`.
   - `record_memory_retrieved(memory_ids: &[MemoryId], reasons: &[String])` — emits `MemoryRetrieved`.
   - `record_memory_expanded(memory_id: MemoryId, depth: u8)` — emits `MemoryExpanded`.
   - `record_plan_created(plan_id: PlanId, target_files: &[FileId])` — emits `PlanCreated`.
   - `record_file_read(file_id: FileId, byte_range: Option<(u64, u64)>)` — emits `FileRead`.
   - `record_patch_applied(patch_id: PatchId, files: &[FileId])` — emits `PatchApplied`.
   - `record_test_run(events: TestRunPair)` — emits the `TestRunStarted` / `TestRunCompleted` pair.
   - `record_diagnostic(diag: DiagnosticRecord)` — emits `DiagnosticObserved`.
   - `record_user_correction(prior_event: EventId, correction: &str)` — emits `UserCorrection`.
   - `record_user_preference(scope: PreferenceScope, value: PreferenceValue)` — emits `UserPreferenceObserved`.
   - `record_workflow_outcome(success: bool, summary: &str, evidence: &[EventId])` — emits `WorkflowSucceeded` or `WorkflowFailed`.
5. Memory lifecycle helpers (used by Phase 3 store and Phase 6 consolidation, defined here so the call sites can be wired in T23/T24 without re-importing): `record_memory_created`, `record_memory_updated`, `record_memory_invalidated`, `record_memory_consolidated`.
6. In `rpc/mcp.rs`, wrap `handle_tools_call` so that every dispatch goes through `EventCapture::record_tool_called` before the tool runs and `record_tool_result` after — including in the error branch. Errors propagate to the JSON-RPC response; capture must NOT swallow them.
7. In each instrumented workflow tool, add capture calls at the outcome points (e.g. `prepare_change` calls `record_context_bundle` + `record_workflow_outcome`). Where the tool already has telemetry hooks via `session_metrics`, route capture through the same hook so the two stay in sync.
8. Use the batched flush policy from T13 for hot-path tools (`prepare_change`, `get_context_capsule`, `expand_context`) so capture writes do not stall the response. Use sync flush for terminal outcomes (`WorkflowSucceeded`/`Failed`, `MemoryInvalidated`) so durability is guaranteed before the caller proceeds.
9. Define `ToolOutcome` and the per-tool outcome enum (`Success(serde_json::Value)`, `Error { code, message }`) so capture can record structured failure reasons, never just a stringified error.
10. In `rpc/event_capture_tests.rs`, write tests that:
    - dispatch each instrumented tool through a test handler and assert the expected event sequence appears via `EventReader::tail`.
    - assert tool errors still emit a `ToolResult` event with `Error`, and the JSON-RPC error is still returned to the caller.
    - assert workspace mismatch on session setup is rejected at `EventCapture::new`.
    - assert batched flush coalesces multiple `ToolCalled` events for the same session under one fsync.

## Coding-standard checks

- File length ≤800 lines per file (split per-tool wiring into helper modules if needed).
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10.
- Schema parity: every payload struct emitted matches a T11 typed payload — no ad-hoc JSON.
- No silent error handling — tool errors propagate to JSON-RPC; capture errors log at `warn` and never swallow the tool result.
- No `TODO`, `FIXME`, commented-out code.
- For SQLite: not applicable directly; the writer (T13) owns SQL.
- Use `tracing::info_span!("tool", name = ...)` around dispatch so capture spans correlate with operator-visible logs.
