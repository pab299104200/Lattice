**Standards:** Cadres coding standard; Lattice project rules (`/home/pete/cadres/lattice/CLAUDE.md`, `AGENTS.md`).

## Goal

This task adds the spec-required manual-review queue for high-scope memory changes (repo and organization scope). Proposals targeting workspace-local or session-local memory may be auto-applied by operator policy, but every proposal whose target memory carries scope `repo` or `organization` MUST land in the manual-review queue and stay there until a human operator decides. The queue is the durable backing for the Phase 10 "memory inbox" UI surface listed in §Human Review Surface. Without this gate, T42's LLM-driven jobs could silently promote repo-wide claims into trusted state, violating the spec §Opaque Memory Mutation risk control.

## Steps

1. Read spec §Consolidation Engine "Consolidation modes" and §Human Review Surface "Required operator views" lists. Copy the scope-gating rule into the top-of-file doc comment on `review_queue.rs`.
2. In `consolidation/review_queue.rs`, define `pub struct ReviewQueue { /* backed by consolidation_proposals where scope ∈ {repo, organization} */ }` with operations: `enqueue(proposal)`, `list_pending(workspace_id, filter) -> Vec<ReviewItem>`, `decide(proposal_id, decision: ProposalDecision, decided_by: OperatorId, reason: Option<String>)`, `inspect(proposal_id) -> ReviewItem` (full prior + proposed state for the UI).
3. Add a scope-gating hook in the T39 runtime: before enqueuing any proposal for execution, call `ReviewQueue::should_gate(proposal) -> bool` which returns `true` when the target memory's scope is `repo` or `organization`. Gated proposals skip the deterministic auto-apply path and stay `pending` in `consolidation_proposals` until `decide` is called.
4. Define `pub struct ReviewItem { proposal_id, job_id, kind, scope, target_memory_id, prior_state, proposed_state, evidence, provenance: Option<LlmProvenance>, enqueued_at }`. Implement `From<ConsolidationProposalRow>` so the existing table backs the queue without a parallel store.
5. Implement `decide`: it routes through the T39 `ConsolidationProposal::apply()` / `reject()` so the same audit path (event emission, prior-state preservation) applies. Record `decided_by` and `reason` in `consolidation_proposals.decision` / a new `decision_reason TEXT NULL` column (migration in this task).
6. Add `list_pending` filters: `scope`, `kind`, `older_than`, `workspace_id`. Return results ordered by `enqueued_at ASC` so the oldest pending items surface first in the inbox.
7. Expose a thin internal API on `ReviewQueue` so the Phase 10 review-UI plumbing can call it via JSON-RPC without re-implementing the gating logic. Cite the §Human Review Surface heading in the API doc comment so the boundary is explicit.
8. In `consolidation/review_queue_tests.rs`, write tests that: (a) a `session`-scope proposal is NOT gated and proceeds to auto-apply, (b) a `branch`-scope proposal is NOT gated, (c) a `repo`-scope proposal IS gated and stays `pending`, (d) an `organization`-scope proposal IS gated and stays `pending`, (e) `decide(apply, operator_id, reason)` routes through `ConsolidationProposal::apply()` and emits `MemoryConsolidated` with the `decided_by` recorded, (f) `decide(reject, operator_id, reason)` leaves memory unchanged and records the rejection, (g) `list_pending` returns items in `enqueued_at ASC` order and honors filters, (h) calling `decide` twice on the same proposal is a no-op on the second call (idempotent), (i) the migration adds `decision_reason` and the schema round-trips.

## Coding-standard checks

- File length ≤800 lines per file.
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10. `decide` is a guard + dispatch (apply or reject) + record.
- Single source of truth: gating decision lives in `ReviewQueue::should_gate`; apply/reject route through the T39 `ConsolidationProposal` API. No parallel write paths.
- Error handling: typed `ReviewQueueError` (proposal not found, already decided, scope mismatch). No bare `unwrap`; no silent `.ok()`. Decision-on-non-pending is a typed `AlreadyDecided` outcome, not an error.
- Naming: `ReviewQueue`, `ReviewItem`, `should_gate`, `decided_by`. No `Manager`/`Helper`.
- Schema parity: `decision_reason` column maps to `Option<String>` on `ReviewItem` and `ConsolidationProposal`; migration covers up direction.
- No `TODO`, `FIXME`, `XXX`, commented-out code, or unjustified `#[allow(...)]`.
- Observability: every `decide` call emits a `tracing::info_span!("manual_review_decision", proposal_id, scope, decision, decided_by)` and writes the appropriate event through the existing event writer.
- Doc citation: file-top doc comment cites `## 6. Consolidation Engine` "Consolidation modes" and `## 10. Human Review Surface` "Required operator views" (per `lattice/CLAUDE.md` § Markdown Heading References).
