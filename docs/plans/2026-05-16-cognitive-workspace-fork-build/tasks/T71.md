## Goal

This task lays the foundation for the entire Phase 10 review surface. It registers a new VS Code webview view under the existing `viewsContainers.activitybar.lattice` slot in `extension/package.json`, wires a typed JSON-RPC bridge that translates the new memory/event/verification tool responses into UI state, and bootstraps the i18n catalog that every later subview (T72–T76) depends on. Without this scaffolding, the memory inbox, promotion queue, contradiction queue, stale view, event trace view, retrieval explanation view, consolidation queue, indexing health, and graph health subviews have no parent panel, no transport, and no string catalog. Spec §10 names the surface explicitly: "This can be a VS Code extension panel or local web UI. It should be a review and trust surface, not the center of the product." This task delivers that panel skeleton.

## Steps

1. Read spec §10 Human Review Surface and §Phase 10 deliverables in full so the panel scope (eleven operator views) is explicit before writing any code.
2. Open `extension/package.json` and add a new view contribution under `contributes.views."lattice"` named `lattice.reviewPanel` with `type: "webview"`, an explicit title, and an icon path. Keep the existing `lattice.sidebar` view intact so the existing surface continues to function (per `AGENTS.md` backward-compatibility discipline).
3. Add a command contribution `lattice.openReviewPanel` that focuses the new view, and bind it to the activity-bar group so the operator can launch the panel from the existing Lattice container.
4. Create `extension/src/review/reviewPanel.ts` exporting a `ReviewPanelProvider` class implementing `vscode.WebviewViewProvider`. The provider owns the webview lifecycle (resolve, dispose), sets up CSP headers, and bootstraps the subview router that T72–T76 plug their views into. Set `enableScripts: true`, `localResourceRoots` restricted to the extension's `media/` and `out/` directories.
5. Create `extension/src/review/rpcBridge.ts` exporting a typed `ReviewRpcBridge` class wrapping the existing `daemon.ts` client. Expose typed methods for the new tools introduced in Phases 6–9 (memory inbox listing, promotion queue, contradiction queue, stale memory, evidence inspection, event trace, retrieval explanation, consolidation queue, indexing health, graph health). Every method returns a `Promise<Result>` shape with explicit error variants — never swallow errors (`coding.md` §Error handling).
6. Each `ReviewRpcBridge` method handler wraps its call in `try/catch` and surfaces failures via `vscode.window.showErrorMessage(err.message)` (the VS Code analogue of `parseApiError + toast.error` since `parseApiError` does not apply outside the Cadres web portal). Where a mutation result is also rendered into the webview, the bridge also posts a `{ type: 'error', message }` event to the webview so the subview can render an inline error state.
7. Create `extension/src/review/i18n/en.json` with namespaced keys for every user-facing string the panel scaffolding emits today (panel title, "loading", "no items", "error loading data", retry label, "unverified"/"verified"/"in_review"/"stale"/"contradicted"/"superseded"/"expired"/"invalidated" status labels, accept/reject action labels). Provide a tiny `i18n.t(key, params?)` helper at `extension/src/review/i18n/index.ts` that reads from the catalog at module load. ICU placeholders only — never string concatenation (per `ui-specification.md` §14).
8. Register `ReviewPanelProvider` from `extension/src/extension.ts` during activation, using `vscode.window.registerWebviewViewProvider('lattice.reviewPanel', provider)`. Wire the `lattice.openReviewPanel` command to `vscode.commands.executeCommand('lattice.reviewPanel.focus')`.
9. Run `cd extension && npm install && npm run compile && npm run lint` and fix every error and warning before stopping. Confirm the new view shows up in the existing Lattice activity bar container without disturbing the existing sidebar.

## Coding-standard checks

- File length ≤800 lines per file (`wc -l extension/src/review/reviewPanel.ts extension/src/review/rpcBridge.ts`).
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10. Webview message-handler dispatch uses a table-driven switch, not nested ifs.
- Single source of truth: the new RPC bridge is the only path the review subviews use to talk to the daemon; existing `daemon.ts` is wrapped, never duplicated.
- No `TODO`, `FIXME`, `XXX`, commented-out code, or unjustified `// eslint-disable`.
- No silent error handling — every `await` either bubbles via `try/catch` to `vscode.window.showErrorMessage` or returns a typed `Result`.
- Doc citation: code comments that explain panel scope cite `## 10. Human Review Surface` from the plan doc (per `lattice/CLAUDE.md` Markdown Heading References).

### UI specification

- All user-facing strings via `i18n.t(...)` (loaded from `extension/src/review/i18n/en.json`); no inline English literals in `reviewPanel.ts`, `rpcBridge.ts`, or the webview HTML this scaffolding emits.
- All modals via native `<dialog>` (per `ui-specification.md` §7); no `window.confirm`, `window.prompt`, `window.alert`, or any imperative dialog API in the scaffolding or anywhere the subviews mount through it.
- All mutation handlers use `try/catch`. Because this is a VS Code extension (not the Cadres web portal), the canonical Cadres `parseApiError(e) + toast.error(...)` pair does not apply directly — instead, every catch surfaces the error via `vscode.window.showErrorMessage(err.message)`, mirroring the same "never swallow, always surface" intent from `ui-specification.md` §8.5.
- All ID inputs use `SearchableSelect` where applicable to webview UI. For VS Code tree-view interactions (e.g. picking a workspace, branch, memory class), use `vscode.window.showQuickPick` with typed entries — never raw `<select>` or `prompt`-based ID entry.
- Sortable tables use `SortableHeader` + `useTableSort` patterns where applicable. The scaffolding itself does not render a table; T72 onwards do, but the panel must expose hooks/utilities so subviews mount their tables with consistent sort state.
- Status badges + loading + empty + error states for every interactive surface. The scaffolding ships baseline component primitives (status-badge stub, loading skeleton stub, empty-state stub, error banner) used by all subviews; every subview built on top must render the appropriate state.
