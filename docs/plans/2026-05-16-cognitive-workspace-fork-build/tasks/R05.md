## Purpose

This review certifies that Phase 0 has produced an evidence-backed fork/extend decision, a complete architecture overview, a binding crate boundary plan and migration policy, and a runnable baseline benchmark suite. It is the gate that all Phase 1+ tasks depend on; passing it means later phases can rely on a fixed substrate vocabulary and an objective regression baseline.

## Review procedure

1. Open `docs/architecture/2026-05-16-fork-or-extend-decision.md` and verify it evaluates all four spec gate conditions with explicit `met`/`unmet` verdicts citing files and lines; verify a branch or repo name is committed under the `## Branch or repo name` heading.
2. Open `docs/architecture/2026-05-16-cognitive-workspace-architecture.md` and verify it contains `## Workspace graph`, `## Event log`, and `## Memory graph` sections; spot-check that each enumerates the node/edge/event/memory families from spec §System Architecture rather than paraphrasing.
3. Open `docs/architecture/2026-05-16-mcp-compatibility-policy.md` and verify every existing MCP tool (cross-check against `daemon/crates/lattice-daemon/src/rpc/mcp.rs` registrations) has a classification of `stable`, `additive`, `redesigned-with-shim`, or `deprecated-with-deadline`. Verify the `## Backward compatibility` section states the binding rule.
4. Open `docs/architecture/2026-05-16-crate-boundary-plan.md` and verify all seven new substrates (identity, events, memory, retrieval, working-memory, consolidation, verification) are present by literal grep, each with a layout decision and rationale.
5. Open `docs/architecture/2026-05-16-storage-migration-policy.md` and verify `## Migration order` enumerates Phase 1 through Phase 7 schema introductions in chronological order, and `## Rollback` lists an inverse operation per migration.
6. Open `daemon/crates/lattice-core/benches/baseline_workflows.rs` and verify benches exist for `prepare_change`, `get_context_capsule`, `expand_context`, `impact_from_diff`, `diagnose_failure`, `search_symbols`, and `find_relevant_tests`. Run `cd daemon && cargo bench --bench baseline_workflows -- --warm-up-time 1 --measurement-time 3` and confirm `baseline_metrics.json` is regenerated.
7. Run `wc -l` on every file produced by Phase 0 to confirm none exceeds 800 lines.
8. Grep all Phase 0 artifacts for `TODO`, `FIXME`, `XXX`, and commented-out code blocks; flag any hit as a finding.
9. Cross-check that doc citations use exact `## Heading` references (per `lattice/CLAUDE.md` § Markdown Heading References) and not vague "see the spec" prose.

## Required sections in the review output file

The reviewer writes to `docs/plans/2026-05-16-cognitive-workspace-fork-build/reviews/R05-foundation.md` with these mandatory headings (each must contain real findings, not "n/a"):

- `## Spec alignment` — phase-by-phase coverage matrix for Phase 0 deliverables: fork decision, architecture docs, crate/module plan, storage migration policy, compatibility policy, baseline benchmarks. One row per deliverable, evidence column citing the artifact and heading.
- `## Coding-standard alignment` — line-by-line audit vs. hard limits: file length (`wc -l` results per file), forbidden tokens grep, suppression audit, naming audit on the bench function names.
- `## Findings` — issues found, severity (`blocker`, `major`, `minor`), suggested follow-up tasks. Follow-up tasks must be opened in this build (do not defer outside).
- `## Verdict` — `PASS`, `PASS-WITH-FOLLOWUP-TASK-Txx`, or `BLOCK` (with named blockers).
