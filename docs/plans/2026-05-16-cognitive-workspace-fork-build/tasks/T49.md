**Phase:** 7

**Standards:** Cadres coding standard; Lattice project rules (`/home/pete/cadres/lattice/CLAUDE.md`, `AGENTS.md`).

## Goal

This task implements the second verification check from spec §Verification Engine: when a memory's evidence captured an exact text span (a byte range or `(start_line, end_line)`) at the time of creation, verification must confirm the current file content at that span still matches what was captured. If it does not, the verifier emits a `MarkStale` proposal (the assertion may still be true but the citation is stale) or `MarkInvalidated` (the evidence is gone). This is the difference between "the file still exists" (T48) and "what the memory said about the file is still backed by the same bytes." It is the load-bearing mechanism for the spec's §Stale Memory Leakage risk control.

## Steps

1. Read spec §Verification Engine "Verification checks" list. Copy the span-validation bullet verbatim into the top-of-file doc comment on `verification/spans.rs`.
2. Define `pub struct EvidenceSpan { file_id: FileId, byte_start: u32, byte_end: u32, line_start: u32, line_end: u32 }` (mirror the Phase 3 column shape) and `pub enum SpanMismatch { ContentChanged, FileShrunkBelowSpan, EncodingChanged, FileMissing }`.
3. In `verification/spans.rs`, implement `SpanValidator::validate(evidence: &MemoryEvidence, current_file_bytes: &[u8]) -> VerificationVerdict`. Algorithm: (a) if `evidence.span` is `None`, return `Verified` (this check is no-op for evidence without an exact span — the existence check from T48 already covered the file), (b) if `byte_end > current_file_bytes.len()`, return `VerificationVerdict { status: Stale, reason: "FileShrunkBelowSpan" }`, (c) compute SHA-256 of `current_file_bytes[byte_start..byte_end]` and compare to `evidence.evidence_content_hash`; equal → `Verified`, unequal → `Stale { reason: ContentChanged }`, (d) handle encoding-mismatch (BOM appearance/removal, CRLF/LF flip) explicitly by recording `EncodingChanged` so the surfacing layer in T52 can distinguish noise from substantive change.
4. Wire `SpanValidator` into `VerifierCore::verify_memory` (T48): after existence checks pass, run span validation on every evidence row that has a span. Aggregate verdicts so the final memory status downgrades to `stale` if any span mismatches but no anchor is missing.
5. Provide a streaming read path: do NOT read the whole file when only a small span needs verifying. Use the existing storage layer's `read_range(file_id, start, end)` (or add one if absent, in the same task) so verification stays cheap on large files.
6. Persist span-mismatch details: extend the verification-jobs `reason` column to carry a structured JSON payload `{ "kind": "SpanMismatch", "subkind": "ContentChanged" | "FileShrunkBelowSpan" | "EncodingChanged" | "FileMissing", "evidence_id": <id> }` so the Phase 10 inbox UI can render the exact reason.
7. Emit the verdict as a `MarkStale` proposal through the T39 runtime (never direct memory writes), carrying the structured reason payload.
8. In `verification/spans_tests.rs`, write tests that: (a) unchanged content at the span returns `Verified`, (b) modified content at the span returns `Stale { ContentChanged }`, (c) file truncated below `byte_end` returns `Stale { FileShrunkBelowSpan }`, (d) CRLF↔LF flip is reported as `EncodingChanged`, not `ContentChanged`, (e) evidence with `span = None` returns `Verified` (no-op), (f) span validation never reads the whole file (assert via a tracing-instrumented mock storage that counts bytes read).

## Coding-standard checks

- File length ≤800 lines per file.
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10. `SpanValidator::validate` is a guard cascade — keep it flat.
- Single source of truth: span validation routes through `VerifierCore` (T48) and emits proposals through T39; no parallel memory writes; range reads go through the existing storage layer.
- Error handling: typed `SpanValidationError` for I/O or hash failures. No bare `unwrap`. A missing file is a typed `SpanMismatch::FileMissing` verdict, not an error.
- Naming: `SpanValidator::validate`, `EvidenceSpan`, `SpanMismatch::ContentChanged`. No `Manager`/`Helper`.
- Schema parity: structured-reason JSON has matching Rust types so serde round-trips losslessly.
- No `TODO`, `FIXME`, `XXX`, commented-out code, or unjustified `#[allow(...)]`.
- Observability: every span-validation call emits a `tracing::debug_span!("validate_span", memory_id, file_id, byte_start, byte_end, verdict)`.
- Doc citation: file-top doc comment cites `## 8. Verification Engine` "evidence text still matches when exact spans were captured" and the §Non-Negotiable Product Properties bullet on stale surfacing (per `lattice/CLAUDE.md` § Markdown Heading References).
