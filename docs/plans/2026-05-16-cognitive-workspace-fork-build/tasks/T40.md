# T40 — Phase 6 — Synchronous session consolidation (episode summaries)

**Phase:** 6
**Type:** backend
**Model class:** balanced
**Depends on:** T39
**Spec anchor:** [§Consolidation Engine](../../2026-05-16-cognitive-workspace-fork-plan.md#6-consolidation-engine), [§Phase 6: Consolidation Engine](../../2026-05-16-cognitive-workspace-fork-plan.md#phase-6-consolidation-engine)
**Standards:** Cadres coding standard; Lattice project rules (`/home/pete/cadres/lattice/CLAUDE.md`, `AGENTS.md`).

## Goal

This task adds the `synchronous post-task consolidation` mode from spec §Consolidation Engine. It runs only on small task traces immediately after a workflow concludes, producing an episode-summary proposal that links the task's event slice to a new or updated episode memory. It must NOT run on the hot path: spec §Phase 2 DoD pins event writes at ≤5ms P99 on `prepare_change` / `get_context_capsule`, and the consolidation engine §LLM-driven block forbids LLM inference on the synchronous post-task hot path. The session consolidator therefore uses the deterministic episode template only; LLM-driven episode generation lives in T42.

## Spec excerpts that drive this task

> "Consolidation modes: synchronous post-task consolidation for small task traces; background scheduled consolidation for larger histories; manual review mode for high-impact repo or organization memories; replay mode for rebuilding memory state from the event log."

> "Consolidation jobs: create episode summaries from completed tasks ..."

> "LLM-driven jobs run only in background or manual review modes, never on the synchronous post-task hot path."

> Phase 2 DoD: "event write ≤5ms P99 on `prepare_change` / `get_context_capsule`" — synchronous consolidation must respect the same hot-path discipline.

## Steps

1. Read spec §Consolidation Engine "Consolidation modes" and §Phase 6 DoD. Copy the synchronous-mode definition into the top-of-file doc comment on `session.rs`.
2. In `consolidation/episode.rs`, define `EpisodeTemplate` — the deterministic shape of an episode summary: `task_id`, `session_id`, `outcome` (success/failure/abandoned), `event_window: Range<EventId>`, `salient_anchors: Vec<StableRef>` (files, symbols, docs touched), `tools_used: Vec<ToolName>`, `summary_text` (deterministic template like `"Task {task_id}: {n} tools, {n} files, outcome={outcome}"`). No LLM call. Implement `EpisodeTemplate::from_task_slice(events: &[EventEnvelope]) -> Result<EpisodeTemplate, EpisodeError>`.
3. In `consolidation/session.rs`, implement `SessionConsolidator::on_task_complete(workspace_id, task_id, outcome)`. Steps: (a) fetch the task's event slice via the event reader using `task_id`-indexed lookup, (b) reject slices over the `synchronous_max_events` ceiling (configurable, default 200) by enqueuing the work into `background` mode instead, (c) build an `EpisodeTemplate`, (d) construct a `CreateMemory` or `UpdateMemory` proposal through the T39 runtime carrying the template's fields as `proposed_state`, (e) return immediately — apply/reject is the operator's call.
4. Enforce the hot-path budget: wrap `on_task_complete` in a `tracing::info_span!` with elapsed-time recording and a `debug_assert!` for ≤5ms P99 in tests. The body must short-circuit if the slice exceeds the ceiling so the operation cannot grow unbounded.
5. Wire `SessionConsolidator` into the workflow-outcome path (the daemon's existing `record_workflow_outcome` handler) so it fires once per completed task — but never blocks the response.
6. Forbid LLM imports: this module must not depend on any `consolidation::llm::*` symbol. Add a crate-level compile assertion (a `#[cfg(test)]` test that uses `cargo metadata` or a string-grep guard test against this file's source) so future edits cannot silently introduce an LLM call here.
7. In `consolidation/session_tests.rs`, write tests that: (a) a 3-event task slice produces a `CreateMemory` proposal with a deterministic summary, (b) a slice of 250 events is redirected to background mode rather than processed synchronously, (c) the runtime never mutates `memories` directly (assert via store telemetry), (d) elapsed time per call stays well under the 5ms budget on a benchmark fixture, (e) the LLM-forbid guard test fails if a `consolidation::llm` symbol is referenced from this module.

## Coding-standard checks

- File length ≤800 lines per file.
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10. `on_task_complete` is a flat sequence: guard, fetch, template, propose, return.
- Single source of truth: episode shape lives in `episode.rs`; do not redefine the template in `session.rs`. Reuse the T39 proposal API; do not duplicate the `ConsolidationProposal` write path.
- Error handling: `EpisodeError` is a typed enum (missing task slice, ceiling exceeded, store unavailable). No bare `unwrap`; no swallowed `Result`s. Ceiling exceedance is normal control flow (returns a `Redirected` outcome) not an error.
- Naming: `SessionConsolidator`, `EpisodeTemplate`, `on_task_complete`, `synchronous_max_events`. No `Helper` / `Manager` / generic `data`.
- No `TODO`, `FIXME`, `XXX`, commented-out code, or unjustified `#[allow(...)]`.
- Observability: `tracing::info_span!("session_consolidation", workspace_id, task_id, slice_len)` around every call; elapsed time recorded on span exit.
- Doc citation: file-top doc comments cite `## 6. Consolidation Engine` "Consolidation modes" and `## Phase 2: Event Log Substrate` DoD for the hot-path budget (per `lattice/CLAUDE.md` § Markdown Heading References).
