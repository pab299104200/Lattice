## Goal

This task delivers the three operations-focused subviews of the review panel: the consolidation queue (background and manual-review consolidation jobs with depth/state visibility), the indexing health view (ingestion pipeline state, parser failures, vector index freshness), and the workspace graph health view (node/edge counts per family, broken-link detection, stale-edge detection). These views are how operators answer "is the daemon healthy and is its substrate trustworthy?" — without them, only the daemon-side logs show whether consolidation is keeping up, whether parsing is failing silently, or whether the graph has degenerated. Spec §10 names all three explicitly; this task delivers the last three of the eleven required operator views, completing the Phase 10 view set before smoke tests (T77).

## Spec excerpts that drive this task

> "Required operator views: ... usefulness metrics; workspace graph health; indexing health; consolidation queue." (spec §10)

> "Consolidation queue depth must be bounded; when the queue is full, new jobs are dropped with a log warning rather than stalling the daemon." (spec §6 — drives the queue-depth indicator and dropped-job count.)

> "The graph must support exact identity lookup, bounded neighborhood traversal, impact queries, doc/code backlinks, and freshness queries." (spec §2 — drives the freshness/staleness counters in the graph health view.)

## Steps

1. Read spec §6 Consolidation Engine (job types, modes, LLM-driven constraints, queue depth rule) and §2 Workspace Graph (node families, edge families, freshness queries) so the column sets are grounded in the spec.
2. Create `extension/src/review/consolidationQueueView.ts` exporting `mountConsolidationQueueView(host, bridge, i18n)`. Render a sortable, paginated table with columns: `Status` badge, `Kind` (episode summary, procedure extraction, contradiction detection, failure-pattern extraction, duplicate detection, supersession proposal, etc. per spec §6), `Mode` (synchronous / background / manual-review / replay per spec §6 consolidation modes), `Created At`, `Started At`, `Completed At`, `Duration`, `LLM Model` (where applicable), `Result Summary`, `Actions` (Inspect, Retry).
3. Above the table render a queue-depth indicator showing current depth vs the documented bound, plus a count of jobs `dropped` due to queue full (per spec §6 "queue depth must be bounded"). When the dropped count is non-zero, render a warning banner with the count and a link to the event trace view (T75) filtered to `MemoryConsolidated` and consolidation-failure events.
4. Filter bar: `Status` (multi-select), `Kind` (multi-select), `Mode` (multi-select), all via `vscode.window.showQuickPick`.
5. Create `extension/src/review/indexingHealthView.ts` exporting `mountIndexingHealthView(host, bridge, i18n)`. Render a panel layout with sections:
   - Ingestion pipeline status: per-language parser status (count of files parsed, count failed, last error), watcher status, last full-rescan timestamp.
   - Vector index health: total embeddings, last rebuild timestamp, average freshness, count of stale embeddings.
   - FTS index health: row count per FTS table, last rebuild, count of orphan rows.
   - Event log health: events ingested last hour / 24h / 7d, last compaction snapshot timestamp (per spec §Storage Design event-log compaction), event-payload-spillover row count.
   - Each section ends with a refresh button that calls the relevant bridge method.
6. Create `extension/src/review/workspaceGraphHealthView.ts` exporting `mountWorkspaceGraphHealthView(host, bridge, i18n)`. Render per-node-family counts and per-edge-family counts (all node and edge families from spec §2) in tables, plus three diagnostic panels: `Broken references` (edges pointing to non-existent identities), `Stale edges` (edges whose `stale_against` flag is set per spec §2 edge families), and `Orphan symbols` (symbols not referenced by any file). Each panel has a `Recompute` button that triggers a re-verification.
7. Cross-link: clicking a failed consolidation job opens the event trace view (T75) filtered to the related task/session; clicking a broken-reference row opens the file or symbol via `vscode.commands.executeCommand('vscode.open', uri)`; clicking a stale-edge row opens the evidence inspector (T74) for the related memory if one exists.
8. Add i18n keys under `consolidationQueueView`, `indexingHealthView`, and `workspaceGraphHealthView` namespaces: every column header, status/kind/mode label, panel title, action label, success/error string, loading hint, empty state.
9. Wrap every bridge call in `try/catch` and surface failure both inline and via `vscode.window.showErrorMessage`.
10. Run `cd extension && npm run compile && npm run lint` and fix every error/warning before stopping.

## Coding-standard checks

- File length ≤800 lines per file. If a view grows beyond, split per panel.
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10. Panel renderers are table-driven over the documented node/edge/job-kind sets.
- Single source of truth: job-status badge from T72; node/edge family enumerations live in one place referenced by both the daemon contract and the i18n catalog.
- No `TODO`, `FIXME`, `XXX`, commented-out code, or unjustified `// eslint-disable`.
- No silent error handling — every bridge call surfaces failure inline + via `vscode.window.showErrorMessage`.
- Doc citation: comments cite `## 6. Consolidation Engine` for the queue-depth and dropped-job rule and `## 2. Workspace Graph` for the node/edge family set (per `lattice/CLAUDE.md` Markdown Heading References).

### UI specification

- All user-facing strings via `i18n.t(...)` from the three namespaces; no inline literals in any of the three files.
- All modals via native `<dialog>` — these views are mostly panels; the "Retry job" confirmation uses a native `<dialog>` or routes through `vscode.window.showInformationMessage` with explicit actions. Never `window.confirm/prompt/alert`.
- All mutation handlers (Retry, Recompute, refresh) use `try/catch` with `vscode.window.showErrorMessage(err.message)` (`parseApiError + toast.error` is the Cadres web equivalent; for VS Code, the analogue is the error toast).
- All ID inputs use `SearchableSelect` (webview) or `vscode.window.showQuickPick` (tree-view) — every filter picker uses `showQuickPick`. Never raw `<select>` or `prompt`-based ID entry.
- Sortable tables use `SortableHeader` + `useTableSort` equivalents on the consolidation queue (sortable on `Status`, `Kind`, `Mode`, `Created At`, `Duration`), per-family counts in graph health (sortable on `Family`, `Count`), and broken-refs / stale-edges / orphan-symbols panels (sortable on `Identity`, `Reason`). Pagination required on every list per `ui-specification.md` §6.1.
- Status badges + loading + empty + error states for every interactive surface: badges for every job status; loading skeleton on first load and per-section spinner on refresh; distinct empty states for healthy ("No queued consolidation jobs.", "Indexing pipeline is up to date.", "No broken references.") vs filtered ("No jobs match the current filters."); warning banner when queue-depth bound is hit; error banner inline + VS Code toast on failure.
