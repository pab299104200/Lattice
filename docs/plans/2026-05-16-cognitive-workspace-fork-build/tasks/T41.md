**Phase:** 6
**Type:** backend
**Model class:** balanced

**Spec anchor:** [§Consolidation Engine](../../2026-05-16-cognitive-workspace-fork-plan.md#6-consolidation-engine), [§Phase 6: Consolidation Engine](../../2026-05-16-cognitive-workspace-fork-plan.md#phase-6-consolidation-engine)
**Standards:** Cadres coding standard; Lattice project rules (`/home/pete/cadres/lattice/CLAUDE.md`, `AGENTS.md`).

## Goal

This task implements the deterministic consolidation jobs spec §Consolidation Engine names verbatim: duplicate detection, supersession-candidate proposals, demotion of unused/low-value memories, marking memories stale after graph changes, and refreshing memories whose evidence still matches. These jobs do not require LLM inference — they are computed entirely from the workspace graph, the memory graph, and `memory_accesses` / `memory_scores` from Phase 3. Each job MUST route through the T39 proposal runtime (no silent writes) and MUST run cheaply enough to be invoked from background scheduling without blocking. Together these jobs supply the "self-cleaning" half of consolidation that has to be online before the LLM-driven jobs (T42) layer on.

## Spec excerpts that drive this task

> "Consolidation jobs: ... detect duplicate memories; detect contradictions; detect supersession candidates; demote unused or low-value memories; mark stale memories after graph changes; refresh memories whose evidence still matches current code ..."

> Phase 6 DoD: "consolidation is auditable, reversible, and test-covered".

## Steps

1. Read spec §Consolidation Engine "Consolidation jobs" list. Copy the verbatim names into module doc comments so each file states which spec bullet it implements.
2. In `consolidation/duplicates.rs`, implement `DuplicateDetector::scan(workspace_id, kind_filter)` that buckets memories of the same `MemoryClass` and scope, computes pairwise vector similarity above a configurable threshold (default 0.92), confirms typed-evidence overlap (shared `FileId`/`SymbolId`), and emits an `UpdateMemory` or `Supersede` proposal pairing the older memory as supersedee of the newer when both carry compatible assertions, or a `Demote` proposal when both look stale. The detector must run in O(n log n) using vector-index nearest-neighbor queries, never full pairwise.
3. In `consolidation/supersession.rs`, implement `SupersessionCandidates::scan(workspace_id)` that finds memories whose evidence has been replaced by newer memories on overlapping anchors. Emit a `Supersede` proposal: `prior_state` captures the older memory verbatim; `proposed_state` flips it to status `superseded` with a link back to the newer memory in the `memory_links` table.
4. In `consolidation/demotion.rs`, implement `DemotionScanner::scan(workspace_id, cutoff)` that queries `memory_accesses` for memories with `access_count == 0` since `cutoff` AND `memory_scores.usefulness < demotion_threshold`. Emit a `Demote` proposal whose `proposed_state` lowers the memory's salience score and flips status to `unverified` if currently `verified`. Never delete: the spec invariant is reversibility.
5. Add `consolidation/stale_marker.rs` (extending `mod.rs`) implementing `StaleMarker::on_graph_change(changed_files: Vec<FileId>)`: for every memory whose evidence cites any changed file or contained symbol, emit a `MarkStale` proposal that flips `verification_status` to `stale` and records `staleness_reason` in `prior_state` vs `proposed_state`. Wire it into the indexer's "files-updated" hook so it fires on graph deltas.
6. Add `consolidation/refresh.rs` implementing `RefreshScanner::scan(workspace_id)`: for every memory whose evidence still resolves cleanly against the current graph AND whose `last_verified_at < refresh_interval`, emit a `Refresh` proposal whose `proposed_state` bumps `last_verified_at` to `now` without changing the assertion. This is the "refresh memories whose evidence still matches current code" spec bullet.
7. Each scanner exposes the same shape: `scan(...) -> ScanReport { proposals_enqueued: u32, skipped: u32, elapsed: Duration }`. Every proposal carries `prior_state` and `proposed_state` so apply/reject is reversible.
8. Register `mod duplicates; mod supersession; mod demotion; mod stale_marker; mod refresh;` in `consolidation/mod.rs`. No new SQL tables — these jobs reuse the T39 `consolidation_jobs`/`consolidation_proposals` schema.
9. In `consolidation/deterministic_tests.rs`, write per-scanner tests on a seeded memory fixture: (a) two near-duplicate memories produce a supersession proposal, (b) a memory whose anchor file was deleted produces a `MarkStale` proposal, (c) a never-accessed low-score memory produces a `Demote` proposal, (d) a memory whose evidence still matches produces a `Refresh` proposal, (e) every scanner is a no-op (zero proposals) on a fresh empty store, (f) every proposal carries `prior_state` and `proposed_state` and routes through the T39 runtime (assert no direct `memory.store.write(...)` calls — verify via a test seam that counts direct writes).

## Coding-standard checks

- File length ≤800 lines per file. If `duplicates.rs` approaches the ceiling, extract `duplicates/bucketing.rs` and `duplicates/scoring.rs`.
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10. Each scanner's `scan` method should be a top-level pipeline of small helpers (collect candidates → score → propose).
- Single source of truth: every proposal goes through the T39 runtime; do not re-implement proposal persistence here. Vector similarity routes through the existing embeddings module; do not introduce a parallel index.
- Error handling: typed `ScanError` per scanner; no bare `unwrap` or silent `.ok()`. Per-memory failures emit a `tracing::warn!` and continue scanning the rest — never abort the whole pass.
- Naming: `DuplicateDetector`, `SupersessionCandidates`, `DemotionScanner`, `StaleMarker`, `RefreshScanner`. No `Manager`/`Helper` suffixes.
- No `TODO`, `FIXME`, `XXX`, commented-out code, or unjustified `#[allow(...)]`.
- Observability: every scanner emits a `tracing::info_span!` with `workspace_id`, `kind`, `proposals_enqueued`, `elapsed_ms`.
- Doc citation: each scanner file cites the matching bullet from `## 6. Consolidation Engine` "Consolidation jobs" so the spec→code map is explicit (per `lattice/CLAUDE.md` § Markdown Heading References).
