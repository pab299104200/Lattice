## Goal

This task produces the binding fork-or-extend decision that every subsequent task in this build assumes. The spec gates Phase 0 on a "fork only if necessary" rule with four named gate conditions; this document evaluates each gate condition against current Lattice code evidence, names a branch or repo, and records the decision. The decision must precede any structural change because `depends_on` chains assume the layout, crate boundaries, and migration policy that this document selects. Without an explicit, evidence-backed decision, later phases would be free to silently diverge.

## Spec excerpts that drive this task

> "Phase 0 ends with an explicit fork/extend decision before any structural code changes begin. Fork if any of the following are true: the memory graph schema changes require breaking the existing `memories` table in a way that cannot be migrated without a full rebuild; the identity model requires changing the primary key or graph edge representation in a way that invalidates existing indexed data; the event log requires a new storage file or WAL mode incompatible with the current daemon's SQLite usage; two or more of the above apply and sharing a codebase would require sustained compatibility shims across all phases."

> "If none of those conditions hold, extend in place on a long-lived branch and skip the repo split. Document the decision and the evidence for it before Phase 1 begins."

## Steps

1. Read `docs/plans/2026-05-16-cognitive-workspace-fork-plan.md` §Phase 0 in full to internalize the gate conditions verbatim.
2. Inspect `daemon/crates/lattice-core/src/memory/storage.rs` and `daemon/crates/lattice-core/src/memory/schema.rs` (or equivalent) and enumerate every column on the `memories` table; record which Phase 3 fields are additive vs. breaking.
3. Inspect graph primary keys and edge representation in `daemon/crates/lattice-core/src/graph/`; determine whether the Phase 1 identity model invalidates existing indexes.
4. Inspect current SQLite connection setup in `daemon/crates/lattice-core/src/storage/` and confirm WAL/journal mode; determine whether a new `events.db` file can coexist without WAL incompatibility.
5. Evaluate each of the four gate conditions against the evidence and record a `met`/`unmet` verdict per condition with file/line citations.
6. State the decision (`extend on long-lived branch` or `fork to new repo`) and name the branch or repo (e.g. `feat/cognitive-workspace`).
7. Document the migration implication of the decision: which existing data must be preserved, which is rewritten, and the rollback path.
8. List every downstream task that the decision binds (T02 architecture overview, T03 crate boundaries, T04 baselines, all Phase 1 backend tasks).
9. Save the decision under `docs/architecture/2026-05-16-fork-or-extend-decision.md` with the mandatory headings checked by verification commands.
