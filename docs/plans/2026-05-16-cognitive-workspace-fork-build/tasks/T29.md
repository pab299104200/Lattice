## Goal

This task delivers pipeline steps 4 through 7 from spec §Retrieval Engine: gather candidate results from every source enumerated under "Candidate sources" — exact path/symbol lookup, code graph traversal, doc backlinks/outgoing links, FTS, embeddings, event similarity, memory links, workflow similarity, recent active working memory — and produce a unified `Candidate` stream the scorer (T30) can rank. Each candidate carries its source, the resolved anchor(s) that produced it, and a preliminary `inclusion_reason` string the shaper (T31) will refine. Hot-path budgets from spec §Phase 1/§Phase 2 still apply, so per-source retrieval is bounded by configurable caps and never performs unbounded traversal.

## Steps

1. Re-read spec §Retrieval Engine "Candidate sources" and "Pipeline" steps 4–7 in full; note the explicit ordering between exact lookup → graph traversal → docs → FTS/embeddings → events → memory links → workflow → working memory.
2. Define `Candidate { identity, source, seed_anchor, raw_score, preliminary_inclusion_reason, expansion_handle_hint }` in `candidates.rs`. The `source` variant enumerates exactly the nine spec-named sources; no additional sources sneak in without spec amendment.
3. Implement one async retriever per source as a small dedicated function (≤50 lines each), gated by a per-source budget cap drawn from a `RetrievalBudget` struct (max candidates per source, max graph hops, max FTS rows, embedding k, event window, working-memory window). Defaults must come from configuration, not literals scattered across functions.
4. Compose the retrievers in `retrieve_candidates(intent: &IntentClassification, anchors: &[ResolvedAnchor], budget: &RetrievalBudget, ctx: &RetrievalContext) -> Vec<Candidate>` so the orchestration is one place, parallel via `tokio::join!` where safe, and short-circuits when intent disqualifies a source (e.g. `update_docs` skips event similarity unless explicitly requested).
5. Wire bounded graph expansion (spec pipeline step 7) through the existing graph-traversal API — never call `petgraph` directly here. Expansion radius is `min(intent_default, budget.max_graph_hops)` and every traversal must record the path that produced the candidate (used by T30 graph-proximity scoring and by T31's expansion handle).
6. Hot-path discipline: log the candidate count per source and total elapsed time at `debug` (never `info` on hot paths). Assert in debug builds that no single retriever exceeded its budget cap; in release builds, truncate with a `BudgetExhausted` flag on the candidate set so the scorer/shaper can surface it.
7. Add `daemon/crates/lattice-core/src/retrieval_v1/candidates_tests.rs` covering: each of the nine sources produces candidates for an appropriate seed; budgets are enforced (synthetic huge graph does not blow up); intent gating skips disqualified sources; bounded expansion records traversal paths; FTS, embeddings, and event similarity all participate when present; working-memory window returns the most-recent N items from the session context (interface stub acceptable here — T35 wires the real producer); empty anchor list still yields working-memory and event-similarity results when those exist.
8. Run `cd daemon && cargo build --release` and the verification test command; fix any clippy warnings before stopping.
