## Goal

This task delivers the stale-memory view and the evidence inspector, plus the on-demand verification trigger that calls the Phase 8 `verify_memory` tool. The stale view is the operator's lever to see every memory whose linked files, symbols, docs, or tests have drifted; the evidence inspector is the deep-dive surface for any single memory (used both from the inbox in T72 and the stale view here); and the verification trigger lets an operator re-run verification on demand instead of waiting for the background verifier. Together they implement the human-side control for spec §Stale Memory Leakage: "agents trust outdated memory; control: freshness indexes, graph-change-triggered verification, stale labels in all memory surfaces, and tests that stale memory cannot rank as trusted."

## Steps

1. Read spec §8 Verification Engine and §Stale Memory Leakage in full so the verification status taxonomy and the "stale label in all surfaces" requirement are grounded in the spec.
2. Create `extension/src/review/staleView.ts` exporting `mountStaleView(host, bridge, i18n)`. List every memory whose verification status is `stale`, `contradicted`, `superseded`, `expired`, or `invalidated` (per spec §8). Columns: `Status` badge, `Class`, `Scope`, `Content (truncated)`, `Stale Since`, `Stale Reason` (e.g. "linked symbol removed", "evidence span no longer matches", "branch scope drift"), `Actions` (Inspect Evidence, Re-verify).
3. Add filter controls for `Status` (multi-select over the five stale-family statuses) and `Scope` (multi-select). Filters route through `vscode.window.showQuickPick` (no raw `<select>`).
4. Create `extension/src/review/evidenceInspector.ts` exporting `mountEvidenceInspector(host, bridge, i18n, memoryId)`. The inspector is the deep-dive surface for one memory, mounted as a full-panel subview (not a modal — it carries too much content for a `<dialog>`). It renders:
   - Memory header: id, class, scope, status badge, confidence + reason.
   - Content panel: the memory's textual claim.
   - Evidence list: every `memory_evidence` row linked to this memory, with file/symbol/doc/test references that resolve to clickable `vscode.commands.executeCommand('vscode.open', uri)` links.
   - Provenance list: every event from the event log that touched this memory (created, updated, verified, invalidated, consolidated), with timestamp, actor, and link to the event trace view (T75).
   - Link list: every `memory_links` row (supports, contradicts, supersedes, refines, etc.) with link type, target, strength, and reason.
   - Verification panel: last verified at, last verification result, and a `Re-verify now` button.
5. Wire the `Re-verify now` button to call `bridge.verifyMemory(memoryId)`. Show a loading spinner on the button while the call is in flight; on success refresh the inspector and surface a `vscode.window.showInformationMessage('Verification complete: <new status>.')`; on failure render an inline error banner and call `vscode.window.showErrorMessage(err.message)`.
6. Stale view rows also expose a `Re-verify` action that calls `bridge.verifyMemory(memoryId)` without opening the inspector. Pattern is the same — loading state on the row, success refresh, failure surfaces both inline and via VS Code error toast.
7. Add i18n keys under `staleView` and `evidenceInspector` namespaces: column headers, action labels, stale-reason translation table (one key per documented reason from spec §8 verification checks), button labels, success/error strings, loading hint, empty state.
8. Cross-link: stale view row click navigates to the evidence inspector; evidence inspector "Open Trace" button navigates to the event trace view (T75). Use the subview router from T71's `ReviewPanelProvider`.
9. Wrap every bridge call in `try/catch` and surface failure both inline and via `vscode.window.showErrorMessage`.
10. Run `cd extension && npm run compile && npm run lint` and fix every error/warning before stopping.

### UI specification

- All user-facing strings via `i18n.t(...)` from the `staleView` and `evidenceInspector` namespaces; no inline literals in either file.
- All modals via native `<dialog>` — the evidence inspector is a panel, not a modal; if an inline confirm is needed (e.g. for a destructive re-verify on a high-scope memory), use `<dialog>` or `vscode.window.showInformationMessage` with explicit actions. Never `window.confirm/prompt/alert`.
- All mutation handlers (the re-verify trigger) use `try/catch` with `vscode.window.showErrorMessage(err.message)` (`parseApiError + toast.error` is the Cadres web equivalent; for VS Code, the analogue is the error toast).
- All ID inputs use `SearchableSelect` (webview) or `vscode.window.showQuickPick` (tree-view) — stale view filters use `showQuickPick`; cross-memory navigation from the inspector uses `showQuickPick` when picking from many. Never raw `<select>` or `prompt`-based ID entry.
- Sortable tables use `SortableHeader` + `useTableSort` equivalents on the stale view: sortable on `Status`, `Class`, `Scope`, `Stale Since`.
- Status badges + loading + empty + error states for every interactive surface: status badges via `StatusBadge.ts`; loading skeleton on first load and per-row spinner during re-verify; distinct empty states ("No stale memories. Verification is up to date." vs "No stale memories match the current filters."); error banner inline + VS Code toast on failure.
