## Goal

This task closes the spec's §Scope Leakage risk control: branch-scoped memory MUST NOT leak into unrelated branches, workspace-scoped memory MUST NOT leak across workspaces, and organization-scoped memory MUST NOT leak into workspaces that do not belong to that organization. The check is named verbatim in §Verification Engine's checks list. This is the source of authority for scope filtering — every retrieval, every workflow bundle, every consolidation proposal targeting a memory must obey it. Negative tests are non-negotiable: the spec's risk control names "negative tests" explicitly as part of the mitigation.

> Phase 7 DoD: "stale or contradicted memory cannot appear as normal trusted guidance" — scope-leaked memory is the worst possible "trusted guidance".

## Steps

1. Read spec §Verification Engine "Verification checks" + §Risks — Scope Leakage in full. Copy both verbatim into the top-of-file doc comment on `verification/scope_enforcement.rs`.
2. In `verification/scope_enforcement.rs`, define `pub struct ScopeFilter { workspace_id: WorkspaceId, branch: Option<BranchRef>, organization_id: Option<OrganizationId> }` and `pub fn allows(memory_scope: &MemoryScope, filter: &ScopeFilter) -> bool`. Rules: (a) `Session` scope matches only the session that owns it (rejects cross-session by default), (b) `Branch` scope matches only when the filter's `branch == memory.scope_branch`, (c) `Repo` scope matches only when `workspace_id == memory.scope_workspace_id`, (d) `Organization` scope matches only when `organization_id == memory.scope_organization_id`. Implement as guard cascade — never default-allow.
3. Implement `ScopeEnforcement::audit_memory(memory) -> VerificationVerdict`: load the memory's recorded scope and the workspace's current `(workspace_id, branch, organization_id)` triple, run the `allows` rule, and return `Verified` (scope holds) or `Invalidated { reason: "ScopeLeak" }` (scope is being read from a non-matching workspace). Emit through the T39 proposal runtime.
4. Wire `ScopeFilter` into the memory store at the API boundary: every `list_memories` / `get_memory` / `search_memory` call MUST accept a `ScopeFilter` argument and return only matching memories. Add a `cfg(debug_assertions)` invariant check that panics in debug builds if any returned memory fails `allows`, and a `tracing::error!` + filter-out in release builds (defense in depth).
5. Add an audit-trail event: when scope filtering drops a memory at the store boundary, emit a `MemoryScopeFiltered` event (extend the Phase 2 event-kind list via the existing migration discipline) carrying `memory_id`, `attempted_workspace_id`, `attempted_branch`, `memory_scope` so the operator can see leak attempts in the event log.
6. Add a top-level guard so retrieval (Phase 4) and consolidation (Phase 6) cannot bypass scope filtering by reading the store directly: mark the raw `MemoryStore::all_rows()` helper as `#[cfg(test)]` only and route every callsite through the filtered API.
7. Make the `ScopeFilter` type the canonical structure: every later phase (Phase 4 retrieval, Phase 8 workflow tools, Phase 10 UI) passes `ScopeFilter` into store calls; do not introduce overloaded `list_memories_for_branch` / `list_memories_for_org` variants.
8. In `verification/scope_leak_tests.rs`, write negative tests (required by spec): (a) a `Branch`-scope memory created on `feat/foo` does NOT appear when listed with a filter for `feat/bar`, (b) a `Repo`-scope memory from workspace A does NOT appear when listed with a filter for workspace B, (c) an `Organization`-scope memory does NOT appear when listed with a filter whose `organization_id` is `None` or different, (d) a `Session`-scope memory does NOT appear when listed from a different session, (e) `ScopeEnforcement::audit_memory` returns `Invalidated { reason: "ScopeLeak" }` for any leaked memory, (f) the debug-assertions guard fires when a test bypasses `ScopeFilter` and a leaked row is returned, (g) the `MemoryScopeFiltered` event is emitted for every drop at the store boundary.

## Coding-standard checks

- File length ≤800 lines per file.
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10. `allows` is a guard cascade with one match arm per scope.
- Single source of truth: `ScopeFilter` is the only canonical filter type; no parallel `list_memories_for_*` variants. The store API is the single enforcement point — retrieval, consolidation, and the workflow engine all go through it.
- Error handling: `ScopeFilterError` typed for missing-filter / contradictory-filter inputs. No bare `unwrap`. Leak detection is a typed `VerificationVerdict::Invalidated`, not a panic in release.
- Naming: `ScopeFilter`, `allows`, `audit_memory`, `MemoryScopeFiltered`. Booleans read as questions (e.g. `allows_memory(...)` rather than `check_memory_perm`).
- Schema parity: any new event payload column has a matching Rust field.
- No `TODO`, `FIXME`, `XXX`, commented-out code, or unjustified `#[allow(...)]`.
- Observability: every leak-detection drop emits a `tracing::warn!("scope_leak_blocked", memory_id, attempted_workspace_id, attempted_branch)` AND writes a `MemoryScopeFiltered` event.
- Doc citation: file-top comment cites `## 8. Verification Engine` "branch-scoped memory is not leaking" and `## Risks — Scope Leakage` (per `lattice/CLAUDE.md` § Markdown Heading References).
