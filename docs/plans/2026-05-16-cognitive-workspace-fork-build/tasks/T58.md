# T58 — Phase 8 — New memory tools: get_task_memory + save_memory + propose_memory_evolution(action=apply|reject)

**Phase:** 8
**Type:** backend
**Model class:** balanced
**Depends on:** R55
**Spec anchor:** [§MCP Surface](../../2026-05-16-cognitive-workspace-fork-plan.md#9-mcp-surface)
**Standards:** Cadres coding standard; Lattice project rules (`/home/pete/cadres/lattice/CLAUDE.md`, `AGENTS.md`).

## Goal

This task introduces three new memory-facing MCP tools required by spec §MCP Surface: `get_task_memory` (read working memory + relevant durable memory for the current task), `save_memory` (create a new durable memory record with evidence and validity conditions), and `propose_memory_evolution` (the unified successor to the spec's `propose_memory_evolution` + `apply_memory_evolution` pair, collapsed per spec §MCP Surface "Tool surface discipline" into a single tool with an `action` parameter accepting `propose | apply | reject`). The collapse is binding: spec §MCP Surface explicitly says "audit whether `propose_memory_evolution` + `apply_memory_evolution` can collapse into a single tool with an `action` parameter, and whether `verify_memory` + `explain_memory` can be unified. The goal is the smallest surface that covers all assistant workflows." Without the unified `propose_memory_evolution`, the new memory surface ships ten tools instead of the audited eight, increasing client cognitive load for no gain.

## Spec excerpts that drive this task

> "New or redesigned memory tools: `get_task_memory`, `save_memory`, `propose_memory_evolution`, `apply_memory_evolution`, `verify_memory`, `explain_memory`, `list_memory_conflicts`, `consolidate_session`, `get_memory_metrics`, `get_event_trace`."

> "Tool surface discipline: ten new memory tools is a meaningful cognitive load for clients. Before shipping Phase 8, audit whether `propose_memory_evolution` + `apply_memory_evolution` can collapse into a single tool with an `action` parameter, and whether `verify_memory` + `explain_memory` can be unified. The goal is the smallest surface that covers all assistant workflows. Consolidate before stabilizing the MCP contract." (spec §MCP Surface)

> "Each memory record requires: stable id, content, memory class, assertion type, scope, verification status, confidence and confidence reason, freshness policy, validity conditions, invalidation triggers, provenance events, evidence references, linked files, linked symbols, linked docs, linked tests, linked memories, contradiction links, supersession links, access history, usefulness scores, last verified state." (spec §Memory Graph)

> "Adopt the structure and link evolution. Do not adopt silent uncontrolled mutation. In this system, memory evolution should produce auditable proposals or transactional updates with provenance." (spec §A-Mem)

## Steps

1. Read spec §MCP Surface and §Memory Graph in full. Quote the "Tool surface discipline" paragraph verbatim into a doc comment on `memory_v2/mod.rs` so the rationale for collapsing `propose_memory_evolution` + `apply_memory_evolution` is preserved at the call site.
2. Create `daemon/crates/lattice-daemon/src/rpc/memory_v2/mod.rs` exporting the three tools and the shared request/response types (`TaskMemoryBundle`, `MemoryRecord`, `EvolutionProposal`, `EvolutionAction`).
3. Implement `get_task_memory` in `memory_v2/get_task_memory.rs`: take `task_id` (resolved through Phase 1 identity) plus optional `intent_hint` and `budget_tokens`; query the Phase 5 working-memory checkpoint for active context; query Phase 3 typed memory streams (`Observation`, `Decision`, `Constraint`, `Pattern`, `AntiPattern`, `WorkflowOutcome`, `FailurePattern`, `Procedure`, `Preference`, `ArchitectureInvariant`, `DocsContract`, `OpenQuestion`, `CounterMemory`) for relevant durable claims; rank via the Phase 4 scorer; return a compact `TaskMemoryBundle` where each entry carries inclusion reason, evidence strength, verification status, freshness status, contradiction/supersession state, scope, and an expansion handle per spec §MCP Tool Contract Principles "Every memory-bearing response should identify…".
4. Implement `save_memory` in `memory_v2/save_memory.rs`: accept all spec-required memory fields (`content`, `memory_class`, `assertion_type`, `scope`, `confidence`, `confidence_reason`, `freshness_policy`, `validity_conditions`, `invalidation_triggers`, evidence event refs, linked files/symbols/docs/tests). Validate scope-aware filters (spec §Risks "Scope Leakage"), default `verification_status = unverified`, persist via Phase 3 store, emit a `MemoryCreated` event via Phase 2 writer, enqueue a verification job per Phase 7, and return the created `MemoryId` plus the resulting `MemoryRecord`.
5. Implement `propose_memory_evolution` in `memory_v2/propose_memory_evolution.rs` as the unified tool with an `action: "propose" | "apply" | "reject"` parameter (collapsed per spec §MCP Surface "Tool surface discipline"). On `propose`, persist a proposal record referencing the source memory and the proposed delta (content change, link addition, supersession, invalidation) without altering durable memory; on `apply`, apply the proposal transactionally, emit `MemoryUpdated`/`MemoryConsolidated` events, and preserve prior state in `memory_evidence` per spec §Memory Graph "Memory evolution should produce auditable proposals or transactional updates with provenance"; on `reject`, mark the proposal rejected and emit a consolidation outcome event.
6. Every tool must emit the appropriate Phase 2 events (`MemoryRetrieved`, `MemoryCreated`, `MemoryUpdated`, `MemoryConsolidated`, `MemoryInvalidated`) and stay within the hot-path budget for the tools that participate in the hot path.
7. Register the three new tools in `daemon/crates/lattice-daemon/src/rpc/mcp.rs`. Per the T02 compatibility policy, the spec's nominal `apply_memory_evolution` name continues to respond as a deprecation shim that internally calls `propose_memory_evolution` with `action: "apply"`; the shim emits a deprecation warning in the response.
8. Scope-leak controls: every store query must include `scope` filters at the store layer (spec §Risks "Scope Leakage" requires "scope-aware queries, enforced filters in store APIs, and negative tests"). Reject any cross-scope leak with a typed error rather than silently returning empty.
9. In `memory_v2/memory_tools_tests.rs`, write tests that: (a) round-trip each tool's request/response through serde; (b) assert `get_task_memory` surfaces inclusion reason + verification status for every returned memory; (c) assert `save_memory` defaults `verification_status = unverified`, persists every spec field, emits a `MemoryCreated` event, and enqueues a verification job; (d) assert `propose_memory_evolution` with `action = propose` does NOT alter durable memory, `apply` updates transactionally with provenance preserved, `reject` records rejection; (e) assert scope-leak negative tests (a session-scoped query cannot return a branch-scoped memory created in a different branch); (f) assert the `apply_memory_evolution` shim continues to respond and forwards correctly.
