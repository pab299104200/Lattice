# T03 — Phase 0 — Crate/module boundary plan + storage migration policy

**Phase:** 0
**Type:** foundation
**Model class:** advanced
**Depends on:** T01, T02
**Spec anchor:** [§Phase 0: Fork Foundation](../../2026-05-16-cognitive-workspace-fork-plan.md#phase-0-fork-foundation)
**Standards:** Cadres coding standard; Lattice project rules (`/home/pete/cadres/lattice/CLAUDE.md`, `AGENTS.md`).

## Goal

This task fixes the crate layout and storage migration ordering before any Phase 1+ backend task writes code. It names the new crates (`lattice-identity`, `lattice-events`, `lattice-memory`, `lattice-retrieval`, `lattice-working-memory`, `lattice-consolidation`, `lattice-verification`) that will live under `daemon/crates/` (or documents the case for keeping each as a module inside `lattice-core` instead) and specifies the binding storage migration order plus rollback steps for every schema introduction in Phases 2 through 7. Without this contract, individual phase tasks would re-litigate boundaries and order, and migrations would be added in inconsistent ways.

## Steps

1. Read T01 and T02 outputs and re-read the spec sections §Storage Design and §Fork Strategy.
2. For each of the seven new substrates (identity, events, memory, retrieval, working-memory, consolidation, verification), pick one of two layouts: a separate crate under `daemon/crates/` named `lattice-<substrate>`, or a module inside `lattice-core`. Record the choice and the rationale (compile-time boundary, dependency cycles avoided, public-API stability).
3. In `2026-05-16-crate-boundary-plan.md`, write one section per crate or module with: name, purpose, public API surface, allowed dependencies (other lattice crates only), and the spec sections it implements.
4. Add a `## Dependency graph` section showing the directed acyclic dependency relationship between the new crates and `lattice-core` / `lattice-daemon`. No cycles permitted.
5. Add a `## Test boundary` section stating that each crate carries its own `tests.rs` modules under `src/` per Lattice convention (see `context.md` §2 "Tests").
6. In `2026-05-16-storage-migration-policy.md`, write a `## Migration order` section that enumerates every schema introduction in chronological phase order: Phase 1 identity tables, Phase 2 `events` + `event_payloads`, Phase 3 `memory_links` + `memory_evidence` + `memory_accesses` + `memory_scores`, Phase 5 `working_memory_checkpoints` + `context_handles`, Phase 6 `consolidation_jobs`, Phase 7 `verification_jobs`.
7. Add a `## Rollback` section that names, for every migration, the inverse operation, the data-loss class (none, archived, destructive), and the operator command to invoke rollback. Migrations that cannot be safely rolled back must be flagged explicitly.
8. Add a `## Compaction snapshot policy` subsection covering the daemon-managed background compaction described in spec §Storage Design (versioned format, independently readable, no manual trigger).
9. Cross-reference the architecture overview from T02 and the fork-or-extend decision from T01 at the top of both docs.
