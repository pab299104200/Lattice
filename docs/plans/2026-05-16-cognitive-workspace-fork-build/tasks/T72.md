## Goal

This task delivers the memory inbox — the operator's primary list view over every memory the daemon knows about. It mounts inside the review panel scaffolding from T71, lists memories with filterable columns (status, scope, class), and renders one status badge per row covering all eight verification states from spec §Verification Engine. The inbox is the entry point operators use to find the memory they want to verify, accept, reject, or inspect — without it, the promotion queue (T73), contradiction queue (T73), stale view (T74), and evidence inspector (T74) have nothing to link to. Spec §10 lists "memory inbox" first among the required operator views, which fixes its position as the spine of the review surface.

## Spec excerpts that drive this task

> "Required operator views: memory inbox; proposed promotions; proposed contradictions; stale memory list; memory evidence view; event trace view; retrieval explanation view; usefulness metrics; workspace graph health; indexing health; consolidation queue." (spec §10)

> "Verification outputs: `verified`; `unverified`; `in_review`; `stale`; `contradicted`; `superseded`; `expired`; `invalidated`." (spec §8 — every status the badge must render)

> "Each memory record requires: stable id; content; memory class; assertion type; scope: session, branch, repo, user, organization; verification status; confidence and confidence reason; freshness policy; ... last verified state." (spec §4 — drives the filter axes)

## Steps

1. Read spec §4 Memory Graph fields and §8 Verification Engine status set so the filter taxonomy and badge palette are grounded in the spec, not invented.
2. Create `extension/src/review/memoryInbox.ts` exporting a `mountMemoryInbox(host, bridge, i18n)` function that the review panel router calls when the operator opens the "Inbox" subview. The function returns a `dispose()` handle for clean teardown.
3. Build the inbox UI inside the webview as a sortable table with columns: `Status` (badge), `Class`, `Scope`, `Content (truncated)`, `Last Verified`, `Confidence`, `Actions` (View Evidence, Open Trace). Render the table via the table primitives exposed by T71's scaffolding; use the `SortableHeader` + `useTableSort` equivalents for the webview context.
4. Above the table render a filter bar with three controls: `Status` (multi-select over the eight statuses from §8), `Scope` (multi-select over `session`, `branch`, `repo`, `user`, `organization` from §4), `Class` (multi-select over the memory classes from §4 including `Observation`, `Decision`, `Constraint`, `Pattern`, `AntiPattern`, `WorkflowOutcome`, `FailurePattern`, `Procedure`, `Preference`, `ArchitectureInvariant`, `DocsContract`, `OpenQuestion`, `CounterMemory`). Each control is a `vscode.window.showQuickPick` invocation triggered from a button (no raw `<select>`); the chosen values post back to the webview which re-queries the bridge.
5. Create `extension/src/review/components/MemoryRow.ts` exporting `renderMemoryRow(memory, i18n)`. The function returns the DOM snippet for one row, encapsulating column formatting, truncation (per `ui-specification.md` §12.3), and `data-testid` attributes for telemetry. No business logic — pure rendering.
6. Create `extension/src/review/components/StatusBadge.ts` exporting `renderStatusBadge(status: VerificationStatus, i18n)`. Map each of the eight statuses to a DaisyUI-style semantic color (`badge-success`, `badge-warning`, `badge-error`, etc. — see `ui-specification.md` §11.1) plus an i18n label key. The badge palette is the only place this mapping lives — no inline color logic elsewhere in the review surface.
7. Add inbox-specific i18n keys to `extension/src/review/i18n/en.json` under a `memoryInbox` namespace: column headers, filter labels, empty-state message ("No memories match the current filters."), error-state message, loading skeleton hint, and per-status badge labels (already partly present from T71; reuse keys instead of forking).
8. Wire the row click handler to post a message back to `ReviewPanelProvider` requesting navigation to the evidence inspector (T74). Wire the "Open Trace" action to request navigation to the event trace view (T75).
9. Wrap every bridge call in `try/catch`. On error, render the inline error banner from T71 and call `vscode.window.showErrorMessage(err.message)` so the error is visible at both surfaces.
10. Run `cd extension && npm run compile && npm run lint` and resolve every error/warning before stopping.

### UI specification

- All user-facing strings via `i18n.t(...)` from the `memoryInbox` namespace in `en.json`; no inline English literals in any of the three files.
- All modals via native `<dialog>` — the inbox itself does not open modals (action buttons route to T73/T74 which own their dialogs), but any inline confirm (e.g. "Clear all filters?") uses `<dialog>` or routes through `vscode.window.showInformationMessage` with explicit actions. Never `window.confirm/prompt/alert`.
- All mutation handlers (filter changes are reads, not mutations, but row-action handlers and any future inline mutation) use `try/catch` with `vscode.window.showErrorMessage(err.message)` (`parseApiError` does not apply in the VS Code extension context).
- All ID inputs use `SearchableSelect` (webview) or `vscode.window.showQuickPick` (tree-view interactions). Filter pickers use `showQuickPick`; no raw `<select>` or `type="number"` for any ID field.
- Sortable tables use `SortableHeader` + `useTableSort` equivalents exposed by T71's scaffolding; the inbox table sorts on `Status`, `Class`, `Scope`, `Last Verified`, and `Confidence` columns.
- Status badges + loading + empty + error states for every interactive surface: status badges via `StatusBadge.ts`; loading skeleton on first load (`ui-specification.md` §8.2); empty state with distinct messages for "no memories yet" vs "no memories match filters" (`ui-specification.md` §8.3); error banner inline + VS Code error toast on failure (`ui-specification.md` §8.5).
