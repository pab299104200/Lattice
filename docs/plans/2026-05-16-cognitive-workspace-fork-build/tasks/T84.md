## Goal

This task delivers two test modules that enforce the two long-term-compatibility surfaces of the fork: the storage migration path from the legacy Lattice schemas (Phase 3 memory rows, identity model, event-absent state) into the new schemas, and the MCP schema compatibility regression that confirms every backward-compat shim from R64 still functions. Spec §Phase 3 deliverables include "migration/import path from existing Lattice memory rows"; spec §Phase 11 deliverables list "migration tests" and "MCP schema compatibility tests" separately. Without these tests, an operator upgrading an existing Lattice deployment could silently lose memory or break a pinned assistant client.

## Steps

1. Read spec §Phase 3 deliverables (migration path), §Phase 11 deliverables (migration tests + MCP schema compat tests), §MCP Tool Contract Principles, and the T03 storage migration policy doc.
2. Create `daemon/crates/lattice-core/src/hardening/migration_tests.rs` covering:
   - **Legacy memory rows → new memory + links + evidence**: seed a temp SQLite database with the legacy `memories` table populated with representative rows (covering every memory class and every legacy verification status); run the migration entry point from T22; assert every legacy row maps to exactly one new memory record with the correct class, scope, and verification status; assert evidence and links are extracted from the legacy provenance JSON blob into the new `memory_evidence` and `memory_links` tables.
   - **Legacy memory with malformed JSON evidence**: seed a row whose provenance JSON is malformed; assert the migration emits an event, quarantines the row in a `migration_quarantine` table, and does not abort the migration.
   - **Idempotent migration**: run the migration twice; assert the second run is a no-op (no duplicate new rows, no version-table errors).
   - **Forward migration order**: assert migrations apply in the order documented by `## Migration order` in `docs/architecture/2026-05-16-storage-migration-policy.md`; out-of-order application is rejected with a clear error.
   - **Rollback path**: per `## Rollback` in the migration policy, assert each migration has a documented inverse; apply forward, then inverse, then forward again, and assert state is consistent.
   - **Pre-event-log state**: seed a database that predates Phase 2 (no `events` table); assert the migration creates the events tables and bootstraps without requiring event-log data.
   - **Large legacy dataset**: seed 100k legacy memory rows; assert the migration completes within a documented time budget and that no row is lost (count in == count out + count quarantined).
3. Create `daemon/crates/lattice-daemon/src/rpc/mcp_compat_tests.rs` covering:
   - **Every R64 shim still responds**: enumerate every legacy tool name from `docs/architecture/2026-05-16-mcp-compatibility-policy.md` (T02) and assert that calling the legacy name returns a successful response shaped per the legacy schema. This is the backward-compat regression spec §MCP Tool Contract Principles requires.
   - **Additive fields do not break legacy clients**: for every tool classified as `additive`, send a request omitting the new fields; assert the response is a valid superset (legacy fields present with original types).
   - **Deprecated-with-deadline tools surface a warning**: for every tool classified as `deprecated-with-deadline`, assert the response includes a documented `deprecation_warning` field naming the removal date.
   - **Compact and full render modes**: per spec §MCP Tool Contract Principles, every tool supports both modes; assert both modes return valid responses for every review-UI tool and every workflow tool.
   - **Stable handles round-trip**: any context handle returned by a tool can be passed back via `expand_context` and resolves to the same content; assert this holds for every tool that returns handles.
   - **Schema parity vs `mcp_schema` test**: cross-check against the existing `mcp_schema` test set so this module adds compat regression coverage without duplicating schema-shape assertions.
4. Each test uses real daemon code paths (no mocks) and asserts both the response shape and the observable side effects (events emitted, audit rows written).
5. Run `cd daemon && cargo build --release` then `cd daemon && cargo test -p lattice-core --lib hardening::migration_tests` and `cd daemon && cargo test -p lattice-daemon --lib rpc::mcp_compat_tests` and confirm every test passes.
