# T19 — Phase 3 — Memory schema redesign (classes incl CounterMemory + required fields)

**Phase:** 3
**Type:** backend
**Model class:** advanced
**Depends on:** R18
**Spec anchor:** [§Memory Graph](../../2026-05-16-cognitive-workspace-fork-plan.md#4-memory-graph)
**Standards:** Cadres coding standard; Lattice project rules.

## Goal

This task replaces the legacy single-table memory model with a typed memory schema that the rest of Phase 3 builds on. It defines the full memory-class taxonomy (including `CounterMemory` as a first-class class distinct from a `contradicts` link), the SQLite DDL covering every spec-required memory field, the Rust types that mirror the schema, and an architecture doc that records the model authoritatively so later phases (retrieval, consolidation, verification) reference one source of truth. Without this redesign, memory cannot represent claims, evidence, validity conditions, or counter-claims — only loose notes — which violates the spec's core thesis.

## Spec excerpts that drive this task

> "Primary memory classes: `Observation`, `Decision`, `Constraint`, `Pattern`, `AntiPattern`, `WorkflowOutcome`, `FailurePattern`, `Procedure`, `Preference`, `ArchitectureInvariant`, `DocsContract`, `OpenQuestion`, `CounterMemory` — a memory record that explicitly asserts a prior memory is wrong or no longer applicable. Distinct from a `contradicts` link: a link connects two existing memories; a CounterMemory is a first-class record authored by an agent or user that carries its own evidence, scope, and verification status and can itself be superseded or invalidated."

> "Each memory record requires: stable id, content, memory class, assertion type, scope: session, branch, repo, user, organization, verification status, confidence and confidence reason, freshness policy, validity conditions, invalidation triggers, provenance events, evidence references, linked files, linked symbols, linked docs, linked tests, linked memories, contradiction links, supersession links, access history, usefulness scores, last verified state."

## Steps

1. Read spec §Memory Graph in full and quote the 13 memory classes + the field list verbatim into doc comments on `MemoryClass` and the schema header.
2. In `memory_graph/classes.rs`, define `pub enum MemoryClass` with all 13 variants: `Observation`, `Decision`, `Constraint`, `Pattern`, `AntiPattern`, `WorkflowOutcome`, `FailurePattern`, `Procedure`, `Preference`, `ArchitectureInvariant`, `DocsContract`, `OpenQuestion`, `CounterMemory`. Derive `Serialize`, `Deserialize`, `Clone`, `Copy`, `Debug`, `PartialEq`, `Eq`, `Hash`. Implement `as_str()` returning canonical snake_case wire names.
3. Define `pub enum AssertionType { Observation, Decision, Constraint, Hypothesis, Procedure, Outcome, Preference, Question, Counter }` so the model separates "what kind of structure the record has" (class) from "what truth-status it asserts" (assertion type). Wire-canonical strings.
4. Define `pub enum MemoryScope { Session, Branch, Repo, User, Organization }` matching the spec's five scopes. Deny-by-default at query time is enforced by T21; the enum is shared here.
5. Define `pub enum VerificationStatus { Unverified, InReview, Verified, Stale, Contradicted, Superseded, Expired, Invalidated }` matching spec §Verification Engine outputs.
6. Define `pub struct FreshnessPolicy { kind: FreshnessKind, ttl: Option<Duration>, recheck_interval: Option<Duration> }` with `FreshnessKind = { SessionScoped, BranchScoped, RepoScoped, TimeBound, EventTriggered }`.
7. Define `pub struct ValidityCondition { description: String, predicate: ValidityPredicate }` where `ValidityPredicate` is an enum over machine-checkable conditions (file exists, symbol exists, doc heading exists, test passes, time before).
8. Define `pub struct InvalidationTrigger { kind: TriggerKind, target: StableRef }` so verification (Phase 7) can subscribe deterministically: `TriggerKind = { FileChanged, SymbolChanged, DocSectionChanged, TestFailed, TimeExpired }`.
9. Define the canonical `pub struct MemoryRecord` mirroring the schema below, with one field per spec-required attribute. Every non-private column has a corresponding field; nullability is matched precisely.
10. In `memory_graph/schema.sql`, define the `memories` table (this is the new redesigned table, separate from the legacy one; T22 owns the migration). Columns, in order:
    - `memory_id TEXT PRIMARY KEY` (stable id, UUIDv7 or ULID)
    - `content TEXT NOT NULL`
    - `class TEXT NOT NULL` (canonical `MemoryClass` wire name)
    - `assertion_type TEXT NOT NULL`
    - `scope TEXT NOT NULL` (`session` | `branch` | `repo` | `user` | `organization`)
    - `scope_session_id TEXT NULL`, `scope_branch TEXT NULL`, `scope_workspace_id TEXT NULL`, `scope_user_id TEXT NULL`, `scope_org_id TEXT NULL` (denormalized for index-friendly scope queries; exactly one set is required matching `scope` column)
    - `verification_status TEXT NOT NULL`
    - `confidence REAL NOT NULL CHECK(confidence BETWEEN 0 AND 1)`
    - `confidence_reason TEXT NOT NULL`
    - `freshness_policy_json TEXT NOT NULL`
    - `validity_conditions_json TEXT NOT NULL`
    - `invalidation_triggers_json TEXT NOT NULL`
    - `provenance_event_ids_json TEXT NOT NULL` (JSON array of event ids that produced or justified this memory)
    - `last_verified_event_id INTEGER NULL`
    - `last_verified_state TEXT NULL` (small JSON snapshot of what was true at last verification)
    - `usefulness_score REAL NOT NULL DEFAULT 0`
    - `usefulness_score_updated_at INTEGER NOT NULL`
    - `created_at INTEGER NOT NULL`, `created_by TEXT NOT NULL`
    - `updated_at INTEGER NOT NULL`, `updated_by TEXT NOT NULL`
    - `superseded_by TEXT NULL` (memory_id pointer; T20's `memory_links` is the authoritative supersession edge, this column is a denormalized fast-path)
    - `schema_version INTEGER NOT NULL`
    - All `*_json` columns are validated against typed structs on read; never trust raw JSON.
11. Add CHECK constraints: exactly one `scope_*_id` column non-null matching `scope`; `verification_status` ∈ allowed enum values; `class` ∈ allowed enum values; `assertion_type` ∈ allowed enum values.
12. Document the schema in `docs/architecture/2026-05-16-memory-graph-schema.md` with sections: `## Classes`, `## Required fields`, `## Scopes`, `## Verification statuses`, `## Freshness, validity, invalidation`, `## CounterMemory semantics`, `## Schema parity table` (column ↔ Rust field), `## Migration plan reference` (link to T22 doc), `## Index inventory` (point to T23's authoritative index list when added).
13. In `memory_graph/mod.rs`, re-export `MemoryClass`, `AssertionType`, `MemoryScope`, `VerificationStatus`, `FreshnessPolicy`, `ValidityCondition`, `InvalidationTrigger`, `MemoryRecord`. Add a top-level doc comment that cites `docs/architecture/2026-05-16-memory-graph-schema.md` headings.

## Coding-standard checks

- File length ≤800 lines per file; split `classes.rs` if the typed structs push it past the limit.
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10.
- Schema parity: every spec-required field appears as both a SQL column and a Rust struct field; nullability and type widths match.
- No silent error handling — `*_json` decode failures return typed errors, never `unwrap`.
- No `TODO`, `FIXME`, commented-out code.
- For SQLite: declarative DDL in `schema.sql`; no `format!` of SQL anywhere; CHECK constraints encode enum-value invariants at the engine level.
- Use `tracing` only on decode errors; types themselves are passive.
