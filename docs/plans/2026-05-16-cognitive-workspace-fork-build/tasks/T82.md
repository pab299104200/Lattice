## Goal

This task delivers two test modules that prove the daemon survives the failure modes Phase 11 names explicitly: recovery from a partial-write or crash, and handling of corrupted event payloads. Spec §Storage Design requires event-log compaction snapshots to be "versioned and independently readable so the daemon can bootstrap from a snapshot without replaying the full history"; spec §3 makes the event log replayable; spec §Phase 11 deliverables list "recovery tests" and "corrupted-event handling" separately. Without this suite, a single corrupted event payload could brick the daemon and a partial snapshot would silently lose history — both unacceptable per spec §Non-Negotiable Product Properties ("every background consolidation pass is recoverable, replayable, and observable").

## Steps

1. Read spec §Storage Design (event log compaction snapshot, versioned format), §3 Event Log (append-only, replayable), §Phase 2 deliverables (corruption handling), §Phase 11 deliverables (recovery + corrupted-event), and §Non-Negotiable Product Properties so the recovery and corruption invariants are pinned.
2. Create `daemon/crates/lattice-core/src/hardening/recovery_tests.rs` covering:
   - **Replay from snapshot**: produce an event log, trigger a compaction snapshot at timestamp T, append more events after T, simulate daemon restart, assert the daemon bootstraps from the snapshot + replays events-after-T to reconstruct the exact same graph + memory state.
   - **Replay from event log only**: delete the snapshot, restart the daemon, assert it can replay the full event log to reconstruct the state (slower path, but must work).
   - **Partial snapshot recovery**: write a snapshot file that is truncated mid-write (simulate crash during compaction); on restart, assert the daemon detects the truncated snapshot, ignores it, and falls back to full event-log replay without data loss.
   - **Partial event write recovery**: write an event whose row is committed but whose spillover-payload row failed to commit (simulate crash between two writes); on restart, assert the daemon detects the dangling event id, emits a `recovery` event under spec §Phase 2 DoD "failure paths emit useful events without hiding errors", and either reconciles or quarantines the event with an explicit log line.
   - **WAL recovery**: kill the daemon mid-write (simulate `kill -9`); on restart, assert SQLite WAL recovery completes cleanly and no events are lost.
3. Create `daemon/crates/lattice-core/src/hardening/corruption_tests.rs` covering:
   - **Corrupted event payload**: write a valid event envelope but a corrupted (random bytes) payload to the spillover table; on read, assert the daemon emits a `corruption` event, returns an explicit error for that event, and continues processing subsequent events without crashing.
   - **Mismatched payload hash**: write an event whose `payload_hash` does not match the actual payload bytes; on read, assert the daemon detects the hash mismatch, logs a `corruption` event, and quarantines the row.
   - **Invalid event kind**: write a row whose `kind` column contains a string not in the 20-kind enum; on read, assert the daemon rejects the row with a clear error rather than panicking.
   - **Invalid stable reference**: write an event with a `StableRef` pointing to a non-existent file/symbol/memory; on read, assert the daemon emits a `dangling-reference` event and surfaces the row in a quarantine query without crashing.
   - **Truncated event log file**: physically truncate the events SQLite file mid-page; on open, assert the daemon detects the truncation, runs SQLite recovery, and continues with the events it can read while emitting a recovery log line.
   - **Snapshot version mismatch**: write a snapshot with a higher `format_version` than the daemon supports; on read, assert the daemon refuses to bootstrap and emits a clear "snapshot format too new" error rather than silently loading garbage.
4. Each test asserts the daemon survives (no panic), emits the documented recovery / corruption event under spec §Phase 2 DoD, and that the surviving state remains queryable.
5. Run `cd daemon && cargo build --release` then `cd daemon && cargo test -p lattice-core --lib hardening::recovery_tests` and `cd daemon && cargo test -p lattice-core --lib hardening::corruption_tests` and confirm every test passes.

- File length ≤800 lines per file (split per scenario family if it exceeds).
