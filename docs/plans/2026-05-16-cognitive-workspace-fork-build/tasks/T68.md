**Phase:** 9
**Type:** backend
**Model class:** balanced
**Depends on:** T65, T66

## Goal

This task ships the `lattice_report` binary and its supporting `metrics/report.rs` module so operators and CI can render the full Phase 9 metric set from the T65 collector and the T66 benchmark output. Spec §Phase 9 Deliverables names "regression dashboard or CLI report" as binding and the Phase 9 DoD requires that "changes to retrieval, memory, and workflow behavior can be evaluated without relying on anecdote." The CLI is the surface that turns the metrics module into something a human or CI job can read.

## Spec excerpts that drive this task

> "Phase 9 Deliverables: …regression dashboard or CLI report."

> "Definition of done: changes to retrieval, memory, and workflow behavior can be evaluated without relying on anecdote." (spec §Phase 9)

> "Initial targets: 30 percent fewer discovery tool calls on benchmark tasks; 40 percent fewer irrelevant file reads; 80 percent memory inclusion precision on curated memory benchmarks; zero trusted display of known contradicted memory; zero trusted display of known stale memory without stale label; 90 percent correct relevant-test recommendation on curated tasks." (spec §Measurable Success Criteria)

## Steps

1. Read spec §Phase 9 and §Measurable Success Criteria in full.
2. Implement `daemon/crates/lattice-core/src/metrics/report.rs` exposing: (a) `ReportInput { current: Vec<MetricValue>, baseline: Option<Vec<MetricValue>>, benchmark_report_path: PathBuf, scope: MetricScope, success_criteria: SuccessCriteriaThresholds }`; (b) `RegressionReport` rendering per-signal current value, baseline value, delta, target threshold (from spec §Measurable Success Criteria), pass/fail per row; (c) renderers for human-readable text, machine-readable JSON, and a CI-friendly summary line; (d) per-signal evidence pointer back to the contributing event/memory IDs so any regression is investigable. `SuccessCriteriaThresholds` encodes the spec §Measurable Success Criteria initial targets explicitly (30%, 40%, 80%, 0, 0, 90%) so the report's pass/fail column is grounded in the spec.
3. Implement `daemon/crates/lattice-daemon/src/bin/lattice_report.rs` as the CLI binary. Argument surface: `--scope`, `--time-range`, `--signals`, `--baseline <path>`, `--benchmark <path>`, `--format text|json|ci-summary`, `--output <path>`, `--fail-on-regression`. The binary loads the current metrics via the T65 collector against the active workspace, optionally loads a baseline JSON, optionally loads the T66 benchmark JSON, and renders the `RegressionReport` to stdout or the `--output` path. With `--fail-on-regression`, exits non-zero when any signal fails its spec §Measurable Success Criteria target.
4. Author `docs/architecture/2026-05-16-metrics-report.md` describing: report architecture, signal definitions (referencing T65), thresholds (referencing spec §Measurable Success Criteria), input/output formats, CI integration guidance, regression-investigation runbook. The doc is the operator-facing reference.
5. Implement `daemon/crates/lattice-core/src/metrics/report_tests.rs` covering: (a) deterministic rendering across all three formats; (b) baseline-vs-current delta computation; (c) target threshold pass/fail logic for each spec §Measurable Success Criteria initial target; (d) honest reporting of `null` signals (renders as `n/a` with reason, never as zero); (e) exit-code behavior of `--fail-on-regression`; (f) per-signal evidence-pointer round-trip.
6. Wire the binary into the workspace `Cargo.toml` so `cargo build --release --bin lattice_report` produces an installable binary. Document the build/deploy path in `docs/architecture/2026-05-16-metrics-report.md`.
7. Workspace boundary: the CLI honors the workspace it was invoked against — it never crosses workspace boundaries even if multiple `.lattice/` paths are reachable.
8. Honor Cadres coding standard `## Observability`: the CLI emits structured `tracing` output to stderr so CI logs capture every signal collected and every threshold evaluated.

## Coding-standard checks

- File length ≤800 lines per file (split `report.rs` per renderer if needed).
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10.
- Schema parity: `RegressionReport`, `ReportInput`, `SuccessCriteriaThresholds` derive `Serialize`, `Deserialize`, `Debug`, `Clone`; JSON output schema documented in `docs/architecture/2026-05-16-metrics-report.md`.
- No silent error handling — every IO/parse failure surfaces with a typed error and a non-zero exit code; honest `null` values render as `n/a` with reason, never zero.
- No `TODO`, `FIXME`, `XXX`, commented-out code; no unjustified `#[allow(...)]`.
- Public API names follow intent-over-mechanism naming (`SuccessCriteriaThresholds::memory_inclusion_precision`, not `Thresholds::mip`).
- For SQLite: storage access goes through T65 `MetricsCollector`; no raw SQL in the binary or report module.
- Observability: binary emits structured `tracing` to stderr with `scope`, `signal_count`, `pass_count`, `fail_count`, `format` fields per invocation.
- Doc citation: cite spec headings `## Phase 9: Metrics And Evaluation` and `## Measurable Success Criteria` in `docs/architecture/2026-05-16-metrics-report.md` and the binary source.
