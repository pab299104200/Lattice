## Goal

This task delivers two of the most consequential operator surfaces in Phase 10: the promotion queue (proposed promotions awaiting accept/reject) and the contradiction queue (memory pairs the consolidation engine flagged as conflicting, awaiting a human verdict). Per spec §Opaque Memory Mutation, "automatic consolidation corrupts durable repo knowledge" is a named risk whose control is "event-backed proposals, reversible updates, provenance, review queue for high-scope changes, and replay." This task implements the human side of that control: the queue UIs and the proposal-confirm dialogs that turn a proposed memory evolution into an applied write only when an operator explicitly clicks accept. Dialogs are native `<dialog>` elements per the UI specification — never `window.confirm`.

## Steps

1. Read spec §6 Consolidation Engine, the "LLM-driven consolidation" subsection, §10 Human Review Surface, and §Opaque Memory Mutation risk control in full so the proposal-only-then-apply contract is grounded in the spec.
2. Create `extension/src/review/promotionQueue.ts` exporting `mountPromotionQueue(host, bridge, i18n)`. The function lists pending promotion proposals (memory candidates the consolidation engine wants to elevate, e.g. session → branch, branch → repo) with columns: `Proposed Class`, `Current Scope`, `Target Scope`, `Confidence`, `Evidence Count`, `Created At`, `Status` badge, `Actions` (Review, Accept, Reject).
3. Create `extension/src/review/contradictionQueue.ts` exporting `mountContradictionQueue(host, bridge, i18n)`. The function lists pending contradiction pairs with columns: `Memory A`, `Memory B`, `Link Type` (`contradicts`/`supersedes` candidate), `Detected By` (rule or LLM proposal provenance), `Created At`, `Status` badge, `Actions` (Review, Accept Resolution, Reject Resolution).
4. Create `extension/src/review/components/ProposalDialog.ts` exporting `openProposalDialog({ proposal, onApply, onReject }, i18n)`. The dialog uses a native `<dialog>` element mounted into the webview (never `window.confirm`). The dialog renders: proposal summary, evidence list with file/symbol/event links, model + prompt-hash + response-hash provenance (per spec §6 LLM-driven consolidation), expected effect on durable memory, and a `Diff preview` panel showing the memory record before/after. Footer: `Cancel`, `Reject (with reason)`, `Accept and apply`.
5. The dialog enforces typed-confirm for high-scope proposals (per `ui-specification.md` §7.2): if the target scope is `repo`, `user`, or `organization`, the operator must type the memory class name (e.g. `ArchitectureInvariant`) before the Accept button enables. Below `repo` scope, single-click accept is sufficient.
6. The `onApply` handler calls `bridge.applyPromotion(proposalId)` (or `bridge.applyContradictionResolution(...)` for the contradiction dialog). Wrap in `try/catch`; on success post a `vscode.window.showInformationMessage('Promotion applied.')` and refresh the queue. On failure, render an inline error inside the dialog and call `vscode.window.showErrorMessage(err.message)` (per `ui-specification.md` §8.5).
7. The `onReject` handler requires a reason string (rendered as a `<textarea>` inside the dialog, required to be non-empty). Calls `bridge.rejectPromotion(proposalId, reason)`. Reasons are persisted by the daemon as event-log evidence so rejected proposals are auditable per spec §Opaque Memory Mutation control.
8. Add queue-specific i18n keys to `en.json` under `promotionQueue` and `contradictionQueue` namespaces: column headers, action labels, dialog title, dialog body strings, typed-confirm prompt, success/error toast strings. Status-badge labels reused from T71.
9. Wrap every bridge call in `try/catch`. On read failure render the inline error banner; on mutation failure render inline + `vscode.window.showErrorMessage(err.message)`.
10. Run `cd extension && npm run compile && npm run lint` and fix every error/warning before stopping.

### UI specification

- All user-facing strings via `i18n.t(...)` from the `promotionQueue`, `contradictionQueue`, and `proposalDialog` namespaces; no inline literals in any of the three files.
- All modals via native `<dialog>` (per `ui-specification.md` §7) — `ProposalDialog.ts` mounts an actual `<dialog>` element in the webview and uses `dialog.showModal()` / `dialog.close()`. No `window.confirm`, no `window.prompt`, no `window.alert`, no DaisyUI `modal modal-open` `<div>` pattern. Typed-confirm for high-scope (repo / user / organization) per `ui-specification.md` §7.2.
- All mutation handlers (`onApply`, `onReject`) use `try/catch` with `vscode.window.showErrorMessage(err.message)` (`parseApiError + toast.error` is the Cadres web equivalent; for the VS Code extension this is the analogue per the build harness rule).
- All ID inputs use `SearchableSelect` (webview) or `vscode.window.showQuickPick` (tree-view) — proposal selection inside the dialog uses `<dialog>` content, not a separate ID picker; if cross-references to other memories or events are picked, use `showQuickPick`, never raw `<select>` or `prompt`.
- Sortable tables use `SortableHeader` + `useTableSort` equivalents on both queue tables. Sortable on `Confidence`, `Evidence Count`, `Created At`, and `Status`.
- Status badges + loading + empty + error states for every interactive surface: badge for proposal status, loading skeleton on first load, distinct empty states ("No pending promotions." vs "No pending contradictions."), error banner on read failure, inline dialog error on apply/reject failure plus VS Code error toast.
