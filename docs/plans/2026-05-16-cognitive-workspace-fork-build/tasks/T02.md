**Phase:** 0

## Goal

This task produces the two foundational design documents that govern every later phase: the successor architecture overview (workspace graph, event log, memory graph as three first-class sources of truth) and the MCP compatibility policy (which existing tools remain stable, which gain additive fields, which are deprecated with shims). It matters because spec §Design Thesis requires all three substrates to share identity, storage, and ranking primitives — without a single overview doc, each phase risks diverging. The compatibility policy is binding for every Phase 8 tool redesign and protects existing assistant clients while the substrate evolves.

## Spec excerpts that drive this task

> "The correct abstraction is not memory attached to a code graph. The correct abstraction is a workspace cognition substrate with three first-class sources of truth: 1. Workspace graph: files, symbols, docs, tests, dependencies, routes, schemas, build targets, runtime surfaces, and ownership boundaries. 2. Event log: every assistant action, tool call, context bundle, edit, diagnostic, test result, user correction, deployment step, and outcome. 3. Memory graph: durable typed claims over the workspace and event history, with evidence, freshness, contradiction, supersession, use history, and retrieval explanations."

> "Phase 0 Deliverables: ... architecture docs copied and revised ... compatibility policy for existing MCP tools."

## Steps

1. Read T01's decision doc and the spec sections §Design Thesis, §System Architecture, §MCP Surface, §MCP Tool Contract Principles.
2. In `2026-05-16-cognitive-workspace-architecture.md`, write a `## Workspace graph` section enumerating the node and edge families from spec §Workspace Graph and mapping each to the existing or planned crate.
3. Write a `## Event log` section summarizing the 20 event types, the append-only invariant, compaction snapshots, and the hot-path budget (≤5ms P99) from spec §Event Log and §Phase 2 DoD.
4. Write a `## Memory graph` section covering the memory classes, link types, evidence model, and the `CounterMemory` distinction from spec §Memory Graph.
5. Add a `## Shared substrate primitives` section explaining how identity, storage, and ranking are shared across the three substrates.
6. Add a `## Reference to existing docs` section linking forward to the prior `2026-04-11-*` architecture docs without duplicating their content.
7. In `2026-05-16-mcp-compatibility-policy.md`, enumerate every existing MCP tool by name and assign each a status: `stable` (no breaking change), `additive` (gains optional fields only), `redesigned-with-shim` (legacy name keeps responding with a compatibility shim), or `deprecated-with-deadline`.
8. Write a `## Backward compatibility` section stating the binding rule: every existing assistant client must continue to function for a full phase cycle after any tool's redesign lands. Include the shim removal protocol.
9. Cross-link the two docs and reference the spec heading anchors precisely.
