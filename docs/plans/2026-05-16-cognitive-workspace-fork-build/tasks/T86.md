## Goal

This task delivers the two operational documents that turn the architecture suite into something an on-call human can actually use under pressure: the daily-operations runbook and the recovery playbook. The runbook is the day-in-the-life: how to deploy, how to verify health, how to read the metrics, how to respond to common alerts. The recovery playbook is the worst-day-of-the-week document: what to do when the daemon crashes, when the event log is corrupted, when memory is contradictory at scale, when migration breaks. It includes the binding deploy sequence from `lattice/CLAUDE.md` Build/Deploy and the replay-from-snapshot procedure proved viable by T82 recovery tests.

## Steps

1. Read T85's operator guide and event-log design doc so the runbook layers on top without duplicating their content.
2. Create `docs/operator-guide/2026-05-16-runbook.md`. Required headings:
   - `## Daily operations` — required by verification. Cover: starting/stopping the daemon, checking health via the review panel from T76 (`consolidationQueueView`, `indexingHealthView`, `workspaceGraphHealthView`), reading the metrics report from T68/T69 (Phase 9), reviewing accepted/rejected promotions weekly.
   - `## Deploy sequence` — quote the canonical sequence from `lattice/CLAUDE.md` Build/Deploy verbatim: `pkill -f lattice && cp daemon/target/release/lattice extension/bin/ && cp daemon/target/release/lattice ~/.vscode/extensions/lattice.lattice-0.1.0/bin/`. Document the `sleep 2` between `pkill` and `cp` per the canonical sequence. Document the verification steps: confirm the new binary is running via `pgrep -fa lattice`; confirm the extension picks up the new binary via the activity bar.
   - `## Health checks` — list the green/yellow/red thresholds for each indicator in the indexing health and graph health views: parser failure rate, vector index freshness, FTS row count, event log ingestion rate, compaction snapshot age. Each threshold cites the spec heading that motivates it.
   - `## Alerts and response` — for each alert (queue depth at bound, dropped consolidation jobs, broken references, stale-edge spike, hot-path P99 budget breach), document the on-call response: which review-panel view to open, which log target to inspect, what to escalate.
   - `## Memory hygiene` — operator weekly tasks: review promotion queue, review contradiction queue, audit stale memory, audit usefulness metrics from T68/T69.
   - `## Backups` — document the backup strategy for `.lattice/` (graph.db, memories.db, events.db, snapshots, vector index) and the restore procedure (cross-link to the recovery playbook).
3. Create `docs/operator-guide/2026-05-16-recovery-playbook.md`. Required headings:
   - `## Recovery procedures` — required by verification. Cover the full recovery decision tree: daemon won't start, daemon starts but indexing fails, daemon indexing succeeds but queries return empty, queries return stale data, memory state is contradictory, snapshot file is missing or corrupted.
   - `## Replay from snapshot` — required by verification. The binding procedure proved viable by T82 recovery tests. Steps: (1) stop the daemon (`pkill -f lattice`); (2) verify the snapshot file exists at `.lattice/snapshots/<latest>.snap`; (3) verify the snapshot file integrity (file size, format version header, checksum); (4) move the existing `graph.db` and `memories.db` to a quarantine location for forensics; (5) start the daemon with `--bootstrap-from-snapshot <path>`; (6) confirm the daemon emits a `SnapshotBootstrap` event; (7) confirm queries return the expected pre-snapshot state plus post-snapshot replay; (8) document the post-recovery audit checklist. Cross-link to the test `test_replay_from_snapshot_reconstructs_state` in `daemon/crates/lattice-core/src/hardening/recovery_tests.rs`.
   - `## Replay from event log only` — fallback procedure when no snapshot is usable. Steps and post-replay verification.
   - `## Quarantine and forensics` — procedure for preserving corrupted state for diagnosis without blocking recovery.
   - `## Corruption recovery` — per-class procedures matching the T82 corruption test scenarios: corrupted payload, mismatched hash, invalid kind, invalid stable reference, truncated file, snapshot version mismatch.
   - `## Rollback` — how to roll back a bad migration using the inverse migrations from T03's migration policy doc and T84's migration tests.
   - `## Communicating incidents` — what to log, who to notify, what to capture for the post-incident review.
4. Cross-link both documents: the runbook's "Alerts and response" section links to the recovery playbook for procedures that require recovery; the recovery playbook's intro links back to the runbook for daily-operations context.
5. Confirm both documents cite spec headings exactly (per `lattice/CLAUDE.md` Markdown Heading References) — `## Storage Design` for compaction snapshots, `## 3. Event Log` for replay semantics, `## Phase 11: Hardening` for the operational invariants.
6. Confirm the quoted deploy sequence matches `lattice/CLAUDE.md` Build/Deploy character-for-character.
