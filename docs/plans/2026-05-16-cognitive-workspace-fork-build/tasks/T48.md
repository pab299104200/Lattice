**Phase:** 7
**Type:** backend
**Model class:** balanced
**Depends on:** R47
**Spec anchor:** [§Verification Engine](../../2026-05-16-cognitive-workspace-fork-plan.md#8-verification-engine), [§Phase 7: Verification And Freshness](../../2026-05-16-cognitive-workspace-fork-plan.md#phase-7-verification-and-freshness), [§Storage Design](../../2026-05-16-cognitive-workspace-fork-plan.md#storage-design)
**Standards:** Cadres coding standard; Lattice project rules (`/home/pete/cadres/lattice/CLAUDE.md`, `AGENTS.md`).

## Goal

This task lands the Phase 7 verification engine's core: the existence checks for files, symbols, docs, and tests that every durable memory's evidence cites. It introduces the `verification_jobs` table from spec §Storage Design, the eight-state verification output model (`verified` / `unverified` / `in_review` / `stale` / `contradicted` / `superseded` / `expired` / `invalidated`), and the basic verifier entrypoints that downstream Phase 7 tasks (T49 spans, T50 scope, T51 incremental + expiry, T52 surfacing) layer onto. Without this core, the spec's §Stale Memory Leakage risk control has no mechanism — and memory cannot be safely surfaced as trusted guidance.

## Spec excerpts that drive this task

> "Verification checks: linked files still exist; linked symbols still exist; cited docs still exist; linked tests still exist; evidence text still matches when exact spans were captured; implementation still matches memory claim where deterministic checks are possible; contradicted/superseded states remain coherent; branch-scoped memory is not leaking into unrelated branches; time-bound memory has expired."

> "Verification outputs: `verified`; `unverified`; `in_review`; `stale`; `contradicted`; `superseded`; `expired`; `invalidated`."

> "Verification must be incremental and tied to workspace changes. Large repos cannot tolerate full rescans for every memory."

> Core tables include `verification_jobs` (§Storage Design).

## Steps

1. Read spec §Verification Engine in full and §Phase 7 DoD. Copy the verification-checks list and the eight verification-output states into the top-of-file doc comment on `verification/mod.rs`.
2. Add `daemon/crates/lattice-core/src/verification/mod.rs` re-exporting `existence`, `VerificationStatus`, `VerificationVerdict`, `VerifierCore`. Module doc comment cites `## 8. Verification Engine` and `## Storage Design`.
3. Define `pub enum VerificationStatus { Verified, Unverified, InReview, Stale, Contradicted, Superseded, Expired, Invalidated }` in `verification/mod.rs`, mirroring spec verbatim. Derive serde + display so the SQLite column and the MCP tool surface both serialize the same wire names.
4. Author `verification/schema.sql` defining the `verification_jobs` table (columns: `job_id PK`, `workspace_id`, `target_memory_id`, `check_kind`, `status` ∈ {`queued`, `running`, `completed`, `failed`}, `verdict` ∈ `VerificationStatus`, `reason TEXT`, `queued_at`, `started_at`, `finished_at`, indexes on `(workspace_id, status)` and `(target_memory_id, finished_at)`).
5. In `verification/existence.rs`, implement `FileExistenceCheck`, `SymbolExistenceCheck`, `DocSectionExistenceCheck`, `TestExistenceCheck`. Each consumes a `MemoryEvidence` reference and the current graph snapshot, returns a `VerificationVerdict { status, reason: String }`. `Verified` when the identity resolves; `Invalidated` (file/symbol deletion) or `Stale` (graph snapshot is older than the evidence's anchor timestamp) otherwise. Test evidence resolves through the existing test-id index from Phase 1.
6. Implement `VerifierCore::verify_memory(memory_id)`: load the memory's evidence rows, dispatch each to the matching existence check, aggregate verdicts (any `Invalidated` → memory status `invalidated`; any `Stale` and no `Invalidated` → `stale`; all `Verified` → `verified`). Persist the result by emitting a `MarkStale` / `MarkInvalidated` / `MarkVerified` proposal through the T39 runtime — never direct writes.
7. Wire `mod verification;` into `daemon/crates/lattice-core/src/lib.rs` (alphabetical) and register `verification/schema.sql` in the storage migration runner. Add `MarkVerified` and `MarkInvalidated` variants to `ProposalKind` if not already defined; migration covers the enum extension.
8. Expose `VerifierCore::run_pending_jobs(workspace_id, budget: VerifierBudget)` so the daemon scheduler can drive the verifier under a per-call work budget (e.g. max N memories per call). Return a `VerifierReport { verified, stale, invalidated, expired, elapsed }` for observability.
9. In `verification/existence_tests.rs`, write tests that: (a) a memory whose evidence cites a live file is `Verified`, (b) deleting the file makes the next verify return `Invalidated` (assert via a proposal emitted through T39, not via a direct memory mutation), (c) a memory whose evidence cites a deleted symbol returns `Invalidated`, (d) a memory whose evidence cites a still-existing doc section returns `Verified`, (e) a memory whose evidence cites a deleted test returns `Invalidated`, (f) the `verification_jobs` schema round-trips under the migration runner against a temp DB.

## Coding-standard checks

- File length ≤800 lines per file.
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10. `VerifierCore::verify_memory` is a dispatch loop — keep helpers small and named.
- Single source of truth: status writes route through T39 proposals; do not introduce a parallel memory-mutation path. Existence resolution goes through the graph snapshot API, not ad-hoc filesystem scans.
- Error handling: typed `VerificationError` (storage failure, missing memory, missing graph snapshot). No bare `unwrap`. Per-evidence failures emit a `tracing::warn!` and continue verifying the rest of the memory's evidence — never abort a whole job.
- Naming: `VerifierCore::verify_memory`, `FileExistenceCheck`, `VerificationVerdict`. No `Manager`/`Helper` suffixes.
- Schema parity: `VerificationStatus` matches the spec list verbatim; SQLite column uses the same string names.
- No `TODO`, `FIXME`, `XXX`, commented-out code, or unjustified `#[allow(...)]`.
- Observability: every `verify_memory` call emits a `tracing::info_span!("verify_memory", memory_id, evidence_count, verdict)`; aggregate runs emit `tracing::info!` with `VerifierReport` totals.
- Doc citation: file-top comments cite `## 8. Verification Engine` and `## Phase 7: Verification And Freshness` (per `lattice/CLAUDE.md` § Markdown Heading References).
