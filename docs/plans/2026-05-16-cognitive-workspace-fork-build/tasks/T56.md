# T56 — Phase 8 — Redesigned prepare_change + plan_edit + trace_scenario + diagnose_failure

**Phase:** 8
**Type:** backend
**Model class:** advanced
**Depends on:** R55
**Spec anchor:** [§Phase 8: Workflow Engine V2](../../2026-05-16-cognitive-workspace-fork-plan.md#phase-8-workflow-engine-v2)
**Standards:** Cadres coding standard; Lattice project rules (`/home/pete/cadres/lattice/CLAUDE.md`, `AGENTS.md`).

## Goal

This task redesigns the four edit-planning workflow tools (`prepare_change`, `plan_edit`, `trace_scenario`, `diagnose_failure`) on top of the Phase 1–7 substrates: unified identity, event log, memory graph, retrieval pipeline, working memory, consolidation proposals, and verification status. The redesigned tools must compose those substrates in one call so that an assistant gets a complete edit-planning bundle (code anchors, docs, tests, memory with inclusion reasons, risks, verification commands) without first issuing dozens of low-level discovery calls. This is the central deliverable of Phase 8: spec §Phase 8 DoD requires "common coding tasks require fewer manual discovery calls" and "workflows produce enough context to implement and verify changes without broad file dumping." Without this redesign, the new substrate work in Phases 1–7 stays invisible to callers.

## Spec excerpts that drive this task

> "Phase 8 Deliverables: redesigned versions of context, change planning, scenario tracing, failure diagnosis, docs retrieval, test selection, impact analysis, and playbook generation; workflow composition over graph, event, memory, and working-memory substrates; one-call edit-planning bundles with code, docs, tests, memory, risks, and verification commands; workflow outcome recording integrated by default."

> "Definition of done: common coding tasks require fewer manual discovery calls; workflows produce enough context to implement and verify changes without broad file dumping."

> "Every assistant-facing tool should return: overview, ranked pivots, relevant context, memory highlights, event episodes where relevant, suggested next expansion, stable handles, risks or uncertainty, compact/full render choice, structured payload." (spec §MCP Tool Contract Principles)

## Steps

1. Read spec §Phase 8 and §MCP Tool Contract Principles in full. Copy the bundle field list ("overview, ranked pivots, relevant context, memory highlights, event episodes, suggested next expansion, stable handles, risks, render choice, structured payload") into a doc comment on a shared `WorkflowBundle` struct so the schema is self-documenting.
2. Create `daemon/crates/lattice-daemon/src/rpc/workflow_v2/mod.rs` exporting the four redesigned tools and the shared bundle types (`WorkflowBundle`, `Pivot`, `MemoryHighlight`, `EventEpisode`, `RiskNote`, `ExpansionHint`). Doc-comment the module with a reference to spec §Phase 8.
3. Implement `prepare_change` in `workflow_v2/prepare_change.rs`: classify intent via the Phase 4 classifier, resolve anchors (paths, symbols, errors, APIs, config keys) into stable identities, run hybrid candidate retrieval across graph + docs + memory + events, apply the Phase 4 scorer, then assemble a `WorkflowBundle` containing code anchors, docs sections, candidate test files (from Phase 4 ranking + `tested_by` edges), memory highlights (each carrying inclusion reason + verification status per spec §MCP Tool Contract Principles), risk notes derived from contradiction/supersession state, and verification commands (`cargo test ...`, `npm test`, etc.) inferred from the affected build targets.
4. Implement `plan_edit` in `workflow_v2/plan_edit.rs`: build on `prepare_change` output and produce a patch-oriented plan with ordered edit steps, each step referencing files/symbols by stable identity, named tests to add or run, docs sections to update (so spec §MCP Tool Contract Principles "every workflow tool should record inputs, resolved anchors, selected candidates, excluded high-scoring candidates" is satisfied).
5. Implement `trace_scenario` in `workflow_v2/trace_scenario.rs`: walk call chains using the Phase 1 graph between anchor symbols, attaching event-episode evidence where the chain has been exercised before (from event log) and memory annotations describing prior successes/failures on that chain.
6. Implement `diagnose_failure` in `workflow_v2/diagnose_failure.rs`: take a stack trace, compiler error, or failing test as input, extract anchors, query `FailurePattern` memories and prior `WorkflowFailed` events for similar signatures, surface likely culprit symbols with inclusion reasons + verification status, and suggest a candidate `prepare_change` follow-up bundle handle.
7. Every tool must emit `AssistantTaskStarted`, `ToolCalled`, `ContextBundleReturned`, `MemoryRetrieved`, and `PlanCreated` events via the Phase 2 `EventWriter`. Hot-path budget per spec §Phase 2 DoD: event write must not add more than 5ms P99 on `prepare_change` / `get_context_capsule`.
8. Every tool must produce compact rendering by default with stable expansion handles (per spec §MCP Tool Contract Principles "compact rendering, full structured JSON, context handles, stable expansion targets, budget controls, diagnostic explanations where useful"). The compact form must include enough inclusion reason for an assistant to trust the result.
9. Register the four `workflow_v2` tools in `daemon/crates/lattice-daemon/src/rpc/mcp.rs` under their canonical names while keeping the legacy implementations registered with deprecation flags per the T02 compatibility policy.
10. In `workflow_v2/edit_workflows_tests.rs`, write tests that: (a) round-trip each tool's request/response through serde; (b) assert that `prepare_change` returns a `WorkflowBundle` with at least one ranked pivot, one memory highlight (or an explicit empty rationale), one risk note, and at least one verification command for a fixture repo; (c) assert that no memory with `verification_status = stale | contradicted | superseded | expired | invalidated` appears without an explicit stale label (spec §Phase 7 DoD); (d) assert event-emission order and hot-path budget; (e) assert `plan_edit` produces ordered steps each referencing stable identity types; (f) assert `diagnose_failure` recovers an injected fixture failure pattern.

## Coding-standard checks

- File length ≤800 lines per file (split per-tool when needed; do not co-locate two redesigned tools in one file).
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10.
- Schema parity: `WorkflowBundle` and per-tool request/response structs derive `Serialize`, `Deserialize`, `Debug`, `Clone` and every public field has a doc comment.
- No silent error handling — every retrieval/verifier/event-writer failure returns a typed error and surfaces in the bundle as a `RiskNote` rather than being swallowed.
- No `TODO`, `FIXME`, `XXX`, commented-out code; no unjustified `#[allow(...)]`.
- Public API names follow intent-over-mechanism naming (e.g. `MemoryHighlight::inclusion_reason`, not `MemoryHighlight::why_str`).

- Observability: every tool emits at least one `tracing::info!` span with `tool`, `task_id`, `session_id`, `bundle_size_bytes`, `event_count` fields per spec §MCP Tool Contract Principles.
- Doc citation: cite spec headings `## Phase 8: Workflow Engine V2` and `## MCP Tool Contract Principles` in module doc comments where behavior is bound by those sections.
