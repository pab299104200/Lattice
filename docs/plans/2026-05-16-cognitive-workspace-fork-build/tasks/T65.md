## Goal

This task creates the canonical metrics module that collects every assistant-usefulness signal required by spec §Phase 9. Without a single module owning these signals, downstream tasks (T66 benchmark fixtures, T67 MCP surface, T68 CLI report, T69 regression tests) would each invent their own definitions and diverge. The module turns the event log + memory access history + workflow outcomes into the nine required signals named in spec §Phase 9: tool calls per successful task, irrelevant files opened per task, relevant anchor recall, memory inclusion precision, memory later-used rate, stale memory surfaced rate, contradiction missed rate, tests recommended versus tests needed, and workflow success after first plan.

## Spec excerpts that drive this task

> "Required metrics: tool calls per successful task; irrelevant files opened per task; relevant anchor recall; memory inclusion precision; memory later-used rate; stale memory surfaced rate; contradiction missed rate; tests recommended versus tests needed; workflow success after first plan." (spec §Phase 9)

> "Phase 9 Deliverables: retrieval relevance metrics; memory usefulness metrics; context token efficiency metrics; stale/contradicted memory surfacing metrics; test-pass-after-plan metrics; repeated-failure reduction metrics; benchmark tasks with golden expected anchors; regression dashboard or CLI report."

> "Definition of done: changes to retrieval, memory, and workflow behavior can be evaluated without relying on anecdote." (spec §Phase 9)

## Steps

1. Read spec §Phase 9 in full. Quote the "Required metrics" paragraph verbatim into a doc comment on `metrics/signals.rs` so the canonical list is preserved at the call site.
2. Create `daemon/crates/lattice-core/src/metrics/mod.rs` exporting `signals`, the `MetricSignal` enum, the `MetricValue` struct, and the `MetricsCollector` aggregator. Doc-comment the module with a reference to spec §Phase 9.
3. In `metrics/signals.rs`, define `pub enum MetricSignal` with one variant per spec-required signal: `ToolCallsPerSuccessfulTask`, `IrrelevantFilesOpenedPerTask`, `RelevantAnchorRecall`, `MemoryInclusionPrecision`, `MemoryLaterUsedRate`, `StaleMemorySurfacedRate`, `ContradictionMissedRate`, `TestsRecommendedVsNeeded`, `WorkflowSuccessAfterFirstPlan`. Derive `Serialize`, `Deserialize`, `Clone`, `Copy`, `Debug`, `PartialEq`, `Eq`, `Hash`. Implement `MetricSignal::as_str()` returning the canonical snake_case wire name used by the T67 MCP surface and the T68 CLI report.
4. Define `pub struct MetricValue { signal: MetricSignal, value: Option<f64>, denominator: Option<u64>, sample_count: u64, source: MetricSource, computed_at: DateTime<Utc>, reason_if_null: Option<String> }`. The `Option<f64>` value supports honest reporting when no data is available — never fabricate zeros. The `source` field discriminates `EventLog`, `MemoryStore`, `WorkflowOutcome`, `Verifier`, `SessionMetrics`.
5. In `metrics/signals.rs`, implement a deterministic collector function per signal that aggregates from the appropriate source(s):
   - `ToolCallsPerSuccessfulTask` — count `ToolCalled` events per `task_id` whose terminal event is `WorkflowSucceeded`; mean across tasks in scope.
   - `IrrelevantFilesOpenedPerTask` — count `FileRead` events per task where the file was not part of the eventual `PatchApplied` or `WorkflowSucceeded` artifact set.
   - `RelevantAnchorRecall` — fraction of golden anchors (from T66 fixtures) that appear in the workflow's `ContextBundleReturned` anchor list.
   - `MemoryInclusionPrecision` — fraction of `MemoryRetrieved` entries that were subsequently referenced (`MemoryExpanded`, cited by `PatchApplied`, or referenced by a later `WorkflowSucceeded`).
   - `MemoryLaterUsedRate` — fraction of retrieved memories that the consumer used downstream within the same session or a subsequent reuse window.
   - `StaleMemorySurfacedRate` — fraction of `MemoryRetrieved` entries whose verification status was `stale` and that lacked a stale label in the response payload.
   - `ContradictionMissedRate` — fraction of memory inclusions where a contradiction link existed but was not surfaced.
   - `TestsRecommendedVsNeeded` — comparison between `find_relevant_tests` output and the test set actually required to detect the patch (golden answer from T66).
   - `WorkflowSuccessAfterFirstPlan` — fraction of tasks where the first `PlanCreated` event led to `WorkflowSucceeded` without a `WorkflowFailed` in between.
6. Implement `pub struct MetricsCollector { … }` exposing `collect(scope: MetricScope, signals: &[MetricSignal]) -> Vec<MetricValue>`. `MetricScope` mirrors the §Memory Graph scope taxonomy (`session | branch | repo | user | organization`) plus an optional time range.
7. Honor the spec §Non-Negotiable Product Properties bounds: no unbounded event-log scan on hot paths. Every collector applies a scope filter and a configurable maximum sample size, with explicit `incomplete: true` on the `MetricValue` when truncated.
8. In `metrics/signals_tests.rs`, write tests that: (a) every `MetricSignal` variant has a deterministic collector; (b) collectors return `None` with a reason when no data is available rather than fabricating zero; (c) each collector returns the spec-defined value on a hand-crafted event fixture; (d) scope filters prevent cross-scope leakage; (e) sample-size bounds are honored.

## Coding-standard checks

- File length ≤800 lines per file (split `signals.rs` per signal family if it grows beyond, e.g. `signals/tool_usage.rs`, `signals/memory.rs`).
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10.
- Schema parity: `MetricSignal`, `MetricValue`, `MetricSource`, `MetricScope` derive `Serialize`, `Deserialize`, `Debug`, `Clone`; every public field has a doc comment; wire names match the strings used by T67/T68.
- No silent error handling — missing data produces `None` with a `reason_if_null` string, never a fabricated zero.
- No `TODO`, `FIXME`, `XXX`, commented-out code; no unjustified `#[allow(...)]`.
- Public API names follow intent-over-mechanism naming (`MetricSignal::RelevantAnchorRecall`, not `MetricSignal::AnchorRec`).
- For SQLite: queries go through Phase 2/3/7 APIs; no raw SQL in the metrics module.
- Observability: collectors emit `tracing::debug!` spans with `signal`, `scope`, `sample_count`, `incomplete` fields.
- Doc citation: cite spec headings `## Phase 9: Metrics And Evaluation`, `## Event Log`, `## Memory Graph`, `## Verification Engine` in module doc comments.
