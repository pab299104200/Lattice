## Goal

This task ships the regression tests that prove the cognitive workspace fork beats the baselines on every initial target from spec §Measurable Success Criteria. The tests run the redesigned tools (T56/T57) against the T66 fixture repos, feed the captured events into the T65 metrics collector, render the T68 regression report, and assert each spec §Measurable Success Criteria target. Without this task, the metrics infrastructure exists but no automated gate proves the system meets its stated goals — the Phase 9 DoD ("changes to retrieval, memory, and workflow behavior can be evaluated without relying on anecdote") would not be satisfied.

## Spec excerpts that drive this task

> "Initial targets: 30 percent fewer discovery tool calls on benchmark tasks; 40 percent fewer irrelevant file reads; 80 percent memory inclusion precision on curated memory benchmarks; zero trusted display of known contradicted memory; zero trusted display of known stale memory without stale label; 90 percent correct relevant-test recommendation on curated tasks." (spec §Measurable Success Criteria)

> "Definition of done: changes to retrieval, memory, and workflow behavior can be evaluated without relying on anecdote." (spec §Phase 9)

> "The fork should beat current Lattice on: lower tool calls per coding task; lower irrelevant context inclusion; higher relevant file/symbol recall; higher memory reuse precision; lower stale memory surfacing; better repeated-failure avoidance; better test recommendation accuracy; better user correction retention; faster diagnosis from failures; more explainable context selection." (spec §Measurable Success Criteria)

## Steps

1. Read spec §Measurable Success Criteria and §Phase 9 DoD in full. Quote the "Initial targets" paragraph verbatim into a module-level doc comment on `metrics/regression_tests.rs` so the thresholds are visible at the test source.
2. Implement `daemon/crates/lattice-core/src/metrics/regression_tests.rs` containing one `#[test]` per spec §Measurable Success Criteria initial target. Each test loads the T66 fixtures, runs the redesigned tools end-to-end against the golden tasks, feeds events into the T65 `MetricsCollector`, and asserts the corresponding threshold using the T68 `SuccessCriteriaThresholds`:
   - `test_discovery_tool_calls_at_least_30pct_below_baseline` — `ToolCallsPerSuccessfulTask` is ≥30% below the baseline value from `baseline_metrics.json` for the discovery-tool subset.
   - `test_irrelevant_file_reads_at_least_40pct_below_baseline` — `IrrelevantFilesOpenedPerTask` is ≥40% below baseline.
   - `test_memory_inclusion_precision_at_least_80pct` — `MemoryInclusionPrecision` ≥ 0.80 on the curated memory benchmark tasks from T66.
   - `test_zero_trusted_display_of_contradicted_memory` — `ContradictionMissedRate` equals 0 across all fixture tasks.
   - `test_zero_trusted_display_of_stale_memory_without_label` — `StaleMemorySurfacedRate` equals 0 across all fixture tasks (stale memories may appear, but never without an explicit stale label per spec §Phase 7 DoD).
   - `test_relevant_test_recommendation_at_least_90pct` — `TestsRecommendedVsNeeded` recall ≥ 0.90 on the curated tasks from T66.
3. Each test must surface a useful failure diagnostic: when an assertion fails, print the per-signal `MetricValue` plus the contributing event/memory evidence pointers from T68 so the regression is investigable without re-running.
4. Mark long-running tests `#[ignore]` only if they exceed CI budget; the verification command runs with `-- --include-ignored` so CI executes them. Spec §Tests as documentation forbids silently skipping required coverage.
5. Implement a helper `MetricsTestHarness` in the same file (or a sibling `regression_harness.rs`) that loads fixtures deterministically, executes a fixed tool sequence per task, captures events into an isolated `.lattice/events.db`, and returns the resulting `MetricValue`s. The harness encapsulates the deterministic-seed and fixture-freeze policy from T66 so per-test code is short.
6. Add an explicit assertion at the top of the file that `baseline_metrics.json` exists; if not, the tests fail fast with a clear error pointing to T04 rather than passing accidentally.
7. Workspace boundary + scope: every harness invocation runs in an isolated workspace under a temp directory; never reuses or contaminates the developer's local `.lattice/`.

## Coding-standard checks

- File length ≤800 lines (split into `regression_tests.rs` + `regression_harness.rs` if needed).
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10.
- Schema parity: each test reads thresholds from the T68 `SuccessCriteriaThresholds` rather than hard-coding numbers in two places; signal names use the T65 `MetricSignal` enum.
- No silent error handling — every fixture load / harness failure produces a typed error; no test uses `unwrap()` on a `Result` that could legitimately fail without diagnostic.
- No `TODO`, `FIXME`, `XXX`, commented-out code; no `#[ignore]` without a written reason; no skipped assertions.
- Public API names follow intent-over-mechanism naming (`MetricsTestHarness::run_fixture_task`, not `MetricsTestHarness::go`).
- For SQLite: temp DBs only; harness cleans up on completion.
- Observability: each test emits `tracing::info!` with `signal`, `target`, `actual`, `pass` fields on completion.
- Doc citation: cite spec headings `## Measurable Success Criteria` and `## Phase 9: Metrics And Evaluation` in module doc comments.
