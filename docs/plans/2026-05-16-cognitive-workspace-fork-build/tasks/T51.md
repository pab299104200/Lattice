**Standards:** Cadres coding standard; Lattice project rules (`/home/pete/cadres/lattice/CLAUDE.md`, `AGENTS.md`).

## Goal

This task ships two spec-required Phase 7 mechanisms. First, time-bound expiry: memories with an `expires_at` reach the `expired` state automatically when their timestamp passes, and the verifier emits the corresponding `MarkExpired` proposal. Second, incremental verification: the verifier walks only memories whose evidence cites files/symbols that actually changed since the last graph snapshot, never a full rescan. The spec is explicit that "large repos cannot tolerate full rescans for every memory" — this is the mechanism that makes Phase 7 scalable.

## Steps

1. Read spec §Verification Engine "Verification checks" + "Verification outputs" + the incremental constraint. Copy verbatim into the top-of-file doc comments on `verification/expiry.rs` and `verification/incremental.rs`.
2. In `verification/expiry.rs`, implement `ExpiryScanner::scan(workspace_id, now: DateTime<Utc>) -> ExpiryReport`. Query memories with `expires_at IS NOT NULL AND expires_at <= ? AND verification_status != 'expired'`. For each match, emit a `MarkExpired` proposal through the T39 runtime carrying `prior_state.expires_at` and `proposed_state.verification_status = 'expired'`. Idempotent: re-running on a memory already `expired` is a no-op.
3. Add `MarkExpired` to `ProposalKind` if not already present (T39 migration discipline) and ensure `VerificationStatus::Expired` from T48 round-trips into the memory store.
4. In `verification/incremental.rs`, implement `IncrementalVerifier::on_graph_delta(prior_snapshot_id, new_snapshot_id, changed_files: Vec<FileId>)`. Algorithm: (a) compute the set of changed symbols by intersecting changed files with the graph's `Contains` edges from Phase 1, (b) query `memory_evidence` for every memory citing any changed file or symbol, (c) dispatch each impacted memory through `VerifierCore::verify_memory` (T48 + T49 + T50 in sequence — existence, span, scope), (d) update `last_verified_graph_snapshot_id` on memories whose verdict is now `Verified`, (e) return an `IncrementalReport { impacted, verified, stale, invalidated, expired, elapsed }`.
5. Forbid full rescans on the incremental path: add a `cfg(debug_assertions)` invariant that `impacted.len() <= memory_evidence.rows_for_changed_files()` so a regression cannot silently widen the scan.
6. Wire `IncrementalVerifier::on_graph_delta` into the indexer's existing `files-updated` callback (matches the wiring pattern T41's `StaleMarker::on_graph_change` uses). The verifier should run under a daemon-scheduled bounded work budget so a huge delta does not stall the daemon — overflow re-enqueues remaining memories for the next tick.
7. Provide an explicit `IncrementalVerifier::run_pending_expiry(workspace_id, now)` periodic entry point that wraps `ExpiryScanner::scan` so expiry can run on a slow timer (e.g. every 5 minutes) without a graph delta.
8. Update memory rows on successful verification: bump `last_verified_at = now` and `last_verified_graph_snapshot_id = new_snapshot_id` via T39 proposals (`Refresh` kind from T41) — never direct writes.
9. In `verification/incremental_tests.rs`, write tests that: (a) a graph delta touching file `F` causes only memories whose evidence cites `F` (or symbols contained in `F`) to be re-verified; memories citing unrelated files are NOT scanned (assert via a counting test seam), (b) the `ExpiryScanner` flips `expires_at <= now` memories to `expired` via a `MarkExpired` proposal and is idempotent on re-run, (c) `last_verified_graph_snapshot_id` advances on success, (d) a memory whose evidence cites a deleted file goes from `verified` → `invalidated` on the next delta, (e) `IncrementalVerifier` respects the bounded work budget — given 1000 impacted memories and a budget of 50, exactly 50 are processed and the remainder is re-enqueued.

## Coding-standard checks

- File length ≤800 lines per file.
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10. `IncrementalVerifier::on_graph_delta` is a pipeline of small helpers (delta → impacted set → per-memory verify → report).
- Single source of truth: per-memory verification routes through `VerifierCore::verify_memory` (T48); state writes route through T39 proposals; no parallel paths.
- Error handling: typed `ExpiryError` / `IncrementalError`. No bare `unwrap`. Per-memory failures emit `tracing::warn!` and continue scanning.
- Naming: `ExpiryScanner::scan`, `IncrementalVerifier::on_graph_delta`, `last_verified_graph_snapshot_id`. No `Manager`/`Helper`.
- Schema parity: `last_verified_at`, `last_verified_graph_snapshot_id` migrations covered; nullable columns map to `Option<…>`.
- No `TODO`, `FIXME`, `XXX`, commented-out code, or unjustified `#[allow(...)]`.
- Observability: `tracing::info_span!("incremental_verification", workspace_id, prior_snapshot, new_snapshot, impacted, verified, stale, invalidated, expired, elapsed_ms)`.
- Doc citation: cite `## 8. Verification Engine` "Verification must be incremental and tied to workspace changes" and "time-bound memory has expired" (per `lattice/CLAUDE.md` § Markdown Heading References).
