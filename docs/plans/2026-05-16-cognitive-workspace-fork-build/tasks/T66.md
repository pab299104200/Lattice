**Type:** tests

## Goal

This task ships the cross-language benchmark task fixture repository plus the golden-anchor file that defines the expected retrieval results for every benchmark task. Spec §Phase 9 names "benchmark tasks with golden expected anchors" as a binding deliverable, and spec §Risks "Overfitting To Current Repo" demands the control "fixture repos across languages, repo sizes, and documentation styles." Without cross-language fixtures, every Phase 9 metric measures only Lattice-shaped Rust + TypeScript code and the success-criterion targets in spec §Measurable Success Criteria (30% fewer discovery calls, 40% fewer irrelevant reads, 80% memory precision, 90% relevant-test recommendation) cannot be claimed to generalize.

## Spec excerpts that drive this task

> "Phase 9 Deliverables: …benchmark tasks with golden expected anchors; regression dashboard or CLI report."

> "Risk: benchmarks pass only for Lattice-like Rust/TypeScript repos. Control: fixture repos across languages, repo sizes, and documentation styles." (spec §Risks "Overfitting To Current Repo")

> "Initial targets: 30 percent fewer discovery tool calls on benchmark tasks; 40 percent fewer irrelevant file reads; 80 percent memory inclusion precision on curated memory benchmarks; zero trusted display of known contradicted memory; zero trusted display of known stale memory without stale label; 90 percent correct relevant-test recommendation on curated tasks." (spec §Measurable Success Criteria)

## Steps

1. Read spec §Phase 9, §Measurable Success Criteria, and §Risks "Overfitting To Current Repo" in full. Quote the "fixture repos across languages…" sentence verbatim into `benches/fixtures/README.md` so the cross-language requirement is preserved at the fixture source.
2. Author `benches/fixtures/README.md` describing the fixture layout: one sub-directory per language (`rust-repo/`, `typescript-repo/`, `python-repo/`), each with `manifest.toml` declaring repo size class (`small | medium | large`), documentation style (`sparse | moderate | rich`), and the benchmark tasks the fixture supports. Cross-link to spec §Risks.
3. Create `benches/fixtures/rust-repo/manifest.toml` listing: name, size class, documentation style, list of benchmark task IDs, expected event counts on indexing, and a `golden_anchors_path` pointing into `golden_anchors.json`. Add the actual fixture source under `benches/fixtures/rust-repo/src/` shaped to exercise call graphs, trait impls, type refs, doc backlinks, and at least one cross-module test target. Include `Cargo.toml` and at least one inline Markdown doc citing source symbols.
4. Create `benches/fixtures/typescript-repo/manifest.toml` and the TS fixture (with `package.json`, `tsconfig.json`, at least one React or Node module exercising imports, classes, interfaces, and tests). Document the size class and documentation style.
5. Create `benches/fixtures/python-repo/manifest.toml` and the Python fixture (with `pyproject.toml`, a small module with classes, functions, tests, and a docstring-rich style). Document the size class and documentation style.
6. Author `benches/fixtures/golden_anchors.json` containing one entry per benchmark task. Each entry: `task_id`, `repo`, `intent`, `task_prompt`, `expected_anchors` (list of stable `{file, symbol, doc_section}` identities), `expected_tests`, `expected_memory_classes`, `expected_render_mode`, `success_criteria_thresholds` (cited from spec §Measurable Success Criteria — e.g. relevant_anchor_recall ≥ 0.8). The JSON schema is documented in `benches/fixtures/README.md` and stable.
7. Implement `benches/cognitive_workspace_benchmark.rs` using `criterion` (matching T04 style). For each fixture repo, the benchmark indexes the workspace, runs the redesigned tools (`prepare_change`, `get_context_capsule`, `find_relevant_tests`, `impact_from_diff`, `diagnose_failure`) against each golden task, feeds the resulting events into the T65 `MetricsCollector`, and reports the resulting `MetricValue`s. Reuse the existing `baseline_workflows.rs` patterns; do not duplicate harness code.
8. The benchmark must run in CI-friendly time. Use `--warm-up-time 1 --measurement-time 3` as the default invocation profile (already encoded in the verification commands). The benchmark produces a JSON report that T68 ingests.
9. Provide a deterministic seed and fixture freeze policy in `benches/fixtures/README.md`: fixtures change only via a documented bump that updates `golden_anchors.json` in the same commit.

## Coding-standard checks

- File length ≤800 lines per file (split fixture source into multiple files when needed).
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10 — applies to the benchmark harness code.
- Schema parity: `golden_anchors.json` schema documented in `README.md`; every per-task entry has the same field set; the benchmark code validates the JSON schema before running so a malformed fixture fails fast.
- No silent error handling — fixture indexing or tool failures fail the benchmark with a typed error.
- No `TODO`, `FIXME`, `XXX`, commented-out code; no unjustified `#[allow(...)]`.
- Public API names follow intent-over-mechanism naming (`GoldenAnchor::expected_render_mode`, not `GoldenAnchor::mode`).
- For SQLite: benchmark uses temp DBs under `.lattice/` per-run isolation; cleans up on completion; no shared mutable state across fixtures.
- Observability: benchmark emits `tracing::info!` spans per fixture per task with `fixture`, `task_id`, `tool`, `latency_ms`, `metric_signal_count` fields.
- Doc citation: cite spec headings `## Phase 9: Metrics And Evaluation`, `## Measurable Success Criteria`, `## Risks` (specifically "Overfitting To Current Repo") in `benches/fixtures/README.md`.
