## Goal

This review certifies that Phase 4 — Retrieval V1 — is complete, spec-faithful, and ships the inclusion-reason discipline that makes the retrieval layer trustworthy. The reviewer reads every file produced by T27–T32, runs the verification commands, and writes a structured findings report under `docs/plans/2026-05-16-cognitive-workspace-fork-build/reviews/R33-retrieval-v1.md`. The report uses the headings required by the verification commands so the build harness can confirm it was actually written, not stubbed. Verdict is one of `Pass`, `Pass with follow-ups`, or `Fail with required rework`; `Fail` blocks T34 from starting.

## Spec excerpts that drive this review

> "Pipeline: 1. Parse user task and classify intent. 2. Extract literal anchors: paths, symbols, errors, commands, APIs, config keys. 3. Resolve anchors into graph identities. 4. Retrieve graph candidates. 5. Retrieve memory candidates from typed streams. 6. Retrieve relevant event episodes. 7. Expand through bounded graph and memory neighborhoods. 8. Score candidates. 9. Deduplicate and compress. 10. Return a compact bundle with inclusion reasons and expansion handles." (spec §7. Retrieval Engine)

> "Every durable memory has evidence; every retrieved memory has an inclusion reason." (spec §Non-Negotiable Product Properties)

> "Definition of done: memory retrieval no longer depends on keyword search as the primary path; workflow tools return memory with inclusion reasons and stable expansion handles; irrelevant memory rate is measured and regressed." (spec §Phase 4: Retrieval V1)

> "The ranker should expose scores and reasons in diagnostic mode. ... Risk: ranking becomes hard to reason about. Control: keep ranker feature-based and inspectable before any learned policy." (spec §7. Retrieval Engine, §Ranking Complexity)

## Steps

1. Read spec §7. Retrieval Engine, §Phase 4: Retrieval V1, §Ranking Complexity, §Stale Memory Leakage, and the relevant lines of §Non-Negotiable Product Properties in full.
2. Run every verification command from T27–T32 in sequence and record pass/fail with output excerpts in the review's `## Findings` section.
3. Trace the pipeline end-to-end on at least three representative tasks (one debug, one refactor, one docs) using the diagnostic mode output; confirm each pipeline step produced expected outputs and each ranking signal contributed.
4. Audit inclusion-reason discipline: open the shaper output for every golden test in T32 and confirm `inclusion_reason` is non-empty, ≤120 chars in compact mode, and that the dominant signal is named. Sample at least ten bundle results.
5. Audit expansion-handle integrity: take a random sample of handles from the benchmark run and round-trip them through the existing follow-up-handle resolver; confirm each handle resolves back to the candidate's original identity.
6. Audit Phase 5 forward compatibility: serialize a `RetrievalBundle` and confirm its JSON shape can be embedded under a `selected_memories` field exactly as T34 will need it, with no Phase-4-only fields that block reuse.
7. Audit the stale-memory regression: confirm at least one golden test pins that a stale memory cannot rank above a trusted one with the same raw match, per spec §Stale Memory Leakage.
8. Audit feature-based ranker discipline (§Ranking Complexity): confirm no learned-policy code path exists; every signal has a documented evaluator with an inspectable score and reason.
9. Audit coding-standard compliance across all produced files: file ≤800 lines, function ≤50 lines, nesting ≤3, no TODOs/FIXMEs/commented-out code/unjustified `#[allow(...)]`, single source of truth (no parallel intent classifier, no parallel handle generator, no duplicated SQL).
10. Write the findings report under `docs/plans/2026-05-16-cognitive-workspace-fork-build/reviews/R33-retrieval-v1.md` with the required headings; assign a verdict; list follow-ups (if any) as actionable items addressed to specific subsequent tasks.
