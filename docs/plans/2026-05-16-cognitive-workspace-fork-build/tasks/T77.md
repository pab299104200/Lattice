## Goal

This task delivers the VS Code integration smoke tests that prove the Phase 10 review surface activates cleanly inside a real VS Code instance, the review panel registers, and each of the six subviews (memory inbox, promotion queue, contradiction queue, stale view, evidence inspector, event trace, retrieval explanation, consolidation queue, indexing health, workspace graph health) mounts and renders without throwing. Spec §Testing Requirements lists "extension compile/UI smoke tests" as a required test family; this task makes that test family green for the Phase 10 deliverables. Without it, regressions in webview wiring would land unnoticed because compile + lint cannot catch runtime mount failures.

## Steps

1. Read `extension/package.json` to confirm the test script `npm test` maps to `node ./out/test/runTest.js`. If the runner entry point does not exist, this task is responsible for creating it.
2. Create `extension/src/test/runTest.ts` exporting the standard VS Code `@vscode/test-electron` runner entry. It downloads VS Code if needed, launches it with the extension under test loaded, runs the Mocha suite from `extension/src/test/suite/index.ts` (or equivalent index file), and exits with the suite's pass/fail code.
3. If `extension/src/test/suite/index.ts` does not yet exist (check `extension/src/test/`), add a minimal Mocha entry that registers `review.test.ts` and any pre-existing tests so this task does not regress prior coverage.
4. Create `extension/src/test/review.test.ts` covering:
   - **Activation**: `vscode.extensions.getExtension('lattice.lattice')!.activate()` returns successfully; `vscode.commands.getCommands(true)` includes `lattice.openReviewPanel`.
   - **View registration**: After activation, `vscode.window.registerWebviewViewProvider` has been called for `lattice.reviewPanel` (assert by attempting `vscode.commands.executeCommand('lattice.reviewPanel.focus')` and observing no error).
   - **Subview render: memory inbox**: Open the review panel, route to the inbox subview, assert the webview HTML contains the inbox container element (queried by `data-testid="review-memory-inbox"` per `ui-specification.md` §16) without throwing.
   - **Subview render: promotion queue**: Route to the promotion queue, assert `data-testid="review-promotion-queue"` is present.
   - **Subview render: contradiction queue**: Assert `data-testid="review-contradiction-queue"` is present.
   - **Subview render: stale view**: Assert `data-testid="review-stale-view"` is present.
   - **Subview render: evidence inspector**: Open with a mock memory id, assert `data-testid="review-evidence-inspector"` is present.
   - **Subview render: event trace**: Assert `data-testid="review-event-trace"` is present.
   - **Subview render: retrieval explanation**: Open with a mock request id, assert `data-testid="review-retrieval-explanation"` is present.
   - **Subview render: consolidation queue**: Assert `data-testid="review-consolidation-queue"` is present.
   - **Subview render: indexing health**: Assert `data-testid="review-indexing-health"` is present.
   - **Subview render: workspace graph health**: Assert `data-testid="review-workspace-graph-health"` is present.
   - **No throw on missing data**: For every subview, with the RPC bridge stubbed to return an empty array, assert the subview mounts and renders the documented empty-state string (per `ui-specification.md` §8.3) without throwing.
   - **No throw on bridge error**: For every subview, with the RPC bridge stubbed to reject, assert the subview mounts and renders the error banner without throwing, and that `vscode.window.showErrorMessage` was called (mock or spy).
5. Use a thin stub of `ReviewRpcBridge` injected via a test-only export from `extension/src/review/reviewPanel.ts` (add a `setBridgeForTests` hook if not already present from T71). Do not mock VS Code's API — use the real `@vscode/test-electron` runner.
6. Run the suite locally with `cd extension && npm install && npm run compile && npm test`. Resolve every failure before stopping. Capture the suite output and confirm every named test above runs and passes.
7. Confirm `cd extension && npm run lint` passes with zero new warnings introduced by the test files (lint must include the `src/test` directory).

## Coding-standard checks

- File length ≤800 lines per file.
- Function length ≤50 lines (each `it(...)` block ≤30 lines per `coding.md` §Hard limits "Test length"). Setup factored into beforeEach helpers.
- One test per behavior, named for the behavior (e.g. `it('mounts the memory inbox without throwing')`), per `coding.md` §Tests as documentation.
- Integration tests prefer real collaborators — use the real `@vscode/test-electron` runner; mock only the RPC bridge (the process boundary to the daemon).
- No `TODO`, `FIXME`, `XXX`, commented-out code, or unjustified `// eslint-disable`.
- No silent error handling — every `await` either propagates to Mocha's failure path or is wrapped in `try/catch` with an explicit assertion.
- Doc citation: test comments cite `## Testing Requirements` for the smoke-test family requirement and `## 10. Human Review Surface` for the subview catalog (per `lattice/CLAUDE.md` Markdown Heading References).
