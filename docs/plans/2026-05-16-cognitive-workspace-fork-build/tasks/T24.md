# T24 — Phase 3 — Memory graph tests (links, contradiction, supersession, stale, replay)

**Phase:** 3
**Type:** tests
**Model class:** balanced
**Depends on:** T19, T20, T21, T22, T23
**Spec anchor:** [§Phase 3: Memory Graph Storage](../../2026-05-16-cognitive-workspace-fork-plan.md#phase-3-memory-graph-storage)
**Standards:** Cadres coding standard; Lattice project rules.

## Goal

This task proves the Phase 3 memory graph behaves correctly under the conditions the spec calls out: contradiction creates the right link records and transitions, supersession chains preserve provenance and produce the right state across the network, stale state propagates after graph changes, and the entire memory state can be reconstructed by replaying the event log from a fresh DB. Without these tests, the Phase 3 Definition of Done cannot be claimed and R25 cannot certify the substrate.

## Steps

1. In `memory_graph/contradiction_tests.rs`, write tests covering contradiction semantics:
   - create two memories A and B; add a `Contradicts` link from B to A; assert A.verification_status transitions to `Contradicted` and a `MemoryUpdated` event is emitted with `evidence_event_id` pointing at the link's evidence event.
   - create a `CounterMemory` C that explicitly counters A (CounterMemory is a class, not a link, per spec); assert A transitions to `Contradicted` AND C exists as a queryable first-class memory with its own evidence, scope, and verification status (assert C is not just an edge — read C via `MemoryStore::get`).
   - assert a CounterMemory can itself be superseded or invalidated independently of its target.
   - assert a `Contradicts` link from a low-confidence source does not flip a high-confidence target if confidence-weighted policy rejects it; the link is still recorded but the status does not transition. Document the policy in the test.
2. In `memory_graph/supersession_tests.rs`, write tests covering supersession semantics:
   - create A; create B with a `Supersedes` link to A; assert A.verification_status transitions to `Superseded` and A.superseded_by points at B.
   - create a chain A → B → C; assert each prior memory is in `Superseded` and the chain is traversable via `memory_links` queries; assert no cycle is allowed (`Supersedes` link from C to A returns a typed error).
   - assert that a query for "current claim" walks supersession links to the latest non-superseded successor; assert that historical lookup of A returns A as it existed before being superseded.
3. In `memory_graph/replay_tests.rs`, write tests covering replay:
   - record a sequence of memory creates, updates, transitions, link additions, and invalidations via the public store APIs; capture every emitted event via `EventReader`.
   - open a fresh DB; replay the event log into a new `MemoryStore`; assert the resulting state is byte-for-byte equivalent to the original (every `memories` row, every `memory_links` row, every `memory_evidence` row matches; assert via row-count + content-hash).
   - take a snapshot (T16) at the midpoint; replay snapshot + tail events; assert the same state as full replay.
   - replay over a corrupted event (use T17's corruption fixture) returns a typed error; the replayed DB is left in a consistent partial state (transaction boundaries respected) and the failure is logged.
   - assert that stream classification (T21) of replayed memories matches the original: a `WorkflowOutcome` memory created in the original DB is also classified `WorkflowEpisodes` after replay.
4. Add a stale-state test in `replay_tests.rs` (or a dedicated module if it grows): create a memory referencing file F; simulate F changing (insert an `InvalidationTrigger`-firing event); call the verification trigger path (placeholder if Phase 7 has not built it — for this task, simulate via `transition_status(Stale)`); assert the memory.verification_status is `Stale` and that subsequent reads through a scope filter mark it as stale in the response. (Full incremental verification is Phase 7; this task asserts the state representation works.)
5. Add a links-coverage test in `contradiction_tests.rs` (or split): exercise every one of the 11 link types (T20) end-to-end: insert, retrieve via `get_links_from` and `get_links_to`, delete (where allowed), and assert the right events are emitted. Use a `match` over `MemoryLinkType` with no `_` arm so adding a new link type forces this test to be extended.
6. Use temp-DB fixtures per test (T17 pattern); no shared state between tests.

## Coding-standard checks

- File length ≤800 lines per file.
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10.
- Test length ≤30 lines per test; extract fixture builders into a `tests_common.rs` module under `memory_graph/` so test bodies remain assertion-dominant.
- One test per behavior; names describe the behavior (`test_counter_memory_is_first_class_record`, not `test_counter_1`).
- No silent error handling — every `Result` in test code asserted or `?`-propagated.
- No `TODO`, `FIXME`, commented-out code.
- For SQLite: temp DBs per test; no shared state.
- Use `tracing_subscriber::fmt::try_init()` at the top of replay tests so failures include the full event-emission trail.
