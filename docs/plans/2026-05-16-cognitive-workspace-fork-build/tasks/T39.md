# T39 — Phase 6 — Consolidation job runtime + proposal model (no silent writes)

**Phase:** 6
**Type:** backend
**Model class:** advanced
**Depends on:** R38
**Spec anchor:** [§Consolidation Engine](../../2026-05-16-cognitive-workspace-fork-plan.md#6-consolidation-engine), [§Phase 6: Consolidation Engine](../../2026-05-16-cognitive-workspace-fork-plan.md#phase-6-consolidation-engine), [§Storage Design](../../2026-05-16-cognitive-workspace-fork-plan.md#storage-design)
**Standards:** Cadres coding standard; Lattice project rules (`/home/pete/cadres/lattice/CLAUDE.md`, `AGENTS.md`).

## Goal

This task stands up the consolidation engine's runtime kernel and the proposal model on which every later Phase 6 job depends. It introduces the `consolidation_jobs` table from spec §Storage Design, the bounded job queue, and a strict invariant that no consolidation job — deterministic or LLM-driven — writes durable memory directly. Every job emits a `ConsolidationProposal` record that requires explicit `apply` or `reject` before any memory state changes. Without this kernel, the LLM-driven jobs in T42 would be free to silently mutate memory, violating spec §Non-Negotiable Product Properties and the §Opaque Memory Mutation risk control.

## Spec excerpts that drive this task

> "No consolidation job may silently rewrite high-scope memory without preserving provenance and prior state."

> "each LLM-driven job produces a proposal record, not a direct write; proposals require explicit apply or reject before altering durable memory"

> "consolidation queue depth must be bounded; when the queue is full, new jobs are dropped with a log warning rather than stalling the daemon"

> "Every background consolidation pass is recoverable, replayable, and observable." (§Non-Negotiable Product Properties)

> Core tables include `consolidation_jobs` (§Storage Design).

## Steps

1. Read spec §Consolidation Engine, §Phase 6, and §Storage Design in full; record the proposal-only invariant verbatim in the top-of-module doc comment on `consolidation/mod.rs`.
2. Add `daemon/crates/lattice-core/src/consolidation/mod.rs` re-exporting `proposal`, `queue`, and the `ConsolidationJobRuntime` entry point. The module doc comment must cite the exact `## 6. Consolidation Engine` and `## Storage Design` headings.
3. Author `consolidation/schema.sql` defining the `consolidation_jobs` table (columns: `job_id PK`, `workspace_id`, `kind`, `mode` ∈ {`synchronous_post_task`, `background`, `manual_review`, `replay`}, `status` ∈ {`queued`, `running`, `proposed`, `applied`, `rejected`, `failed`, `dropped`}, `enqueued_at`, `started_at`, `finished_at`, `proposal_id NULLABLE`, `error_kind NULLABLE`, indexes on `(workspace_id, status)` and `(kind, status)`) plus a `consolidation_proposals` table (columns: `proposal_id PK`, `job_id FK`, `target_memory_id NULLABLE`, `proposal_kind`, `prior_state JSON`, `proposed_state JSON`, `evidence JSON`, `decided_at NULLABLE`, `decision` ∈ {`pending`, `applied`, `rejected`}, `decided_by NULLABLE`).
4. In `consolidation/proposal.rs`, define `pub struct ConsolidationProposal { proposal_id, job_id, target: ProposalTarget, prior_state, proposed_state, evidence }`, the `ProposalKind` enum (e.g. `CreateMemory`, `UpdateMemory`, `MarkStale`, `Supersede`, `Demote`, `Refresh`), and the `ProposalDecision` enum. Implement `apply()` and `reject()` methods that mutate `consolidation_proposals.decision`, emit a `MemoryConsolidated` event with prior + proposed state preserved, and only then call the memory store API to materialize the change. `apply` MUST be a no-op if `decision != pending`.
5. In `consolidation/queue.rs`, implement `BoundedJobQueue` with a configurable `max_depth` (default from `LatticeConfig`, no hard-coded literals). When `enqueue` is called and the queue is full, mark the job as `dropped` in `consolidation_jobs`, emit a `tracing::warn!` log including `workspace_id`, `kind`, and current depth, and return an `EnqueueOutcome::Dropped { reason }` — never block. Expose `depth()`, `pop()`, and `drain_for_shutdown()` for observability.
6. Implement `ConsolidationJobRuntime` with `submit(job_spec)`, `run_due()` (polled by the daemon's scheduler), `decide(proposal_id, decision)` and `replay_from(event_id)`. The runtime never writes memory; it only writes proposals and dispatches their decisions.
7. Wire `mod consolidation;` into `daemon/crates/lattice-core/src/lib.rs` (alphabetical order) and register `consolidation/schema.sql` in the storage migration runner so the tables are created on daemon start.
8. In `consolidation/proposal_tests.rs`, write tests that: (a) a deterministic job emits a proposal but does not mutate memory, (b) `apply` materializes the change and writes a `MemoryConsolidated` event with prior + proposed state, (c) `reject` leaves memory unchanged and records the decision, (d) double-apply is a no-op, (e) the queue drops jobs once depth exceeds the bound and emits the warning log (capture via a tracing subscriber fixture), (f) the `consolidation_jobs` schema round-trips under the migration runner against a temp DB.

## Coding-standard checks

- File length ≤800 lines per file. Split `proposal.rs` or `queue.rs` if any approaches the ceiling (e.g. extract a `decision.rs` sub-module).
- Function length ≤50 lines, nesting ≤3, cyclomatic ≤10. `BoundedJobQueue::enqueue` and `ConsolidationProposal::apply` are the hot spots — keep them flat with early returns.
- Single source of truth: proposals MUST route writes through the existing memory store API (`crates/lattice-core/src/memory/`) — do not introduce a parallel write path.
- Error handling: queue-full and apply-on-non-pending are normal control flow (typed `EnqueueOutcome` / `ApplyOutcome`), not panics. No silent `.ok()` drops on storage results.
- Naming: `ConsolidationProposal`, `ProposalDecision`, `BoundedJobQueue` — intent over mechanism; no generic `Manager`/`Helper` suffixes.
- Schema parity: every column on `consolidation_jobs` and `consolidation_proposals` has a typed field on the Rust struct; nullable columns map to `Option<…>`.
- No `TODO`, `FIXME`, `XXX`, commented-out code, or unjustified `#[allow(...)]`.
- Observability: every proposal lifecycle transition emits a `tracing` span carrying `workspace_id`, `job_id`, `proposal_id`, and outcome. Queue drops log at `warn` per spec.
- Doc citation: top-of-module doc comments cite `## 6. Consolidation Engine` and `## Storage Design` headings; per-method comments reference these headings only where behavior is non-obvious (per `lattice/CLAUDE.md` § Markdown Heading References).
