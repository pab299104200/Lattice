## Goal

This task delivers pipeline steps 9 and 10: deduplicate and compress the ranked candidate set, then return a compact bundle in which **every result carries an `inclusion_reason` and an `expansion_handle`**. Per spec §Phase 4 scope constraint, the shaper's output schema must be forward-compatible with the Phase 5 working-memory checkpoints — Phase 5 layers state semantics on top of these bundles without rewriting the Phase 4 schema. The inclusion-reason discipline is the non-negotiable property the R33 review will check: no bundle ships a result without one, and no result ships an expansion handle that points to a non-existent identity.

## Steps

1. Re-read spec §Retrieval Engine pipeline steps 9–10, §Non-Negotiable Product Properties bullets on inclusion reasons and expansion handles, and §Phase 4 scope constraint on forward compatibility with Phase 5 working memory.
2. Define the bundle schema in `shaper.rs`: `RetrievalBundle { task_id, intent_summary, anchors_summary, results: Vec<BundleResult>, diagnostics: Option<RankingDiagnostics>, budget_report }`. `BundleResult { identity, kind, headline, snippet, inclusion_reason, expansion_handle, source, score }`. `inclusion_reason` and `expansion_handle` are non-optional on `BundleResult`; the type system enforces the spec invariant.
3. Implement `daemon/crates/lattice-core/src/retrieval_v1/inclusion_reasons.rs`: a single small module that converts a `RankedCandidate` into a compact `inclusion_reason` string (≤120 chars) summarizing the top-N contributing signals. In diagnostic mode the full per-signal list is carried separately via `RetrievalBundle.diagnostics`. The compact summary is deterministic given the same inputs (no random tie-break).
4. Implement deduplication: when two candidates resolve to the same identity, merge their `signal_scores` (take max per signal), union their source set, and keep the highest-scoring `inclusion_reason`. Document the merge policy inline with `## 7. Retrieval Engine` citation.
5. Implement compression: enforce a global token-budget cap on the bundle by trimming `snippet` length first, then dropping the lowest-scoring trailing results, then setting `BudgetReport::truncated = true`. Never drop a pinned-identity result (the pin set is supplied via a `ShaperContext.pins: HashSet<Identity>` to keep Phase 5 forward compatibility — T35 will populate this).
6. Generate every `expansion_handle` through the existing `expand_context` handle generator (`rpc/context_cache.rs` / Phase 1 follow-up-handle helper). Assert in debug builds that every handle round-trips through the resolver back to the same identity; assertion failure is a panic, because a bad handle in a shipped bundle is a contract violation.
7. Forward-compatibility for Phase 5: place `BundleResult` and `RetrievalBundle` in a `pub mod schema` re-exported from `retrieval_v1::mod` so T34's `working_memory::state` can include the bundle verbatim under `selected_memories` and record dropped items under `excluded_memories` with the same `BundleResult` shape. Document this contract with a doc comment citing `## 5. Working Memory` and `## Phase 5: Working Memory`.
8. Add `daemon/crates/lattice-core/src/retrieval_v1/shaper_tests.rs` covering: every `BundleResult` has a non-empty `inclusion_reason` (string length ≥1, ≤120 in compact mode); every `expansion_handle` resolves back to the original identity; deduplication merges signal scores correctly; compression respects budget without dropping pinned results; diagnostic mode populates `diagnostics`, compact mode does not; serde round-trip preserves the schema unchanged so a Phase 5 checkpoint can include a bundle byte-for-byte; truncation flag is set when results are dropped.
9. Run `cd daemon && cargo build --release` and the verification test command; fix any clippy warnings before stopping.
