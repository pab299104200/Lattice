## Goal

This task delivers pipeline step 8 — the scorer — and the diagnostic mode that makes the scorer auditable per spec §Ranking Complexity. The scorer must apply every ranking signal the spec enumerates, expose each signal as a named, inspectable feature, and emit both scores and human-readable reasons under a diagnostic mode. Compact mode emits only enough explanation for an assistant to trust the result; diagnostic mode emits the full per-signal breakdown. The scorer must remain feature-based — no learned policy is acceptable in Phase 4 — so retrieval ranking stays explainable for the lifetime of this phase.

## Steps

1. Re-read spec §Retrieval Engine "Ranking signals" and §Ranking Complexity in full; copy the thirteen-signal list verbatim into a doc-comment table at the top of `scoring.rs`.
2. Define the data structures: `SignalScore { signal: SignalKind, raw: f32, weighted: f32, reason: String }`, `RankedCandidate { candidate: Candidate, total_score: f32, signal_scores: Vec<SignalScore>, inclusion_reason: String }`, `ScoringWeights` (one weight per signal, defaulting from a documented `RetrievalProfile`), and `DiagnosticMode { Compact, Diagnostic }`.
3. Implement one pure-function evaluator per signal in `scoring.rs`, each ≤50 lines, each returning a `SignalScore` with both score and reason. The thirteen evaluators are: `task_type_compatibility`, `graph_proximity`, `exact_identifier_match`, `semantic_similarity`, `verification_status`, `freshness`, `scope`, `evidence_strength`, `contradiction_or_supersession_state`, `past_usefulness`, `recent_successful_reuse`, `user_preference_compatibility`, `token_cost`. Each MUST be present; missing data yields a score of 0 and a reason like `"no <field> available; signal skipped"`, never a panic or silent skip.
4. Implement `score_candidates(candidates: Vec<Candidate>, intent: &IntentClassification, anchors: &[ResolvedAnchor], weights: &ScoringWeights, mode: DiagnosticMode, ctx: &ScoringContext) -> Vec<RankedCandidate>` that calls each evaluator, sums weighted scores, fills `inclusion_reason` with a compact summary in `Compact` mode and the full per-signal list in `Diagnostic` mode, then sorts descending.
5. Implement `daemon/crates/lattice-core/src/retrieval_v1/diagnostic.rs`: the public API for diagnostic mode. Exposes `RankingDiagnostics { intent, anchors, candidates_per_source, ranked: Vec<RankedCandidate>, weights, budget_exhaustion_flags }` plus serde derivation, so T31 (shaper) and T36 (MCP working-memory inspector) can hand the diagnostics straight to the caller without further transformation.
6. Honor spec §Stale Memory Leakage by ensuring `verification_status` and `contradiction_or_supersession_state` apply a hard penalty (not just a soft weight) when status is `stale`, `contradicted`, or `superseded`, so these candidates cannot rank above trusted ones except when diagnostics explicitly request them. The penalty value and policy live in `ScoringWeights` with inline documentation citing `## Stale Memory Leakage`.
7. Add `daemon/crates/lattice-core/src/retrieval_v1/scoring_tests.rs` covering: each of the thirteen signals is evaluated for a representative candidate; signal absence yields a `0.0` score and a documented reason (no panic); stale/contradicted candidates rank below trusted candidates with the same raw match; diagnostic mode round-trips signal scores and reasons through serde; compact mode produces a non-empty single-line inclusion reason; weight overrides change the ranking deterministically; user-preference compatibility raises the score of candidates matching a stored preference and lowers candidates conflicting with one.
8. Run `cd daemon && cargo build --release` and the verification test command; fix any clippy warnings before stopping.
