# MCP Tool Reference

This document is the canonical Phase 8 MCP tool listing for the cognitive workspace fork. It implements the contract requested by [## MCP Surface](../plans/2026-05-16-cognitive-workspace-fork-plan.md#mcp-surface), [## MCP Tool Contract Principles](../plans/2026-05-16-cognitive-workspace-fork-plan.md#mcp-tool-contract-principles), and [## Phase 8: Workflow Engine V2](../plans/2026-05-16-cognitive-workspace-fork-plan.md#phase-8-workflow-engine-v2). Collapse decisions and shim rationale are recorded in [MCP Surface Audit](./2026-05-16-mcp-surface-audit.md). Compatibility and removal rules come from [MCP Compatibility Policy](./2026-05-16-mcp-compatibility-policy.md).

Implementation source of truth: advertised tools are assembled in `daemon/crates/lattice-daemon/src/rpc/mcp.rs::handle_tools_list`; callable names are dispatched in `daemon/crates/lattice-daemon/src/rpc/mcp.rs::handle_tools_call`.

## Render modes

[## MCP Surface](../plans/2026-05-16-cognitive-workspace-fork-plan.md#mcp-surface) requires compact rendering, full structured JSON, context handles, stable expansion targets, budget controls, and diagnostic explanations where useful. [## MCP Tool Contract Principles](../plans/2026-05-16-cognitive-workspace-fork-plan.md#mcp-tool-contract-principles) requires compact/full render choice and structured payloads.

Workflow tools use `render=json|markdown|hybrid` for delivery shape and `mode=auto|compact|full` when a workflow bundle supports response density. `get_context_capsule` keeps its older `mode=full|focused` discovery control. Memory v2 administrative tools use `render_mode=compact|full|diagnostic`; `verify_explain_memory` additionally uses `mode=verify|explain|verify_and_explain`.

Diagnostic render modes are reserved for traceability: they may include check traces, ranking reasons, payload hashes, spilled-payload row ids, or excluded candidates. Compact modes must remain bounded enough for repeated assistant use.

## Expansion handles

Workflow responses that return bundles store context handles through `context_cache` and expose `suggested_expand` targets. `expand_context` is the canonical follow-up tool and accepts a prior `handle` plus a `focus` such as a file, symbol, test, memory, or stable identity. Memory-bearing responses expose memory or event expansion handles where useful: `get_task_memory`, `verify_explain_memory`, `get_event_trace`, and `inspect_working_memory` all return handles for focused follow-up.

Handles must stay workspace-bound and must not bypass the path scoping, ignored-directory rules, or memory scoping required by the repo contract. Expired, missing, or invalid handles should fail with actionable errors rather than silently returning unrelated context.

## Budget controls

Budget controls are part of the MCP contract in [## MCP Surface](../plans/2026-05-16-cognitive-workspace-fork-plan.md#mcp-surface). Workflow bundle tools accept `budget=tiny|compact|full`, `max_tokens`, and `wire_format=standard|dense` where listed. The daemon constants are `tiny=260`, `compact=850`, and `full=2600` approximate workflow token caps unless a stricter `max_tokens` is supplied.

Other tools expose narrower controls: `limit` bounds list/search/event outputs, `hops` and `max_depth` bound graph traversal, `budget_tokens` bounds `get_task_memory`, `budget_ms` bounds synchronous consolidation, cursor pagination bounds `get_event_trace`, and render modes bound diagnostic detail.

## Deprecation policy

Deprecation follows [## Backward compatibility](./2026-05-16-mcp-compatibility-policy.md#backward-compatibility) and [## Shim removal protocol](./2026-05-16-mcp-compatibility-policy.md#shim-removal-protocol). A redesigned tool must keep maintained clients working for one full numbered phase cycle. The legacy request shape must remain accepted, responses must remain parseable, and new identity/event/ranking/memory fields must be additive unless a shim explicitly documents a successor contract.

The Phase 8 advertised deprecated shims are `apply_memory_evolution`, `verify_memory`, and `explain_memory`. The callable-only legacy aliases are `query_context`, `blast_radius`, `get_file_context`, `store_memory`, and `recall_memories`. Removal requires a phase boundary, migrated first-party docs/fixtures/prompts/cached examples, compatibility tests, and an architecture-doc update in the same change.
