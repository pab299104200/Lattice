# Operator Runbook

This runbook is the daily-operations companion to the broader [Operator Guide](./2026-05-16-operator-guide.md#daily-operations). It is driven by [## Phase 11: Hardening](../plans/2026-05-16-cognitive-workspace-fork-plan.md#phase-11-hardening), [## Storage Design](../plans/2026-05-16-cognitive-workspace-fork-plan.md#storage-design), [### 3. Event Log](../plans/2026-05-16-cognitive-workspace-fork-plan.md#3-event-log), and [## Documentation Requirements](../plans/2026-05-16-cognitive-workspace-fork-plan.md#documentation-requirements). Use the paired [Recovery Playbook](./2026-05-16-recovery-playbook.md#recovery-procedures) for corruption, replay, rollback, and incident response.

## Daily operations

1. Start the daemon by opening the workspace in VS Code and confirming the extension launches `extension/bin/lattice`, as described in [Operator Guide](./2026-05-16-operator-guide.md#installation).
2. Stop the daemon for maintenance with `pkill -f lattice`, then confirm it is gone with `pgrep -fa lattice`.
3. Open the review panel and check `consolidationQueueView`, `indexingHealthView`, and `workspaceGraphHealthView`, which are the Phase 10 health surfaces documented in [Extension Review UI Guide](./2026-05-16-extension-review-ui-guide.md#consolidation-indexing-and-graph-health).
4. Read the Phase 9 metrics report with `lattice_report` or `get_memory_metrics`, and compare the current workspace against the required signals in [Metrics Report Architecture](../architecture/2026-05-16-metrics-report.md#signal-definitions) and [## Measurable Success Criteria](../plans/2026-05-16-cognitive-workspace-fork-plan.md#measurable-success-criteria).
5. Review accepted and rejected promotion proposals at least weekly in the review panel queues so high-scope memory changes remain auditable under [### 6. Consolidation Engine](../plans/2026-05-16-cognitive-workspace-fork-plan.md#6-consolidation-engine).
6. Review contradiction proposals, stale memory, and verification labels before trusting a memory result in operator-facing workflows, per [### 8. Verification Engine](../plans/2026-05-16-cognitive-workspace-fork-plan.md#8-verification-engine).

## Deploy sequence

The canonical deploy sequence from [CLAUDE.md](../CLAUDE.md#deploy) is:

```bash
pkill -f lattice && sleep 2
cp daemon/target/release/lattice extension/bin/
cp daemon/target/release/lattice ~/.vscode/extensions/lattice.lattice-0.1.0/bin/
```

1. Run `pkill -f lattice`, then wait for the required `sleep 2` so the old binary releases its file handles before copy.
2. Copy the fresh daemon binary into `extension/bin/`.
3. Copy the same binary into `~/.vscode/extensions/lattice.lattice-0.1.0/bin/`.
4. Confirm the new binary is the only running daemon with `pgrep -fa lattice`.
5. Re-open the Lattice review panel from the VS Code activity bar and confirm it reconnects without a stale-daemon error.
6. Re-open `indexingHealthView` and `workspaceGraphHealthView` and confirm they refresh against the new process.

## Health checks

The health views are bounded review surfaces, not ad hoc debugging tools, per [### 10. Human Review Surface](../plans/2026-05-16-cognitive-workspace-fork-plan.md#10-human-review-surface). If a field is shown as `Not reported`, treat it as yellow until the daemon reports it authoritatively; if an incident is already open, treat it as red.

| Indicator | Green | Yellow | Red | Why it matters |
|---|---|---|---|---|
| Parser failure rate | `<1%` failed parses in `indexingHealthView` and no recurring `lastError` | `1-5%` failed parses or one recurring parser error family | `>5%` failed parses, repeated parser failures on the same language, or indexing stalls | [### 2. Workspace Graph](../plans/2026-05-16-cognitive-workspace-fork-plan.md#2-workspace-graph) requires bounded, trustworthy graph traversal; [## Phase 11: Hardening](../plans/2026-05-16-cognitive-workspace-fork-plan.md#phase-11-hardening) requires partial-index handling. |
| Vector index freshness | `0` stale embeddings or a fresh rebuild within the last workday | stale embeddings are present but clearly bounded and falling after refresh | stale embeddings keep growing, `averageFreshness` is old across multiple refreshes, or rebuild timestamps stop moving | [### 7. Retrieval Engine](../plans/2026-05-16-cognitive-workspace-fork-plan.md#7-retrieval-engine) depends on freshness-aware ranking; stale vector state degrades explainable retrieval. |
| FTS row count | row counts are non-zero and roughly in family with current files/docs/memory volume | row counts drift unexpectedly after a large re-index but recover after refresh | row counts collapse to zero, orphan rows spike, or rebuild timestamps stop moving | [## Storage Design](../plans/2026-05-16-cognitive-workspace-fork-plan.md#storage-design) treats FTS as a rebuildable accelerator; large drift means retrieval can go empty or misleading. |
| Event log ingestion rate | event counts rise during active work and no unexplained spillover growth appears | counts are flat during expected operator activity or spillover growth needs investigation | active workflows produce no new events, or spillover rows grow without matching workflow volume | [### 3. Event Log](../plans/2026-05-16-cognitive-workspace-fork-plan.md#3-event-log) requires append-only replayable history; [### Phase 2: Event Log Substrate](../plans/2026-05-16-cognitive-workspace-fork-plan.md#phase-2-event-log-substrate) requires useful failure events. |
| Compaction snapshot age | newest snapshot is `<=24h` old in an actively used workspace | newest snapshot is `>24h` and `<=7d` old, or compaction is skipped during low activity | no valid recent snapshot exists, the newest snapshot is `>7d` old, or compaction repeatedly fails | [## Storage Design](../plans/2026-05-16-cognitive-workspace-fork-plan.md#storage-design) requires versioned, independently readable compaction snapshots for bounded recovery time. |

## Alerts and response

1. Queue depth at bound.
Open `consolidationQueueView`. Check whether `currentDepth` equals `maxDepth`, inspect the oldest visible jobs, then inspect daemon stderr or journal logs for queue-bound warnings from the consolidation scheduler. Escalate to the daemon maintainer if the queue remains full for more than one compaction interval or if high-scope proposals stop appearing.

2. Dropped consolidation jobs.
Open `consolidationQueueView` and use the dropped-job banner to open failure evidence. Inspect the event trace for the affected session and the daemon log target that recorded the dropped job. Escalate immediately when dropped jobs affect repo- or organization-scoped memory because [### 6. Consolidation Engine](../plans/2026-05-16-cognitive-workspace-fork-plan.md#6-consolidation-engine) requires auditable proposal flow.

3. Broken references.
Open `workspaceGraphHealthView` and inspect the `brokenReferences` panel. Open the referenced row, then inspect event-trace evidence and the underlying file/symbol identity. Escalate when the same missing identity appears across multiple recent events because replay safety in [### 3. Event Log](../plans/2026-05-16-cognitive-workspace-fork-plan.md#3-event-log) depends on stable references.

4. Stale-edge spike.
Open `workspaceGraphHealthView` and inspect `staleEdges` and `orphanSymbols`, then compare the timing against the last full rescan in `indexingHealthView`. Inspect daemon logs for parser or watcher errors. Escalate if the spike persists after a full rescan because [### 2. Workspace Graph](../plans/2026-05-16-cognitive-workspace-fork-plan.md#2-workspace-graph) requires freshness queries and reliable dependency edges.

5. Hot-path P99 budget breach.
Run the Phase 9 metrics report and compare it with [Metrics Report Architecture](../architecture/2026-05-16-metrics-report.md#thresholds), then inspect daemon tracing for the slow path that breached budget. If event-capture latency is implicated, inspect compaction and spillover activity under [### Phase 2: Event Log Substrate](../plans/2026-05-16-cognitive-workspace-fork-plan.md#phase-2-event-log-substrate). Escalate when the breach persists across repeated runs or crosses workspaces because the system is no longer meeting the production bar in [## Phase 11: Hardening](../plans/2026-05-16-cognitive-workspace-fork-plan.md#phase-11-hardening).

Any alert that requires replay, quarantine, rollback, or corruption handling moves immediately to the [Recovery Playbook](./2026-05-16-recovery-playbook.md#recovery-procedures).

## Memory hygiene

1. Review the promotion queue weekly and accept or reject every mature proposal with a recorded reason.
2. Review the contradiction queue weekly and resolve conflicts before stale or contradicted memories accumulate.
3. Run a stale-memory audit weekly with the review panel stale view or `list_stale_memories`.
4. Review usefulness and regression signals weekly with `get_memory_metrics` or `lattice_report`, focusing on memory inclusion precision, stale-memory surfaced rate, contradiction missed rate, and tests recommended versus tests needed.
5. Re-run verification on memory that is high-scope, recently contradicted, or tied to changed files before promoting it.

## Backups

Back up the entire `.lattice/` state as one unit so replay, quarantine, and rollback all have consistent inputs. The minimum set is:

1. `graph.db`
2. `memories.db`
3. `events.db`
4. `.lattice/snapshots/`
5. vector-index files or directories used by the active workspace

Backup rules:

1. Take a scheduled backup at least daily for active workspaces.
2. Take an additional backup before migrations, compaction-policy changes, or manual recovery.
3. Store checksums beside each backup artifact so restore can prove integrity before daemon restart.
4. Keep at least one backup from before the newest successful compaction snapshot.

Restore rules:

1. Stop the daemon before restoring any `.lattice/` artifact.
2. Restore the full `.lattice/` set from the same backup point instead of mixing dates.
3. Continue with the verification and replay checks in [Recovery Playbook](./2026-05-16-recovery-playbook.md#replay-from-snapshot).
