This runbook is the daily-operations companion to the broader [Operator Guide](./2026-05-16-operator-guide.md#daily-operations). It is driven by [## Phase 11: Hardening](../plans/2026-05-16-cognitive-workspace-fork-plan.md#phase-11-hardening), [## Storage Design](../plans/2026-05-16-cognitive-workspace-fork-plan.md#storage-design), [### 3. Use the paired [Recovery Playbook](./2026-05-16-recovery-playbook.md#recovery-procedures) for corruption, replay, rollback, and incident response.

## Daily operations

1. Start Lattice through an MCP client configured to run `daemon/target/release/lattice --stdio --workspace <workspace>`, as described in [Operator Guide](./2026-05-16-operator-guide.md#installation). The `--stdio` process is a lightweight proxy; it starts or reuses the long-lived daemon automatically.
2. Stop the daemon and any active proxies for maintenance with `pkill -f lattice`, then confirm they are gone with `pgrep -fa lattice`.
3. Run `index_status`, `get_memory_metrics`, and `get_event_trace` to confirm indexing health, memory/workflow signals, and event capture.
4. Keep the daemon resource envelope explicit: `LATTICE_MAX_LOADED_WORKSPACES` defaults to `8`, `LATTICE_WORKSPACE_IDLE_TTL_SECS` defaults to `1800`, and full background vector sync only runs when `LATTICE_ENABLE_BACKGROUND_VECTOR_SYNC=1`.
5. For daemon/proxy lifecycle debugging, inspect `~/.lattice/logs/lifecycle.jsonl` or set `LATTICE_LIFECYCLE_LOG_DIR` to redirect those JSONL records.
6. Read the Phase 9 metrics report with `lattice_report` or `get_memory_metrics`, and compare the current workspace against the required signals in [Metrics Report Architecture](../architecture/2026-05-16-metrics-report.md#signal-definitions) and [## Measurable Success Criteria](../plans/2026-05-16-cognitive-workspace-fork-plan.md#measurable-success-criteria).
7. Review accepted and rejected memory-evolution proposals at least weekly so high-scope memory changes remain auditable under [### 6. Consolidation Engine](../plans/2026-05-16-cognitive-workspace-fork-plan.md#6-consolidation-engine).
8. Review contradiction proposals, stale memory, and verification labels before trusting a memory result in operator-facing workflows, per [### 8. Verification Engine](../plans/2026-05-16-cognitive-workspace-fork-plan.md#8-verification-engine).

## Deploy sequence

The canonical daemon refresh sequence is:

```bash
pkill -f lattice && sleep 2
cd daemon && cargo build --release
```

1. Run `pkill -f lattice`, then wait for the required `sleep 2` so the old binary releases its file handles before copy.
2. Build the fresh daemon with `cd daemon && cargo build --release`.
3. Confirm no old daemon is still running with `pgrep -fa lattice`.
4. Restart the MCP client so it launches `daemon/target/release/lattice --stdio --workspace <workspace>` and the proxy starts or reconnects to the daemon.
5. Run `index_status` and confirm it reports the expected workspace and a fresh process.

## Health checks

Health checks use MCP responses and daemon logs. If a field is not reported by the daemon, treat it as yellow until an authoritative payload or log explains the state; if an incident is already open, treat it as red.

| Indicator | Green | Yellow | Red | Why it matters |
|---|---|---|---|---|
| Parser failure rate | `<1%` failed parses in `index_status` or daemon logs and no recurring `lastError` | `1-5%` failed parses or one recurring parser error family | `>5%` failed parses, repeated parser failures on the same language, or indexing stalls | [### 2. Workspace Graph](../plans/2026-05-16-cognitive-workspace-fork-plan.md#2-workspace-graph) requires bounded, trustworthy graph traversal; [## Phase 11: Hardening](../plans/2026-05-16-cognitive-workspace-fork-plan.md#phase-11-hardening) requires partial-index handling. |
| Vector index freshness | `0` stale embeddings or a fresh rebuild within the last workday | stale embeddings are present but clearly bounded and falling after refresh | stale embeddings keep growing, `averageFreshness` is old across multiple refreshes, or rebuild timestamps stop moving | [### 7. Retrieval Engine](../plans/2026-05-16-cognitive-workspace-fork-plan.md#7-retrieval-engine) depends on freshness-aware ranking; stale vector state degrades explainable retrieval. |
| FTS row count | row counts are non-zero and roughly in family with current files/docs/memory volume | row counts drift unexpectedly after a large re-index but recover after refresh | row counts collapse to zero, orphan rows spike, or rebuild timestamps stop moving | [## Storage Design](../plans/2026-05-16-cognitive-workspace-fork-plan.md#storage-design) treats FTS as a rebuildable accelerator; large drift means retrieval can go empty or misleading. |
| Event log ingestion rate | event counts rise during active work and no unexplained spillover growth appears | counts are flat during expected operator activity or spillover growth needs investigation | active workflows produce no new events, or spillover rows grow without matching workflow volume | [### 3. Event Log](../plans/2026-05-16-cognitive-workspace-fork-plan.md#3-event-log) requires append-only replayable history; [### Phase 2: Event Log Substrate](../plans/2026-05-16-cognitive-workspace-fork-plan.md#phase-2-event-log-substrate) requires useful failure events. |
| Compaction snapshot age | newest snapshot is `<=24h` old in an actively used workspace | newest snapshot is `>24h` and `<=7d` old, or compaction is skipped during low activity | no valid recent snapshot exists, the newest snapshot is `>7d` old, or compaction repeatedly fails | [## Storage Design](../plans/2026-05-16-cognitive-workspace-fork-plan.md#storage-design) requires versioned, independently readable compaction snapshots for bounded recovery time. |
| Resident workspace count | loaded workspace runtimes stay within expected active clients and idle eviction appears in logs | runtimes stay below `LATTICE_MAX_LOADED_WORKSPACES` but do not evict after the configured TTL | the daemon refuses new workspaces or resident runtimes grow without bound | Multi-workspace daemon mode must not trade process consolidation for unbounded graph/index residency. |

## Alerts and response

1. Queue depth at bound.
Inspect consolidation queue metrics through daemon output or metrics surfaces. Check whether `currentDepth` equals `maxDepth`, inspect the oldest visible jobs when exposed, then inspect daemon stderr or journal logs for queue-bound warnings from the consolidation scheduler. Escalate to the daemon maintainer if the queue remains full for more than one compaction interval or if high-scope proposals stop appearing.

2. Dropped consolidation jobs.
Inspect dropped-job evidence in daemon logs and `get_event_trace`. Escalate immediately when dropped jobs affect repo- or organization-scoped memory because [### 6. Consolidation Engine](../plans/2026-05-16-cognitive-workspace-fork-plan.md#6-consolidation-engine) requires auditable proposal flow.

3. Broken references.
Inspect graph-health output, event-trace evidence, and the underlying file/symbol identity for broken references. Escalate when the same missing identity appears across multiple recent events because replay safety in [### 3. Event Log](../plans/2026-05-16-cognitive-workspace-fork-plan.md#3-event-log) depends on stable references.

4. Stale-edge spike.
Inspect graph-health output for `staleEdges` and `orphanSymbols`, then compare the timing against the last full rescan reported by `index_status` or daemon logs. Inspect daemon logs for parser or watcher errors. Escalate if the spike persists after a full rescan because [### 2. Workspace Graph](../plans/2026-05-16-cognitive-workspace-fork-plan.md#2-workspace-graph) requires freshness queries and reliable dependency edges.

5. Hot-path P99 budget breach.
Run the Phase 9 metrics report and compare it with [Metrics Report Architecture](../architecture/2026-05-16-metrics-report.md#thresholds), then inspect daemon tracing for the slow path that breached budget. If event-capture latency is implicated, inspect compaction and spillover activity under [### Phase 2: Event Log Substrate](../plans/2026-05-16-cognitive-workspace-fork-plan.md#phase-2-event-log-substrate). Escalate when the breach persists across repeated runs or crosses workspaces because the system is no longer meeting the production bar in [## Phase 11: Hardening](../plans/2026-05-16-cognitive-workspace-fork-plan.md#phase-11-hardening).

Any alert that requires replay, quarantine, rollback, or corruption handling moves immediately to the [Recovery Playbook](./2026-05-16-recovery-playbook.md#recovery-procedures).

## Memory hygiene

1. Review memory-evolution proposals weekly and accept or reject every mature proposal with a recorded reason.
2. Review contradictions weekly with `list_memory_conflicts` and resolve conflicts before stale or contradicted memories accumulate.
3. Run a stale-memory audit weekly with `list_stale_memories`.
4. Review usefulness and regression signals weekly with `get_memory_metrics` or `lattice_report`, focusing on memory inclusion precision, stale-memory surfaced rate, contradiction missed rate, and tests recommended versus tests needed.
5. Re-run verification on memory that is high-scope, recently contradicted, or tied to changed files before promoting it.

## Backups

Back up the entire `.lattice/` state as one unit so replay, quarantine, and rollback all have consistent inputs. The minimum set is:

1. `graph.db`
2. `memories.db`
3. `events.db`
4. `.lattice/snapshots/`
5. vector-index files or directories used by the active workspace

Backup rules:

1. Take a scheduled backup at least daily for active workspaces.
2. Take an additional backup before migrations, compaction-policy changes, or manual recovery.
3. Store checksums beside each backup artifact so restore can prove integrity before daemon restart.
4. Keep at least one backup from before the newest successful compaction snapshot.

Restore rules:

1. Stop the daemon before restoring any `.lattice/` artifact.
2. Restore the full `.lattice/` set from the same backup point instead of mixing dates.
3. Continue with the verification and replay checks in [Recovery Playbook](./2026-05-16-recovery-playbook.md#replay-from-snapshot).
