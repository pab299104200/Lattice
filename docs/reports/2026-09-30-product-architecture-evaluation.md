# Lattice product & architecture evaluation

Date: 2026-09-30 (revised after a verification deep dive the same day). Method: read the shipped documentation (README, `docs/*`), then traced the daemon source (`daemon/crates/`) to compare claimed behavior against implemented behavior, with emphasis on the multi-worktree / multi-branch path where tools of this kind usually break. The central findings below were then re-verified by direct reading of the dispatch and git code and, where possible, by an on-disk git fixture. Evidence is cited by file:path. This is an assessment, not a change; no production code was modified.

### Verification status of each major claim

- **Two retrieval engines, agents use the weaker one** — VERIFIED by direct handler trace plus a zero-hit call-site search across the whole `lattice-daemon` crate (not inference). Strongest finding.
- **Divergent git-ref resolution across linked worktrees** — VERIFIED by reading both resolvers and reproduced empirically against a real `git worktree` fixture. The original write-up overstated it as a general "mistimed branch switch"; the precise, corrected statement is below.
- **GC starvation under worktree churn** — VERIFIED by reading the exact restart-on-generation-change logic; mitigations noted.
- **Name-based graph edges (indexing fidelity)** — NEW finding from reading the graph builder; was not in the first pass.
- **Full daemon runtime test** — NOT POSSIBLE in this environment (no `cargo`/`rustc`, no prebuilt binary). The git-layout failure mode was reproduced on disk with real git instead; everything else is from direct source reading.

## What Lattice is trying to be

A local, single-user engine that indexes a workspace into a code/doc/memory graph and serves *focused context* to coding agents over MCP and a CLI — "find the working set for a task, understand the impact of a change, carry verified lessons across sessions." Eight MCP verbs: `context`, `prepare_change`, `impact`, `diagnose`, `search`, `remember`, `recall`, `status`. Structural + lexical retrieval always; local embeddings (MiniLM via ONNX) optional. One long-lived daemon serves many workspaces; linked git worktrees share repository memory and immutable parsed/symbol/embedding objects while keeping per-checkout graphs.

The product thesis is sound and well-aimed: agents waste tokens rediscovering structure and repeat mistakes they've already made. A local graph + a disciplined memory with honest trust signals is a credible answer. The documentation is unusually honest — it repeatedly states what a signal does *not* prove (a loaded runtime is not full vector coverage; a hook firing is not adoption; stored prose is not a passed test). That intellectual honesty is a real asset and mostly matches the code.

## How it actually works (verified)

**Identity and storage** (`daemon/crates/lattice-daemon/src/workspace_identity.rs`). `WorkspaceIdentity::resolve` shells out to `git rev-parse --git-common-dir --git-dir --is-bare-repository`. `repository_id = sha256("repo" + canonical common-dir)` is the only memory-scope authority; `checkout_id = sha256(repository_id + 0x00 + checkout_root)`. Linked worktrees therefore collapse to one `repository_id` (shared common dir) but keep distinct `checkout_id`s — exactly the documented model, and asserted by a real-git worktree test. Storage home is `<primary>/.lattice` for normal/linked checkouts, `<common-dir>/lattice` for bare/separate-git-dir, `<root>/.lattice` for non-git. Shared files (`memories.db`, `parsed-cache.db`, `symbol-bodies/`, `embedding-objects/`) sit at the home root; per-checkout files (`graph.db`, `vectors.db`, `vectors.usearch`, `context_handles.json`) sit under `checkouts/<id>/cache/`. The shared/per-checkout split is enforced by path layout plus a GC allowlist (`DERIVED_FILES`, `storage/lifecycle.rs`) that can only ever reclaim the per-checkout `cache/` bundle. **The documented worktree model is real and matches the code.**

**Branch/HEAD invalidation** (`daemon/crates/lattice-daemon/src/repo_state.rs`). A `RepoStateTracker` keeps `observed` vs `indexed` `(git_dir, head_ref, head_oid)` and an epoch counter. Publication of a freshly built graph is epoch-gated: if HEAD moved while indexing was in flight, `can_publish_epoch` fails and the batch is discarded, so a branch switch mid-index cannot publish a stale graph. The design is right. But the `head_oid` half of the snapshot is unreliable in linked worktrees — see the corrected multi-worktree finding below.

**Storage safety under churn** (`storage/lifecycle.rs`). A `StorageRegistry` (SQLite, WAL + `synchronous=FULL`) tracks checkouts with per-checkout advisory file leases, a shared `maintenance.lock`, and a journaled, resumable derived-cache GC (`cache_gc_journal` with planned/moved/deleted states and a `trash/` dir). GC only reclaims a checkout bundle while it can take that checkout's *exclusive* lease, so a worktree in use is never collected. A "100-checkout churn" test exercises this. Memory aging runs through a single cross-process owner lock (`memory/repository_owner.rs`, `memory-owner.lock`), so extra worktrees or a second daemon cannot double-age the shared store — they time out with `MemoryStorageBusy`.

**Durability generally** is a genuine strength: atomic `BEGIN IMMEDIATE` publication, monotonic generations, trigger-based membership invalidation, crash-recovery tests. The security boundary (`security/workspace.rs`: `openat`+`O_NOFOLLOW` per component) and IPC credential handling are also strong. (These are covered in depth in the separate code-standard audit.)

## The central finding: two retrieval engines, and agents use the weaker one

Lattice contains two completely separate retrieval systems.

1. **`retrieval_v1/`** — a principled, deterministic, auditable ranker. Nine candidate sources gathered concurrently (`candidates.rs`), 13 weighted signals summed into a total score (`scoring.rs`), stable tie-break by identity string, and a rich `RankingDiagnostics` surface (per-source counts, per-signal raw/weighted/reason, budget-exhaustion flags). This is the engine the README's "ranking diagnostics / honest signals" language describes.

2. **`query/engine.rs` + `intelligence/agent.rs`** — a hand-tuned heuristic cascade: a base score (semantic sim or keyword/centrality) mutated by multiplicative penalties and caps with magic constants (variables ×0.25, test files ×0.3, migrations ×0.2, schema ×0.3–0.5, markdown ×0.15, a "negative keyword" cap to 0.04 when a name has ≥2 words absent from the query), then additive accumulators in `prepare_change`.

**`retrieval_v1` is wired into exactly one production caller: `working_memory/operations.rs`.** This is now verified two independent ways, not inferred:

- *Call-site search* — `retrieve_candidates`, `score_candidates`, `shape_retrieval_bundle`, and `RetrievalContext` have **zero** occurrences anywhere in the `lattice-daemon` crate (the entire MCP/RPC surface). The engine is physically unreachable from the tool handlers.
- *Direct handler trace* — I followed each tool from the dispatch table (`rpc/mcp.rs:~1796`): `context` → `tool_query_context` → `engine.query_with_progress()` (`QueryEngine`, `query/engine.rs`); `prepare_change` → `tool_prepare_change`, whose code context is `query_engine.query()` and whose memory is `load_relevant_memory_values()` → `MemoryStoreRouter::recall` / `store.recall_candidates()` (SQLite FTS/scope recall), with the bundle assembled by `intelligence::prepare_change`; `impact` → pure graph ops (`tool_blast_radius`/`tool_get_dependencies`/`tool_get_dependents`/`tool_find_relevant_tests`); `context --mode working_set` → `load_relevant_memory_values` + `get_working_set_context`. None of these touch `retrieval_v1`, and even the *memory* an agent receives is ranked by the simpler SQLite recall path, not the 13-signal scorer.

This is the most important product issue. It means:
- The auditable per-signal "why was this returned" diagnostics the docs lean on are **not** present on the main agent path. The heuristic engine's reasons are far thinner.
- The quality of agent-facing results rests on a cascade of magic constants that are sensitive to query phrasing. The 0.04 "negative keyword" cap in particular can near-zero a genuinely relevant symbol purely because its name contains two words not in the query — a real recall risk for the exact "find the working set" job the product exists to do.
- Two engines means two code paths to maintain, test, and keep honest. The investment in `retrieval_v1` is largely stranded relative to the product's headline use case.

The highest-leverage architectural move is to converge the agent-facing tools onto the `retrieval_v1` signal engine (or explicitly justify why code context needs a different ranker than working memory). Right now the sophisticated part is on the side road and the ad-hoc part is on the highway.

## What's useful

- **The worktree/branch storage model.** Shared memory + immutable objects with per-checkout graphs, enforced by layout and lease-gated GC, is correct and well-tested. The cold-worktree manifest reuse (skip reread/rehash/reparse for unchanged committed files) is a real performance win and a genuine differentiator. (Two seams in the surrounding machinery need work — the git-ref resolver and GC-under-churn, both below — but the storage *layout and isolation* itself is sound.)
- **The memory trust model.** Separating confidence / evidence strength / behavioral verification / checkout applicability / contradiction / retention age into independent dimensions, with recall renewing *retention only* and not erasing drift, is the right design for not poisoning an agent with stale "lessons." The verification runner (declared executables, no shell, bounded, bound to source state before/after) is the correct way to make "verified" mean something.
- **Honest availability signals.** The health module's `FactAvailability {Available, Degraded, Unavailable}` with "unknown is never zero," and risk `BandRange` that *widens* when inputs are missing rather than faking precision, is the most rigorous part of the codebase. Agents can trust partial results because partiality is reported, not hidden.
- **Durability and the security boundary.** Covered above; these are production-grade.
- **The principled ranker itself** (`retrieval_v1`) is genuinely good — deterministic, auditable, degrades cleanly without embeddings (top weights are exact-identifier 1.4 and graph-proximity 1.1, so anchored queries stay strong). Its problem is placement, not quality: it serves working memory, not the agent-facing code-context tools. That is why it appears again under "what's not useful" — the asset is real but mislocated.

## What's not useful, or at risk

- **The stranded principled ranker** (above) — the biggest one.
- **Natural-language queries without embeddings** go through `engine.rs`'s keyword/name fallback, which is a clear second tier. The Explore-intent IDF file-path seeding and 4-hop call BFS exist specifically to paper over this, with comments admitting the weakness. "How does auth work" with no vector index is the weakest real case.
- **Per-source truncation before global scoring** (`candidates.rs`). Each source is capped (24/source, embeddings top-12, FTS 24) *before* the global scorer sees anything, so a high-value candidate ranked 13th by embeddings is dropped before ranking. Truncation can hide the best result.
- **A latent clamp bug**: intent raises graph hops to 3 for Debug/Refactor/Review, then `.min(budget.max_graph_hops)` where the default is 2 — so the intent-based deepening is silently clamped back to 2 (`candidates.rs`, `intent_graph_hops` vs the `.min`). The heuristic never actually fires at its intended depth.
- **ANN tie-break non-determinism** (`storage/usearch_index.rs`): equal cosine scores sort with no secondary key and truncate to top_k, so ties reorder across index rebuilds — a small but real violation of the "deterministic for the same store" promise, on the agent path.
- **Graph edges are name-based, not type-resolved** (`graph/builder.rs`, pass 2). This is the fidelity ceiling under everything else, and I missed it in the first pass. Cross-symbol `Calls` edges (pass 2d) resolve a reference by its bare simple name: try a same-file symbol with that name, else fall back to "the first symbol with that name anywhere in the repo" (`name_lookup.get(simple).first()`, insertion order). There is no scope or type resolution, so every `run`/`handle`/`process`/`get`/`new`/`build` across the repo collapses onto one arbitrary target — producing false edges in any large or polyglot codebase. Imports (pass 2a) are more precise but `resolve_import_path` only handles *relative* imports and appends the source file's own extension; non-relative imports (`import numpy`, `from app.auth import x`, `use crate::auth::login`, Go module paths) are returned verbatim, never match a file, and degrade to the same weak global name-match. **Consequence:** the graph is a useful *approximate* graph — fine for seeding retrieval, which then re-ranks — but materially weaker for `impact`/blast-radius, which (per the trace above) is pure graph traversal with no re-ranking. `impact` will over-report (edges to same-named symbols) and sometimes mis-resolve a real call, worst in Rust/Go/package-import ecosystems and repos with common method names. The docs' "blast radius grep cannot compute" promise is only as true as these edges.
- **Surface area vs. adoption.** The feature set (organization memory, delivery receipts, feedback dispositions, evolution/supersession, cache plan/apply, backup/restore, relocation) is very large for a single-user local tool. The docs themselves concede the hard part is unproven: hooks don't enforce behavior by default, and whether an agent *uses* the returned context "requires actual tool-call traces" (the Beacon acceptance exercise, `docs/agent-workflow.md`, is explicitly still open). The risk is that a lot of sophisticated machinery is built below an adoption question that hasn't been answered yet.

## Multi-worktree / multi-branch: where it will bite

You flagged this as the usual failure zone. The storage model holds up well; the risks are concentrated in three places. (The first was corrected and tightened during the verification deep dive — the original phrasing was too loose.)

1. **Two divergent git-ref resolvers in one crate — and the one on the freshness-check path is wrong for linked worktrees.** This is a precise, reproduced bug, not a vague "the two models can disagree." The daemon has *two* hand-rolled ref resolvers:
   - `watcher.rs` (`read_checkout_head` / `resolve_ref_target` / `git_ref_directories`, ~lines 1302-1392) reads the worktree's `commondir` file and searches *both* the per-worktree gitdir and the common dir. This one is **correct**.
   - `repo_state.rs` (`resolve_ref_oid`, ~lines 164-187) looks only in `<gitdir>/refs/...` and `<gitdir>/packed-refs`, and never reads `commondir`. For a linked worktree the branch ref lives in the *common* dir, so this returns `head_oid = None`.

   I reproduced the consequence against a real `git worktree` on disk: in a linked worktree, a same-branch commit moved the real OID from `cd77417…` to `936ad46…`, but the `repo_state.rs` snapshot was byte-identical before and after (`head_ref=refs/heads/feature`, `head_oid=NONE` both times). So `RepoStateTracker::validate()` reports `Fresh` across a HEAD that actually moved. The watcher's native-event path still catches the commit (it uses the correct resolver and triggers a re-index), so the window where this bites is: the `validate()`-on-query freshness check and the degraded-polling / query-before-the-watcher-batch-lands cases — there a linked worktree can be told a stale graph is `Fresh` after a same-branch commit/amend/rebase/pull. Branch *switches* are still caught because `head_ref` changes. The fix is a single shared ref resolver (the `watcher.rs` one already works); keeping two is itself the "single source of truth" violation from the shared coding standard.

2. **Everything cross-process is advisory locking.** Checkout leases and `memory-owner.lock` are `flock`-style advisory locks released by the kernel on exit. They protect against well-behaved Lattice daemons but not against a non-Lattice writer, and on network/union filesystems where advisory locks are unreliable two daemons could both believe they own aging and race on the shared `memories.db`. Worth at least detecting the filesystem and refusing/ warning on unreliable lock substrates.

3. **GC starvation under constant churn** (verified against `advance_inventory`, `lifecycle.rs:~317-382`). The automatic watermark GC can only reclaim after `advance_inventory` finishes paging through *all* checkouts within one stable registry `generation`. Every checkout insert/delete/root-change bumps `generation` via SQL triggers, and mid-cycle the code detects the bump and **resets the cursor to empty, restarting the whole traversal** (`cursor=''`, `invalidated=1`). `plan_gc` bails with "cache pressure is unknown until a fresh bounded inventory cycle completes" whenever accounting is incomplete. So if worktrees are added/removed — or agents merely connect, since `register_and_lease` is an insert — faster than `ceil(N / page_limit)` advance calls can complete *uninterrupted*, the cycle never finishes, `invalidated` never returns to 0, and automatic reclamation never runs. A fleet that creates a worktree per task can accumulate `cache/` bundles indefinitely. **Mitigation that does exist:** this starves only the *automatic* watermark GC — the operator `storage cache plan/apply` path and the lease-gated manual GC still function, and knowledge/events are never GC candidates, so this is a disk-reclamation problem, not a correctness or data-loss one. The fix is a churn-robust accounting mode (e.g. per-checkout incremental accounting that survives a generation bump) so reclamation can make progress without a globally quiescent registry.

## Recommendations, by leverage

1. **Converge the agent-facing tools (`context`/`prepare_change`/`impact`/`diagnose`) onto the `retrieval_v1` signal engine**, or document a concrete reason code context needs a different ranker than working memory. This aligns the product with its own best engine and its honesty story. Highest leverage by far.
2. **Collapse the two git-ref resolvers into one, commondir-aware resolver.** `repo_state.rs::resolve_ref_oid` should use the `watcher.rs` logic that already reads `commondir`, so the freshness-check path stops being blind to same-branch commit movement in linked worktrees. This is a small, well-scoped fix with a clear regression test (the on-disk fixture above).
3. **Raise graph-edge fidelity, or scope `impact`'s promise to it.** Either improve edge resolution past bare-name matching (scope/type resolution, real import-path resolution for non-relative imports and index/`__init__`/`mod.rs` targets) or make `impact` explicit that its edges are name-approximate and have it report confidence. As-is, `impact` is the tool most exposed to the fidelity ceiling.
4. **Fix the retrieval correctness nits**: the 3-hop clamp, per-source pre-scoring truncation (raise caps or do a global merge before truncation), and the ANN tie-break secondary key.
5. **Prove adoption before adding features.** Run the Beacon 100-task exercise that the docs already specify; measure matched runs with and without Lattice. Treat it as the gate it's described as. Several of the large subsystems should be justified by that evidence, not shipped ahead of it.
6. **Harden multi-worktree operationally**: detect unreliable lock filesystems; add a churn-robust GC path so disk is reclaimable even under constant worktree turnover.

## Bottom line

The foundations are strong and often exceed their documentation: the storage/worktree *layout*, durability, the security boundary, and the memory trust model are production-grade and honest. After the verification deep dive, the gap is clearer and sits at two levels. At the top of the stack, the context an agent receives is produced by a heuristic engine while the principled, auditable ranker the docs describe is confined to working memory — proven, not inferred, by a zero-hit call-site search and a full handler trace. Underneath it, the graph those tools rank over is a name-approximate graph, which caps how good `impact` can be regardless of ranking. The multi-worktree seams are real but narrower than first stated and each has a concrete, small fix: one commondir-aware ref resolver, and a churn-robust GC accounting mode. None of the verified issues is a data-loss or security bug — the durability and boundary work holds. Close the retrieval-placement gap, unify the git resolver, raise edge fidelity (or scope `impact`'s promise), and validate adoption with the Beacon exercise, and this is a genuinely useful tool for agents across many branches and worktrees. Leave it as-is and the risk is a large, well-engineered substrate serving merely adequate, sometimes stale context through a side door.

## Appendix: verification method and its limits

- **Direct source reading** of the dispatch and retrieval paths (`rpc/mcp.rs`, `query/engine.rs`, `retrieval_v1/*`), the two git-ref resolvers (`repo_state.rs`, `watcher.rs`), the GC/inventory path (`storage/lifecycle.rs`), and graph edge construction (`graph/builder.rs`). The two-engine finding is backed by a crate-wide search showing zero `retrieve_candidates`/`score_candidates`/`shape_retrieval_bundle`/`RetrievalContext` references in `lattice-daemon`.
- **On-disk git reproduction** of the linked-worktree ref-resolution bug: a real `git worktree` with a same-branch commit, showing `repo_state.rs`'s inputs resolve to `head_oid = NONE` before and after the commit while the real OID moved. The fixture was created in a temp dir and removed after.
- **Not performed:** a full daemon runtime test (indexing a repo, issuing live `context`/`impact`/`status` calls, switching branches against the running service). This environment has no `cargo`/`rustc` and no prebuilt `lattice` binary, so the daemon could not be built or run. Claims about *runtime* retrieval quality (e.g. how often the heuristic cascade's magic constants mis-rank in practice, real `impact` false-edge rates) are therefore reasoned from the code, not measured. The Beacon acceptance exercise remains the right way to get those numbers.
